05. Gradle & 빌드

Python의 pyproject.toml + pip가 Kotlin에선 build.gradle.kts + Gradle wrapper.

JVM 생태계의 빌드 도구 간략 역사

도구등장스타일현 위치
Ant2000XML 스크립트거의 안 씀 (legacy)
Maven2004XML (pom.xml) 선언적여전히 많음 (엔터프라이즈)
Gradle2007Groovy DSL → Kotlin DSL신규 프로젝트 대세 (특히 Android/Kotlin)

이 프로젝트는 Gradle + Kotlin DSL (build.gradle.kts). .kts는 "Kotlin Script" 확장자로, 빌드 스크립트를 Kotlin 문법으로 쓴다. IDE가 자동완성/타입체크 지원하니 Groovy(.gradle)보다 훨씬 읽기 쉽다.

Gradle Wrapper — "Gradle을 따로 설치할 필요가 없다"

프로젝트 루트의 gradlew, gradlew.bat, gradle/wrapper/ 디렉토리가 wrapper다. 이것들을 커밋해두면, 팀원이 git clone 후 바로 ./gradlew build 하면 된다. Gradle이 설치 안 돼 있어도 wrapper가 지정된 버전을 자동 다운로드.

Django 비교 — Python은 python -m venv + pip install을 팀원이 각자 해야 한다. Gradle wrapper는 그게 필요 없다. JDK만 있으면 나머지는 wrapper가 처리.

build.gradle.kts 구조

이 프로젝트의 backend/build.gradle.kts를 섹션별로 분해:

// 1) 플러그인 — 언어/프레임워크 설정
plugins {
    kotlin("jvm") version "1.9.25"            // Kotlin on JVM
    kotlin("plugin.spring") version "1.9.25"   // Spring과 Kotlin 연동
    kotlin("plugin.jpa") version "1.9.25"      // JPA entity를 open 클래스로
    id("org.springframework.boot") version "3.5.3"
    id("io.spring.dependency-management") version "1.1.7"
}

// 2) JDK 버전
java {
    toolchain { languageVersion = JavaLanguageVersion.of(21) }
}

// 3) 의존성 저장소
repositories { mavenCentral() }

// 4) 의존성 — 이게 핵심
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    implementation("org.springframework.boot:spring-boot-starter-data-jpa")
    implementation("org.springframework.boot:spring-boot-starter-security")
    runtimeOnly("org.postgresql:postgresql")  // 실행 시만 필요

    testImplementation("org.springframework.boot:spring-boot-starter-test")
    testImplementation("org.testcontainers:postgresql")
}

// 5) Kotlin + Spring 통합 옵션
allOpen {
    annotation("jakarta.persistence.Entity")      // @Entity 클래스를 open으로 (Hibernate proxy 용)
    annotation("jakarta.persistence.MappedSuperclass")
}

// 6) Task 설정
tasks.withType<Test> {
    useJUnitPlatform()
}

의존성 scope — implementation / testImplementation / runtimeOnly

scope언제 쓰나pip 비교
implementation컴파일 + 런타임 모두 필요 (일반)install_requires
testImplementation테스트 코드에서만dev-dependencies / [dev]
runtimeOnly컴파일 시엔 노출 안 함, 실행 시만 (DB 드라이버 등)해당 개념 없음
api라이브러리 작성 시, 쓰는 쪽에도 노출해당 개념 없음
왜 PostgreSQL을 runtimeOnly로? 컴파일 단계에서 org.postgresql.Driver를 직접 import할 일이 없다 (JDBC URL로 리플렉션 로드). 실행 시만 있으면 됨. 실수로 코드에서 Postgres 전용 클래스에 의존하는 걸 방지.

"Starter"라는 묶음 — 스프링 생태계의 관습

spring-boot-starter-web은 하나의 패키지가 아니다. 여러 라이브러리를 묶은 메타 패키지:

starter 1개 = 실제로는 수십 개 라이브러리의 버전 궁합이 맞춰진 묶음

덕분에 "Spring Web 쓰려면 jackson, tomcat, validator 등 뭐뭐를 넣어야 하지?" 고민이 사라진다. Spring Boot의 핵심 기여가 이 starter 생태계다.

자주 쓰는 Gradle 명령

명령하는 일
./gradlew build컴파일 + 테스트 + 패키징
./gradlew test테스트만

./gradlew dependencies의존성 트리 확인

심화 Q&A — 자주 헷갈리는 지점

Q. classpath가 뭐야?

classpath = JVM이 "실행 시 클래스 파일(.class)과 리소스를 어디서 찾을지" 알려주는 경로 목록. Python의 PYTHONPATH, Node.js의 NODE_PATH와 비슷한 개념.

JVM은 new ProductController()를 실행할 때 "ProductController라는 이름의 .class 파일"을 classpath에서 찾는다. classpath에 없으면 ClassNotFoundException.

classpath에 들어가는 것들

  • 내가 작성한 코드를 컴파일한 .class 파일 (build/classes/...)
  • 의존성으로 받은 라이브러리 jar (~/.gradle/caches/.../spring-boot-starter-web-3.5.3.jar)
  • 리소스 파일 (application.yml, static/, templates/ 등)

Spring과 classpath — Spring Boot의 많은 기능이 "classpath에 X가 있으면 Y를 자동 설정"한다. 예:

classpath에 있으면Spring Boot가 자동으로
spring-webmvc jar내장 Tomcat + DispatcherServlet + @RestController 스캐너 켬
spring-data-jpa jarDataSource, EntityManagerFactory, @Repository 스캐너 켬
hibernate-validator jar@Valid 처리 활성화
application.yml에 spring.cache.type=caffeine + classpath에 caffeine@EnableCaching 시 Caffeine을 캐시 구현체로 선택

그래서 "의존성만 build.gradle.kts에 추가하면 대부분 작동"한다. 내부적으로 Spring이 classpath 스캔을 하기 때문.

application.yml의 classpath:db/migration도 같은 개념. 이 프로젝트:

# application.yml
spring:
  flyway:
    locations: classpath:db/migration     # ← classpath 루트에서 db/migration/ 하위를 찾아라

빌드 시 backend/src/main/resources/db/migration/*.sql이 jar 안 db/migration/으로 들어간다. Flyway가 실행 시 classpath에서 그 경로를 스캔.

Q. spring-boot-starter-web 실물은 우리 프로젝트 어디에 있어?

우리 프로젝트 안에는 없다. Gradle이 Maven Central에서 받아 홈 디렉토리의 공용 캐시에 보관한다. 모든 프로젝트가 같은 캐시를 공유.

~/.gradle/caches/modules-2/files-2.1/org.springframework.boot/spring-boot-starter-web/3.5.3/
├── <hash>/spring-boot-starter-web-3.5.3.jar      # 실제 jar
├── <hash>/spring-boot-starter-web-3.5.3.pom      # 의존성 메타데이터
└── ...

프로젝트 내부에는 무엇이 있나?

  • backend/build.gradle.kts — implementation("org.springframework.boot:spring-boot-starter-web") 선언 1줄
  • backend/gradle/wrapper/gradle-wrapper.properties — Gradle 버전 지정
  • backend/.gradle/ (gitignore) — 로컬 Gradle 작업 캐시 (빌드 증분, task 결과 등)
  • backend/build/ (gitignore) — 컴파일 결과, jar 패키지

실행 시점에는? — Gradle이 classpath를 조립해 JVM에 전달. ./gradlew bootRun을 돌리면 ~/.gradle/caches/.../spring-boot-starter-web-3.5.3.jar가 classpath에 포함된 상태로 JVM이 뜬다.

검증 명령:

./gradlew dependencies --configuration runtimeClasspath | head -30

의존성 트리 출력. spring-boot-starter-web이 transitive로 가져오는 것들(tomcat, jackson, spring-webmvc, ...)도 전부 표시된다.

Q. ./gradlew로 실행하면 Gradle은 어디에 설치되나? 프로젝트에 캐시로 남나?

Gradle 자체는 사용자 홈 공유 캐시에 저장. 프로젝트 디렉토리가 아니다.

# 1) wrapper가 가리키는 Gradle 버전
# backend/gradle/wrapper/gradle-wrapper.properties
distributionUrl=https\://services.gradle.org/distributions/gradle-8.14.4-bin.zip

# 2) 첫 ./gradlew 실행 시 다운로드되는 위치
~/.gradle/wrapper/dists/gradle-8.14.4-bin/<hash>/gradle-8.14.4/
├── bin/gradle                 # 실제 Gradle 실행 파일
├── lib/                       # Gradle 내부 라이브러리
└── ...

흐름

  1. 팀원이 git clone → backend/gradlew(스크립트)만 있음. Gradle 실체는 없음
  2. ./gradlew build 최초 실행 → wrapper 스크립트가 gradle-wrapper.properties의 distributionUrl 읽음
  3. 해당 zip을 ~/.gradle/wrapper/dists/로 다운로드 후 unzip (20~40초)
  4. 그 Gradle을 사용해 build 수행
  5. 2회 차부터는 캐시 활용으로 다운로드 없음

그래서 "고정 버전 Gradle이 프로젝트에 캐시로 남나?" — 프로젝트 폴더 안에는 없다. 전역 ~/.gradle/wrapper/dists/에 있고, 같은 버전을 쓰는 다른 프로젝트가 재사용한다.

프로젝트 로컬 캐시는 다른 성격:

경로내용git 포함?
~/.gradle/wrapper/dists/Gradle 배포판 본체 (버전별)아님 (홈)
~/.gradle/caches/modules-2/다운로드한 의존성 jar (프로젝트 전체 공유)아님 (홈)
backend/.gradle/프로젝트 빌드 증분 캐시 (task 결과, 컴파일된 .class 체크섬)gitignore
backend/build/컴파일 결과, jar 패키지gitignore

캐시 정리

./gradlew --stop           # Gradle daemon 종료
rm -rf backend/.gradle backend/build    # 프로젝트 캐시만 삭제
rm -rf ~/.gradle/caches     # 전역 의존성 캐시까지 삭제 (재다운로드 발생)

정리

  • 빌드 도구는 Gradle (Kotlin DSL)
  • build.gradle.kts 6개 섹션: plugins / java / repositories / dependencies / 플러그인 옵션 / tasks
  • implementation / runtimeOnly / testImplementation scope 구분
  • starter로 관련 라이브러리 묶음 받음
  • gradlew 덕에 팀원 Gradle 설치 불필요 (Gradle 본체는 ~/.gradle/wrapper/dists/에 공용)
  • 의존성 jar도 ~/.gradle/caches/에 공용. 프로젝트 폴더 안에는 선언(.kts)과 빌드 산출물만

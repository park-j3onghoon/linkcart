Section A — Kotlin 언어 기초

Q1 기본
Kotlin의 val과 var의 차이는? 그리고 val list = mutableListOf(1,2,3)에서 list.add(4)는 허용되나?
val = 재할당 불가한 참조 (read-only reference). var = 재할당 가능.
val은 "불변 객체"가 아니라 "참조 재할당 금지". list.add(4)는 참조 자체는 안 바뀌므로 허용.
면접관이 "val = final/const 같은 거죠?" 같은 오답을 유도하는 경우 있음. "참조 재할당 금지이고 객체 mutability와 별개"를 명확히 구분해서 답변.
Q2 기본
Kotlin data class가 자동 생성하는 5가지 메서드는? Python @dataclass와 가장 큰 차이 1가지?
equals / hashCode / toString / copy / componentN (destructuring).
차이: Kotlin의 copy(field = newValue)는 명명 파라미터로 일부 필드만 변경한 새 객체 반환. Python은 dataclasses.replace(obj, field=newValue)로 같은 기능 제공하지만 data class 자체 메서드는 아님.
Q3 기본
sealed interface ParseResult의 핵심 가치는? enum class로 대체할 수 없는 이유?
when exhaustive check — 모든 subtype 처리 안 하면 컴파일 에러. 새 subtype 추가 시 처리 안 한 모든 when 블록에 자동 에러. 실수로 빠뜨리는 게 불가능.
enum은 값만 가질 수 있지만, sealed는 각 subtype이 다른 필드를 가질 수 있다. Success(product), Partial(fields map), Failure(reason) — 모두 구조가 다름.
Rust Result<T, E>, Haskell Either과 같은 "닫힌 합(sum) 타입" 철학. 예외 던지지 않고 타입으로 표현하는 Railway-Oriented Programming.
Q4 코드
아래 Kotlin 코드에서 ==의 의미는?
val a = Money(1000L, "KRW")
val b = Money(1000L, "KRW")
println(a == b)   // ?
println(a === b)  // ?
a == b → true (구조적 동등성, data class의 equals 자동 구현).
a === b → false (참조 비교, 서로 다른 객체).
Kotlin의 ==는 Java의 .equals(). Java의 ==는 Kotlin의 ===. 반대라 헷갈리기 쉬움.
Q5 기본
Money의 amount를 왜 Double이 아닌 Long으로 선언하나?
Double은 IEEE 754 부동소수점 → 0.1 + 0.2 ≠ 0.3. 금액 정산/결제 시 오차 발생. Long은 64비트 정수, 원화처럼 원 단위 정수 통화에 정확.
대안: BigDecimal (정밀 소수) — 다국가 통화 지원 시 고려. 이 프로젝트는 KRW 원 단위 기본이라 Long 충분.
"왜 Int 아닌 Long?" 추가 질문: Int는 32비트 (21억). 대규모 금액(총 매출, 글로벌 누적 등)은 21억 초과. Long(9 × 10¹⁸)이 안전.

Section B — Spring Boot / DI

Q6 기본
@RestController, @Service, @Component 셋의 기술적 차이? 왜 구분하나?
기술적으로 모두 @Component의 특수화. Spring은 셋 다 동일하게 Bean으로 등록.
구분 이유: 의도 전달. @RestController=HTTP 진입점, @Service=비즈니스 로직, @Component=기타 유틸. 코드 읽는 사람이 레이어를 즉시 파악.
@Repository는 추가로 DB 예외 변환 기능 있음.
Q7 에세이
Spring DI가 Django의 "View에서 직접 객체 생성" 방식에 비해 가지는 장점 3가지?
  1. 테스트 용이: 생성자로 의존성 주입 → 테스트에서 mock을 넣기 쉬움. Django는 View 내부에서 객체 생성 시 patch/mock.patch 남발.
  2. 교체 가능: interface에 의존하면 구현체 교체가 쉬움. OgParser → MockParser로 테스트 시 구현체만 갈아끼우기.
  3. 책임 분리: Controller/Service/Repository 레이어 간 의존성을 Spring이 관리 → 각자 자기 일에 집중.
Q8 기본
kotlin("plugin.spring") 플러그인이 왜 필요한가?
Kotlin 클래스는 기본 final (상속 불가). Spring은 @Configuration, @Service 등의 클래스를 CGLIB 프록시로 감싸 AOP/트랜잭션/캐시를 구현 → 프록시는 원본을 상속해야 함.
이 플러그인이 Spring 어노테이션이 붙은 클래스를 자동으로 open으로 변환.
면접 심화: "그럼 JPA Entity는?" → 별도 kotlin("plugin.jpa")로 @Entity도 open 처리. 이 프로젝트 P2-1에서 추가.
Q9 기본
Spring Boot에서 캐시를 붙일 때 고려해야 할 4가지는?
  1. TTL (Time To Live): 얼마나 오래 유지할지
  2. Cache key: 무엇을 키로 쓸지 (URL? user id + URL?)
  3. Stale data: 낡은 데이터 허용 여부, 외부 상태 변경 시 대응
  4. Invalidation: 무효화 조건 (이 프로젝트는 Failure 미캐시)
tnear 시험 Q15 원문. 이 프로젝트는 TTL 5분 + URL key + Failure 미캐시 (unless로) 조합.

Section C — 아키텍처

Q10 코드
다음 4개 import 중 클린 아키텍처 위반은?
// a) application/auth/usecase/LoginWithGoogle.kt
import com.linkcart.domain.entity.User

// b) domain/entity/User.kt
import com.fasterxml.jackson.annotation.JsonValue

// c) domain/port/UserRepository.kt
import com.linkcart.infrastructure.adapter.UserEntity

// d) infrastructure/adapter/UserRepositoryAdapter.kt
import com.linkcart.application.auth.usecase.LoginWithGoogle
c가 위반 (domain이 infrastructure import) — 의존 방향 역전.
d도 일부 위반 가능성 (infrastructure adapter가 application usecase를 아는 건 드문 경우). 정상이면 infrastructure는 domain port만 구현.
b는 논쟁 여지: domain이 Jackson (infra 라이브러리) 의존. 이 프로젝트는 Mall/ParserName/AuthProvider 선례로 허용 (실용적 타협).
면접에서 a/b/c 네 개를 보여주고 "의존 위반 찾아보세요"는 시니어 코드 리뷰 시뮬레이션 단골.
Q11 에세이
DB를 MySQL에서 PostgreSQL로 교체한다고 할 때, 이 프로젝트의 어느 레이어가 영향받고 어느 레이어는 영향받지 않나?
영향받음: infrastructure/adapter/persistence (JPA Entity, Adapter 구현), Flyway migration SQL 파일 (BIGSERIAL vs IDENTITY 등 DB 문법), application.yml (driver class, URL).
영향 없음: domain (User, UserProduct 등), application (UseCase, Port interface), presentation (Controller, DTO).
이것이 Clean Architecture의 실제 이득. Django ORM 프로젝트는 model이 곧 DB라 전체에 영향.
"Django 경험과 비교"를 물으면: Django는 Model.objects.filter가 어디서든 호출되어 전면적 impact. Port/Adapter는 인프라 교체 시 수정 범위를 1개 어댑터 클래스로 축소.
Q12 기본
OgParser / CoupangApiClient / ElevenStApiClient / ProductParseUseCase를 Domain/Application/Infrastructure/Presentation 중 어디에 배치하나?
  • ProductParseUseCase: application (유스케이스 오케스트레이션)
  • OgParser: infrastructure/adapter/parser (Jsoup 같은 외부 라이브러리 의존)
  • CoupangApiClient: infrastructure/adapter/parser (외부 HTTP API 호출)
  • ElevenStApiClient: 동일 infrastructure

Parser interface (ProductParser)는 domain/port에 둠. 도메인이 "파싱 능력"이라는 개념을 계약으로 정의.

Section D — 외부 통신 / 장애 대응

Q13 에세이
전용 API 파서가 실패했을 때 왜 OG 파서로 폴백하나? 즉시 에러 반환하면 안 되는 이유?
외부 API (쿠팡/11번가) 장애는 우리가 통제 못 함. 즉시 에러 반환하면 외부 장애 = 사용자 장애. OG 파서는 HTML meta 태그 파싱이라 대상 몰 서버만 살아있으면 최소 정보 제공 가능.
원문 (pr3.html): "전용 파서가 실패했다고 해서 요청 전체를 즉시 실패시키면, 외부 API 장애가 곧 사용자 장애가 된다."
티니어 "24/365 장애 없는 환경" 요구의 실전 답. graceful degradation.
Q14 기본
@Cacheable의 unless 옵션으로 Failure를 제외하는 이유?
외부 API가 잠깐 장애일 때 실패가 캐시되면, 실제 복구된 뒤에도 5분간 실패 계속 반환. "실패 결과는 캐시하지 않는다"는 운영 원칙.
원문: "실패를 오래 보관하면, 실제 복구 뒤에도 계속 실패를 재사용하게 되기 때문이다."

Section E — 인증 / 보안

Q15 기본
이 프로젝트가 세션 대신 JWT를 선택한 가장 큰 이유?
모바일 클라이언트(Expo)의 존재. 네이티브 앱은 쿠키 관리가 번거롭고 Bearer 헤더가 표준. 웹+앱 통일 인증 전략을 위해 JWT 채택.
보조: stateless라 확장성. Redis 세션 스토어 인프라 불필요.
단순히 "JWT가 대세라서"는 얄팍한 답. 이 프로젝트의 구체적 요건(모바일)을 드는 게 설득력 있음.
Q16 기본
Refresh Token rotation에서 reuse 감지 시 왜 같은 user의 다른 active Refresh까지 전부 revoke하나?
Refresh 재사용 = "어디선가 탈취됐다"는 강한 신호. 공격자가 R1을 쓰고 정상 사용자는 이미 R2로 rotate한 상태. 어느 쪽이 공격자인지 서버는 구분 불가.
정상 사용자 재로그인 불편 vs 공격 창 확장. 안전 쪽 선택. 정상 사용자는 다시 로그인 + 이상 알림 수신.
Q17 기본
Refresh Token은 JWT가 아닌 opaque (무작위 문자열)인 이유?
Refresh는 rotation과 revoke가 필수 → 어차피 DB state 필요. JWT의 "stateless 검증" 이점이 사라짐.
JWT payload에 정보 노출 대신 의미 없는 무작위 문자열(opaque) + DB에 SHA-256 해시만 저장 → DB 유출 시에도 원본 복구 불가.
Q18 기본
SSRF 공격에서 AWS EC2의 169.254.169.254가 왜 특히 위험한가?
AWS EC2 instance의 metadata endpoint. 여기서 IAM role의 임시 자격증명(AccessKey/SecretKey/Token)을 조회할 수 있음. 공격자가 SSRF로 이 엔드포인트 접근 → 서비스의 AWS 자원 전체 장악 가능.
이 프로젝트 SafeUrlChecker는 isLinkLocalAddress로 169.254.x.x 대역 전체 차단.
Q19 기본
왜 이미지 프록시에서 SVG content-type을 차단하나?
SVG는 이미지이면서 XML. 내부에 <script> 태그를 가질 수 있어 XSS 벡터. 우리 origin에서 서빙되면 우리 JS 권한으로 실행.
해결: allow-list(png/jpeg/gif/webp)로 기본 거부. 안전하지 않은 포맷은 명시적으로만 허용.

Section F — 면접 시뮬레이션 (서술형)

Q20 면접
"Python/Django 주력이었는데 왜 Kotlin/Spring으로 이직 준비하시나요?"
프레임: "언어를 바꾸는 게 아니라, 이미 가진 역량을 더 강한 타입 시스템 위에서 발전시키는 것."

답변 예시: "Python/Django로 5년 실무 했고, N+1 해결, 결제 API fail-fast, 백업 DB 재설계 같은 경험을 쌓았습니다. 이 경험들의 본질은 '장애 대응 + 확장성 + 유지보수성'인데, 정적 타입 시스템과 Spring 생태계 위에서 이걸 더 잘 표현할 수 있다고 판단했습니다.
특히 Kotlin의 sealed interface, null safety 같은 타입 시스템 기능은 Python에서 mypy로 강제했던 규약을 컴파일러가 강제해주는 구조고, Spring의 DI + Clean Architecture는 Django에서 service layer로 우회했던 패턴의 언어 수준 지원입니다.
linkcart 프로젝트를 직접 만들며 이 전환 과정을 증명했습니다."
"Python 강점을 버리지 않는다"가 핵심 메시지. 기술 스택 학습 중이지만 설계/장애 대응/팀워크 역량은 이전되는 것.
Q21 면접
"대규모 트래픽 다뤄본 적 없는데 티니어 날씨 앱(전 세계 6천만 다운로드)에 어떻게 기여하실 건가요?"
정직 + 증거: "제 실전 트래픽 경험은 제한적입니다. 다만 linkcart를 설계하며 대규모 트래픽 대비 기법은 적용했습니다:

• Caffeine TTL 캐시 + @Cacheable unless Failure로 불필요 외부 API 호출 방지
• 외부 HTTP 3초 timeout + Fallback chain으로 단일 외부 장애가 전체 서비스 장애로 번지지 않게
• DB에 (user_id, source_url) UNIQUE + 부분 인덱스로 쓰기 성능과 조회 성능 균형
• SSRF 7단계 방어로 내부망 접근 공격 차단

이전 Django 경험에서도 N+1 쿼리 5시간→15분 단축, 외부 결제 API 지연 시 fail-fast 적용 같은 성능 개선은 있었습니다. 스케일 차이는 있지만 원칙과 도구는 공유되므로 빠르게 따라잡을 수 있다고 봅니다."
약점은 숨기지 말고, 그 약점을 보완하는 구체적 학습 증거로 방어.
Q22 면접
"코드 리뷰를 받을 때 어떤 태도를 가지시나요?"
"피드백은 항상 설계 근거와 함께 반영합니다. 'A가 좋겠어요' 코멘트를 받으면 (1) 현재 코드가 왜 B였는지 정리, (2) A와 B의 트레이드오프 비교, (3) A 채택 시 어떤 부분을 함께 바꿔야 하는지 판단.

실제로 linkcart에서 PR-BE3는 plan-review에서 FallbackProductParser marker interface가 YAGNI라는 제안을 받았는데, Spring DI ambiguous 회피라는 이유로 마커를 유지하면서 명확히 문서화했습니다. 피드백 수용이 무조건 옳은 건 아니고, 근거 있는 유지도 리뷰의 일부라 봅니다."
Q23 면접
"속도와 품질 중 어느 쪽을 우선시하나요?"
"단계별로 다릅니다. 가설 검증 단계는 속도 우선 (작고 빠른 PR, 테스트 최소), 프로덕션 운영 단계는 품질 우선 (회귀 테스트, SSRF 방어, 관측성).

linkcart에서 Phase 1 MVP는 PR 단위 100~200줄로 빠르게 돌렸고, 리팩토링 트랙(BE1~BE6)에서 테스트 커버리지와 보안을 보강했습니다. '빠른 실험, 빠른 실패' + '운영 안전성'은 충돌이 아니라 단계별 책임 배분이라고 생각합니다."
티니어 공고의 "빠른 실험, 빠른 실패" 문구에 정확히 대응. "나는 둘 다 한다"가 정답 프레임.

Section G — 시스템 설계

Q24 설계
linkcart 파싱 API에 갑자기 트래픽이 10배 몰렸다. 제한된 시간/자원 내에서 어떤 순서로 대응하겠는가?
우선순위:
  1. 관측 먼저: 어느 API가 병목? 외부 호출이 느린가 DB가 느린가? 메트릭/로그 확인.
  2. 캐시 TTL 확대: 5분 → 15분. 같은 URL 반복 호출 흡수. stale 허용.
  3. 외부 호출 timeout 축소: 3초 → 2초. 장애 외부 API가 자원 점유 못 하게.
  4. ThreadPool 조정: Tomcat max-threads / HikariCP maxPoolSize 확인. 병목 지점에 맞춰.
  5. Rate limiting: 동일 IP/user 초당 N회로 제한 (Resilience4j Bulkhead).
  6. 수평 확장: 위 조치 후에도 부족하면 인스턴스 추가 (stateless라 쉬움).

원칙: 관측 → 소프트 대응 (설정) → 수평 확장 순서. 처음부터 인스턴스 추가는 비용 대비 효과 불명확.
Q25 설계
날씨 앱이 전 세계 사용자에게 10분마다 날씨를 조회한다. 캐시 전략과 장애 격리를 어떻게 설계하겠는가?
  • 지역별 캐시 키: (city, date-hour) 단위. 1시간 내 같은 지역 요청은 캐시 히트.
  • 외부 날씨 API 장애 대비 Fallback: primary=OpenWeather, fallback=AccuWeather. 둘 다 실패 시 최근 성공한 캐시를 stale로 제공하되 "업데이트 지연" 메타 표시.
  • 모바일 client cache: 서버 응답에 Cache-Control: max-age=600. 앱 단에서도 10분 유지.
  • CDN: 지리적으로 가까운 서버에서 캐시 응답 (CloudFront/Cloudflare).
  • Timeout + retry: 외부 API 2초 timeout, 실패 시 1회만 retry, 그래도 실패면 fallback.
  • 관측: 각 지역/외부 API별 p95 latency, 에러율, 캐시 히트율 대시보드.

// CoupangParser.kt - timeout

// ParseProductUseCase.kt - cache + delegated pipeline
@Service
class ParseProductUseCase(private val pipeline: ParserPipeline) {
    @Cacheable(
        cacheNames = ["products"],
        key = "#url",
        unless = "#result instanceof T(...ParseResult$Failure)",
    )
    fun execute(url: String): ParseResult = pipeline.parseWithFallback(url)
}

// ParserPipeline.kt - fallback + 로깅
fun parseWithFallback(url: String): ParseResult {
    val primary = parserResolver.resolve(url)
    val primaryResult = primary.parse(url)
    if (primaryResult !is ParseResult.Failure || primary is FallbackProductParser) {
        return primaryResult
    }
    log.warn("primary parser {} failed: {}", primaryResult.parserUsed, primaryResult.reason)
    val fallback = parserResolver.fallbackParser.parse(url)
    return when (fallback) {
        is Success -> fallback.copy(fallbackUsed = true)
        is Partial -> fallback.copy(fallbackUsed = true)
        is Failure -> combineError(primaryResult, fallback)
    }
}
이미 이 프로젝트에 구현되어 있음 (BE5 Pipeline + BE3 Resolver + Phase 1 @Cacheable).
실제 구현을 이렇게 한 줄의 요약 아닌 코드로 보여주면 설득력 최고.

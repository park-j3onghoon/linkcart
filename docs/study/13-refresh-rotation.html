13. Refresh Token rotation

Access 15분 + Refresh 14일. 재사용 감지 시 family revoke.

이 챕터의 핵심 용어 — Refresh Token · Access Token · Rotation · JWT · Bearer

왜 Refresh Token이 필요한가

Access JWT가 15분 수명이면, 사용자는 15분마다 재로그인해야 하나? 그러면 UX 끔찍. Refresh Token이 해결:

  • 로그인 성공 시 Access (15분) + Refresh (14일) 동시 발급
  • Access 만료 임박 시 클라가 Refresh를 BE에 전달 → 새 Access + 새 Refresh 받음
  • 사용자는 14일 동안 재로그인 안 해도 됨

Rotation이 뭔가

Rotation = Refresh 때마다 Refresh token을 새로 발급하고 기존 건 폐기하는 전략. 반대는 "Refresh token은 그대로, Access만 재발급". 둘 중 무엇이 안전한가?

Rotation 없을 때의 공격 시나리오

Rotation 없으면 한 번 탈취된 Refresh는 14일간 유효

Rotation이 있을 때

Rotation이 "탈취가 어디선가 일어났다"는 신호로 작동

핵심 논리 — "Reuse Detection"

Refresh token은 딱 한 번 쓸 수 있다. 한 번 쓰면 revoke. 동일 token을 두 번째 쓰려는 시도 = 탈취 의심.

// RefreshTokensUsecase.kt (이 프로젝트)
@Transactional
fun execute(rawRefreshToken: String): IssueTokensUsecase.IssueResult {
    val now = clock.instant()
    val tokenHash = refreshTokenGenerator.hash(rawRefreshToken)
    val existing = refreshTokenRepository.findByTokenHash(tokenHash)
        ?: throw InvalidRefreshTokenException("Refresh token을 찾을 수 없습니다")

    if (existing.isExpiredAt(now)) {
        throw InvalidRefreshTokenException("Refresh token이 만료되었습니다")
    }

    if (!existing.isActive) {
        // ⬇ REUSE 감지: 이미 revoked된 token을 또 썼다
        refreshTokenRepository.revokeAllActiveForUser(existing.userId, now)  // 전체 revoke
        throw InvalidRefreshTokenException("Refresh token 재사용이 감지되었습니다")
    }

    val newIssue = issueTokensUsecase.execute(existing.userId)  // 새 Access + Refresh
    refreshTokenRepository.markRevoked(                          // 기존 revoke
        id = existing.id!!,
        revokedAt = now,
        replacedByTokenId = newIssue.refreshTokenId,              // rotation 체인 기록
    )
    return newIssue
}

Refresh Token 자체의 형태

Access는 JWT. Refresh는? 이 프로젝트는 opaque token (의미 없는 무작위 문자열).

결정 Refresh token 형태
후보
장점
단점
A. JWT (Access와 같은 서명)
통일성. 검증 단순.
JWT는 stateless가 장점인데 Refresh는 어차피 DB 조회 필요. 이점 사라짐. payload 노출.
B. Opaque (SecureRandom)
의미 없는 문자열 → 노출돼도 그 자체엔 정보 없음. DB 해시 저장으로 완전 state 제어.
JWT와 다른 검증 경로 구현 필요 (약간 복잡)
→ B 채택. Refresh는 애초에 stateful(DB에서 revoke 가능해야)이므로 JWT 이점 없음. opaque가 정직.

Opaque 토큰 생성

// SecureRandomRefreshTokenGenerator.kt
override fun generate(): String {
    val bytes = ByteArray(32)                   // 256-bit entropy
    random.nextBytes(bytes)                       // java.security.SecureRandom
    return encoder.encodeToString(bytes)          // URL-safe Base64
}

32 bytes = 256 bits = 2^256가지 조합. 브루트포스 불가능.

DB에 해시 저장 — "원본 탈취돼도 DB에서 복구 불가"

❌ 잘못된 저장
INSERT INTO refresh_tokens (token)
VALUES ('abc123xyz...');

// DB가 유출되면 모든 활성 토큰 원본 노출
// 공격자는 그걸로 각 유저의 Access 갱신 가능
✅ 해시 저장
INSERT INTO refresh_tokens (token_hash)
VALUES ('sha256(abc123xyz...) = ');

// DB 유출돼도 해시만 노출
// SHA-256 역산 불가 → 원본 복구 불가
// 공격자는 유출된 DB로 아무것도 못 함

해시 비교 흐름

  1. 클라가 Refresh "abc123xyz..."를 POST /auth/refresh로 전달
  2. 서버가 SHA-256 해시 → "5f4dcc3b..."
  3. DB에서 token_hash 컬럼으로 조회 → 있으면 그 row의 userId 획득
  4. 없으면 401
비밀번호 해시와 비슷하지만 다른 점 — 비밀번호는 bcrypt/argon2로 느린 해시. 이유: 사용자가 약한 비번을 선택하므로 무차별 공격 방어. Refresh token은 이미 256-bit 무작위라 브루트포스 불가. 빠른 SHA-256으로 충분.

DB 스키마 (V2 마이그레이션)

CREATE TABLE refresh_tokens (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash CHAR(64) NOT NULL UNIQUE,        -- SHA-256 hex 64자
    issued_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    revoked_at TIMESTAMP WITH TIME ZONE,            -- null = active
    replaced_by_token_id UUID REFERENCES refresh_tokens(id) ON DELETE SET NULL
);

-- 활성 token만 빠른 조회 (부분 인덱스)
CREATE INDEX idx_refresh_tokens_user_active
    ON refresh_tokens(user_id) WHERE revoked_at IS NULL;

replaced_by_token_id의 용도

rotation 체인을 기록한다: R1 → R2 → R3. 만약 R1 재사용 감지되면, 감사 로그에서 "R1이 R2에 의해 교체됐고 R2도 R3에 의해 교체됐다"는 체인을 추적 가능. 운영/보안 사건 조사에 유용.

시간 흐름 종합

정상 흐름: A1→A2→A3로 회전. R1 재사용 감지 시 전체 revoke.

엔드포인트 3종 정리

엔드포인트입력성공 응답실패
POST /auth/oauth/google{code, redirect_uri}200 + {access, refresh, user}401 OAuth 실패
POST /auth/refresh{refresh_token}200 + {new_access, new_refresh}401 만료/없음/reuse
POST /auth/logout{refresh_token}204 No Content(존재 안해도 204)
logout을 204로 통일한 이유 — 존재하지 않는 token으로 logout 요청해도 204 반환. 공격자가 "이 token이 유효했나" 탐지 못 함 (timing attack 방지).

정리

  • Access 15분 + Refresh 14일 하이브리드
  • Refresh는 rotation: 쓰면 즉시 revoke + 새 발급
  • Reuse 감지 (이미 revoke된 Refresh 재사용) → 해당 user의 전체 active 토큰 revoke (family revoke)
  • Refresh는 opaque (JWT 아님), DB엔 SHA-256 해시만 저장
  • replaced_by_token_id로 rotation 체인 추적
면접에서 — "왜 family revoke까지?" 질문이 자주 나온다. 답: "reuse는 어디선가 탈취가 있었다는 강한 신호. 그 시점부터 이 user의 모든 세션이 의심스럽다. 정상 사용자가 재로그인하는 불편 vs 공격 창 확장. 안전 쪽을 택한다."

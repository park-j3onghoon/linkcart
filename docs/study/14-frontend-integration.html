14. 프론트엔드 통합

BE OpenAPI → TS 타입 codegen → shared 패키지 → Web(Next.js) / Mobile(Expo)로 한 번에.

이 챕터는 — 이 프로젝트가 BE 단독이 아니라 글로벌 멀티플랫폼을 어떻게 구성하는지를 설명한다. 티니어 채용공고의 "글로벌 멀티 플랫폼 API 설계" 요구와 직결.

전체 흐름 — Spec 한 번, 두 플랫폼

한 DTO에서 시작해 두 플랫폼의 타입과 API 클라이언트가 자동 생성됨

왜 OpenAPI codegen을 먼저 붙이나

원문 (pr5.html): "백엔드 DTO와 프론트 타입을 사람이 각각 관리하면 snake_case/camelCase, nullable 여부 같은 계약이 쉽게 어긋난다. 그래서 스펙을 한 번만 만들고, 프론트는 그 산출물을 재사용한다."

# packages/shared/package.json
{
  "scripts": {
    "codegen": "npx openapi-typescript http://localhost:8080/openapi.json -o src/types/api.gen.ts"
  }
}
계약 정합성 에피소드 — ParseResponse OpenAPI 필드가 처음엔 camelCase imageUrl로 나왔다. 프론트는 snake_case image_url을 기대. 해결: BE의 @JsonNaming(SnakeCaseStrategy)로 실제 JSON + OpenAPI 모두 snake_case로 통일. "한 곳을 고쳐 두 곳이 자동으로 맞춰지는 것"이 스펙-우선 개발의 진짜 가치.

packages/shared — 공통 코드의 실체

packages/shared/
├── src/
│   ├── types/
│   │   ├── api.gen.ts       // 자동 생성, 손대지 않음
│   │   └── product.ts       // api.gen.ts 기반 도메인 타입 재수출
│   ├── api/
│   │   └── client.ts        // createApiClient (fetch + timeout + ApiResult)
│   └── validation/
│       └── url.ts           // 웹/앱 공통 URL 검증
└── package.json

ApiResult — Result 타입

export type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: ApiError }

export type ApiError = {
  kind: 'NETWORK' | 'PARSE_FAILED' | 'TIMEOUT' | 'UNKNOWN'
  message: string
}

Rust의 Result<T, E> 철학. "성공/실패"를 타입 시스템이 강제. FE 코드는 if (result.ok) { ... } else { showError(result.error) }로 분기하여 실수로 에러 처리를 빼먹지 않음.

BE의 ParseResult와 유사한 사상 — Kotlin의 sealed interface ParseResult { Success / Partial / Failure }와 같은 구조를 TypeScript의 discriminated union으로 구현. BE·FE 모두 "예외로 던지지 않고 타입으로 표현"하는 Railway-Oriented Programming 스타일.

layout.tsx vs page.tsx 구분

  • layout.tsx: 공통 html/body, 메타데이터, 폰트, 네비게이션 등 바깥 껍질
  • page.tsx: 실제 라우트 화면의 본문

커스텀 훅 — 책임 분리 모범 사례

"저장 실패 = 앱 실패"로 만들지 않기 — 원문 (pr5.html): "이 PR에서는 저장이 막혀도 현재 세션의 메모리 상태는 계속 유지된다." localStorage 쿼터 초과, 시크릿 모드 등으로 저장 실패해도 앱이 죽지 않음. 견고성 = graceful degradation의 실전 적용.

Expo + React Native — 웹을 모바일로

View/Text/Image — DOM이 아니다

React DOM (웹)
<div style={{ padding: 20 }}>
  <p>상품명</p>
  <img src="..." />
  <button onClick={handler}>추가</button>
</div>
React Native (앱)
<View style={{ padding: 20 }}>
  <Text>상품명</Text>
  <Image source={{ uri: "..." }} />
  <Pressable onPress={handler}>
    <Text>추가</Text>
  </Pressable>
</View>

React DOM은 브라우저 노드를 그리지만, React Native는 iOS/Android 네이티브 위젯 트리를 그린다. 개념은 비슷해도 컴포넌트 이름과 props가 다름.

AsyncStorage vs localStorage

Web — localStorage (동기)
// 즉시 반환
const saved = localStorage.getItem('products')
const data = JSON.parse(saved ?? '[]')
Mobile — AsyncStorage (Promise)
// 비동기
const saved = await AsyncStorage.getItem('products')
const data = JSON.parse(saved ?? '[]')

// → hydration 단계 자체가 비동기 상태 머신

훅 인터페이스는 useStorage로 추상화해 같게 유지 (phase1-refactoring-backlog의 BL-S2 항목). 웹은 createLocalStorageAdapter, 앱은 createAsyncStorageAdapter를 주입.

FlatList — 모바일 성능의 핵심

원문 (pr6.html): "모바일에서 목록이 길어지면 모든 카드를 한 번에 그리는 방식은 메모리와 스크롤 성능에 불리하다. FlatList는 화면에 필요한 아이템만 가상화해서 렌더링한다."

<FlatList
  data={products}
  keyExtractor={(item) => item.sourceUrl}
  renderItem={({ item }) => <ProductCard product={item} />}
  ListHeaderComponent={<UrlInput ... />}  {/* 스크롤 안에 헤더 포함 */}
/>
"boring and safe" 선택 — 원문: "App 전체를 ScrollView로 감싸지 않고, 헤더를 FlatList.ListHeaderComponent로 붙여서 리스트가 스크롤의 중심이 되도록 구성했다. 이게 모바일 성능 관점에서 더 boring하고 안전한 구조다." boring = 예측 가능, 안전 = 돌발 성능 이슈 없음.

shared 재사용의 실제 효과

공유되는 것의미
API 타입 (api.gen.ts)BE snake_case 계약이 웹·앱에 동일 반영
createApiClientfetch/timeout/에러 매핑 로직 한 번 작성
validateUrlURL 검증 로직 중복 제거 (정규식 + URL 파싱)
ApiResult/ApiError 타입에러 처리 패턴 통일

원문 (pr6.html): "핵심은 UI를 새로 짜는 것이 아니라, @linkcart/shared의 API 클라이언트와 URL 검증을 그대로 재사용하고, 저장소만 AsyncStorage로 바꿔 모바일 문법에 맞게 감싼다는 점이다."

원문 (pr6.html): "모바일 테스트는 브라우저 DOM이 아니라 네이티브 컴포넌트 트리를 검사한다는 점만 다르고, '입력 → 상태 변화 → 화면 결과'를 계약으로 고정한다는 원리는 웹과 같다."

정리

  • BE OpenAPI (/openapi.json) → TypeScript 타입 자동 생성
  • shared 패키지에 타입 + API 클라이언트 + 검증 로직 한 번만 작성
  • 웹(Next.js) + 모바일(Expo)이 shared를 임포트해 재사용
  • 저장소(localStorage/AsyncStorage)만 플랫폼별로 어댑터
  • 컴포넌트/렌더링(div/Text, FlatList 등)만 플랫폼 전용
  • 테스트는 도구만 다르고 "입력→상태→화면" 원칙 동일
티니어 면접 포인트 — 이 구조가 "글로벌 멀티 플랫폼 API 설계"의 실전 답안. "shared에 API 계약과 검증을 두고 플랫폼별로 렌더만 분기" 1문장으로 정리 가능.

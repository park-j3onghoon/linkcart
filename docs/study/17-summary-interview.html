티니어 채용공고 요구사항 ↔ 프로젝트 기여

각 요구사항마다 이 프로젝트의 대응 지점

면접에서 반드시 준비할 6가지 이야기

① "왜 Kotlin/Spring으로 했나요?"

답 — "Python/Django가 주력이지만 티니어 기술스택 경험이 필요하다고 판단했다. 처음부터 실무 수준 아키텍처(클린 4-layer + JPA + Security)를 경험하면서 Kotlin 문법도 익혔다. 단순 튜토리얼 따라하기가 아니라 실제 프로덕션 구성 — PostgreSQL + Flyway + OAuth + JWT rotation + SSRF 방어 — 를 갖추려 했다."

② "클린 아키텍처를 이 규모에 쓴 이유는?" (과설계 질문)

답 — "정직히 말해 이 규모에는 과할 수 있다. 다만 (1) Kotlin/Spring의 DI·포트 패턴을 학습하는 목적 (2) 외부 API 3종 + DB + OAuth 등 외부 의존성 분리 이득 실재 (3) 면접에서 '헥사고날/클린 구조를 써봤다' 언급 가능한 실물 생산. 실무에서는 도메인 복잡도를 보고 결정한다는 건 알고 있다."

③ "JWT vs 세션 왜 JWT?"

답 — "웹+모바일 2종 클라이언트. 모바일에서 쿠키 관리가 번거로워 Bearer 헤더 기반 JWT로 통일. 다만 Access-only JWT는 revoke가 약해 Refresh Token rotation + DB 저장으로 보완. 웹 단독이면 Spring Session + Redis가 더 단순했을 것. 선택은 모바일 존재라는 요건에 의한 것."

④ "Refresh rotation에서 family revoke까지 하는 이유?"

답 — "reuse는 '어디선가 탈취가 일어났다'는 강한 신호. 정상 사용자가 rotate 후, 그 구식 token을 또 쓰는 건 공격자일 가능성이 높다. 정상 사용자에게 재로그인을 요구하는 불편 vs 공격 창 확장. 이 프로젝트는 안전 쪽을 택했다."

⑤ "SSRF 방어는 완벽한가?"

답 — "완벽하지 않다. 7개 공격 벡터(scheme, loopback, any-local, link-local, 사설 IP, URL-encoded, 짧은 IP, SVG XSS)는 막았지만 DNS rebinding, 리다이렉트 체이스, 이미지 magic byte 검증은 명시적으로 NOT in scope로 남겼다. 방어의 한계를 문서화하는 것이 '완벽한 척 하다 터지는' 것보다 중요하다고 생각했다."

⑥ "트러블이 생겼을 때 어떻게 해결했나?"

답 — 구체 예: "Testcontainers가 Rancher Desktop 환경에서 Docker socket을 찾지 못해 통합 테스트가 실패했다. 원인을 docker context 경로에서 찾아 ~/.testcontainers.properties로 대체 socket 지정 시도했고, 해결 안 되어 일단 H2 in-memory로 fallback + Integration test @Disabled로 문서화한 뒤 다음 세션 과제로 이관했다. 실행을 막지 않고 진행하되 기술부채를 명시적으로 남긴 게 포인트."

예상되는 약점 질문 + 답변

"대규모 트래픽 다뤄본 경험 있으세요?"
"linkcart는 혼자 만든 사이드 프로젝트라 실제 트래픽은 없다. 다만 캐시/타임아웃/폴백/부분 인덱스 같은 대용량 대비 기법은 적용했다. Django 경력 때는 OO 수준 트래픽을 다뤘고 N+1 수정, Redis 캐시 레이어 추가 같은 실전 경험이 있다. [실제 경험 구체적으로]"
"AWS 운영 경험이 없는데요?"
"사실대로 말씀드리면 AWS는 관찰만 해봤다. linkcart는 Docker Compose 로컬 환경이고 클라우드 배포까지는 못 갔다. 다만 (1) AWS IAM metadata 주소(169.254.169.254)를 SSRF에서 방어할 만큼 인프라 보안 맥락은 이해한다 (2) 오기 전까지 학습할 계획 (3) Python/Django 때 ECS 배포 파이프라인은 팀에서 돌아가는 걸 곁에서 보았다. 입사 후 빠르게 따라갈 자신 있다."
"Kotlin 경력이 없는데 실무에서 생산성 보장되나요?"
"솔직히 Java/Kotlin은 이 프로젝트가 실질적 첫 경험이다. 다만 (1) 5년 전 Java 경력이 JVM 생태계 기반이 됨 (2) 이 프로젝트에서 Spring Security, JPA, Security Filter 같은 깊이 있는 영역까지 들어가 봤다 (3) Python/Django 5년 숙련이 '문제를 빨리 파악하고 해결하는 습관'을 만들어 놨다. 문법 학습 곡선은 2~4주로 극복 가능하다고 본다."

마지막

이 프로젝트의 본질 — "Kotlin/Spring을 얼마나 잘하나"가 아니다. 기간 대비 학습량이 적어서 시니어 Kotlin 개발자와 경쟁할 수 없다. 경쟁 포인트는 "새 기술을 만났을 때 어떻게 접근하는가" — 트레이드오프를 문서화하고, 리뷰 피드백을 리팩토링으로 흡수하고, 한계를 정직히 남겨두는 일하는 방식이다. 티니어가 채용공고에서 말한 "본질과 핵심에 집중, 빠른 실험 빠른 실패"와 정확히 일치하는 서사로 말할 것.

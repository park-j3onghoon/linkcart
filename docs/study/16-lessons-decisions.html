16. 리뷰에서 배운 것 + 결정 기록

코드 리뷰 피드백 → 실제 수정 → 왜 그렇게 고쳤는가. 그리고 Plan Review에서 내린 결정들.

이 챕터의 의도 — "완벽한 설계를 처음부터 했다"가 아니라 "리뷰에서 배워 반영했다"는 서사는 시니어 레벨의 증거. 구체적 결정과 이유를 기록한다.

PR-1 리뷰에서 배운 4가지 원칙 (pr1.html 기준)

① 금액은 항상 Long

Before
data class Money(
    val amount: Int,     // ❌ 21억 초과 불가
    val currency: String,
)
After
data class Money(
    val amount: Long,    // ✅ 9 * 10^18
    val currency: String = "KRW",
)

원문 (pr1.html): "Python은 int가 크기 제한이 없어서(arbitrary precision) 이 문제를 겪지 않지만, JVM 언어에서는 Int(32비트)와 Long(64비트)이 다릅니다. 금액에는 항상 Long을 쓰는 것이 안전합니다."

왜 Double 아닌 Long? IEEE 754 부동소수점은 0.1 + 0.2 ≠ 0.3. 금액 처리에서 이 오차는 결제 불일치, 정산 오류로 직결. BigDecimal도 가능하나 Long이 단순하고 원화처럼 원 단위 정수 통화에 충분.

② 공통 상태가 없으면 sealed interface, 있으면 sealed class

Before
sealed class ParseResult {
    // 공통 필드 없는데 class?
    data class Success(val product: Product) : ParseResult()
    data class Failure(val reason: String) : ParseResult()
}
After
sealed interface ParseResult {
    data class Success(val product: Product) : ParseResult
    data class Partial(val fields: Map<String, Any>) : ParseResult
    data class Failure(val reason: String) : ParseResult
}

원문: "공통 상태(필드)가 필요하면 sealed class, 없으면 sealed interface. ParseResult는 공통 필드가 없으므로 interface가 맞습니다."

③ 인프라 설정은 infrastructure/config/에

CORS가 presentation이 아닌 이유 — 원문: "CORS는 '웹 서버의 인프라 수준 설정'입니다. 비즈니스 로직과 무관하고, 어떤 origin을 허용할지는 배포 환경에 따라 달라지는 인프라 설정입니다. Django로 비유하면: views.py에 CORS 설정을 넣지 않고, settings.py에 넣는 것과 같은 논리입니다."

그래서 WebConfig.kt는 infrastructure/config/에 위치.

④ 네이밍 전략은 글로벌 설정으로

# application.yml — 모든 DTO에 자동 적용
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE

각 DTO마다 @JsonProperty("image_url") 붙이지 않고 전역 설정. "글로벌 서비스 관점에서 API 응답 필드 네이밍을 한 곳에서 통제".

외부 API 운영 원칙 — pr3.html 인용

"실패 결과는 캐시하지 않는다"
원문: "실패 결과는 캐시하지 않는 것도 중요하다. 외부 API가 잠깐 흔들렸을 때 실패를 오래 보관하면, 실제 복구 뒤에도 계속 실패를 재사용하게 되기 때문이다." 
// ParseProductUseCase.kt의 @Cacheable
@Cacheable(
    cacheNames = ["products"],
    key = "#url",
    unless = "#result instanceof T(com.linkcart.domain.model.ParseResult$Failure)",  // ← 실패는 미캐시
)
fun execute(url: String): ParseResult = ...

unless로 Failure 제외. 5분 후에라도 외부 API 복구되면 즉시 성공 반영.

URL 검증의 3레이어 책임 분리 (plan.md 인용)

한 URL에 대한 검증을 어느 레이어에서 해야 하나? 이 프로젝트는 3단계로 나눴다:

레이어책임예시
PresentationURL 형식 검증@Pattern("^https?://.+") / @field:NotBlank / ParseRequest DTO
Application지원 대상 여부 확인ParserResolver.resolve(url) → DedicatedParser 있나 없나
Infrastructure기술적 가능성SafeUrlChecker (SSRF) / 실제 HTTP 접근 / API 응답 파싱
왜 한 곳에서 안 하나 — 형식이 맞는다고 안전한 URL은 아님 (SSRF). 지원 몰이 맞다고 파싱 가능한 건 아님 (API 장애). 각 레이어의 관심사가 다름. 한 곳에서 다 하려 하면 결국 그 한 곳이 god-object가 됨.

보안 리뷰에서 반영한 CRITICAL 3건 (P2-2)

  1. SecurityConfig에 .cors() 누락 → Spring Security 필터 체인이 CORS 무시. 추가.
  2. Google OAuth 원본 에러 메시지가 응답에 노출 가능 → 로깅만 하고 클라이언트엔 추상 메시지.
  3. JWT secret 길이 검증 lazy init → eager로 변경. fail-fast.

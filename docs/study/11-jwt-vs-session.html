11. JWT vs 세션 — 왜 이 프로젝트는 JWT를 골랐나

세션이 더 쉬울 수도 있다. 그런데 왜?

이 챕터의 핵심 용어 — JWT · Bearer · CSRF · XSS · CORS · SOP

기본 차이

세션 방식
// 로그인 성공 시
session_id = random()
store[session_id] = { userId: 42, role: "user" }  // 서버 저장
setCookie("SID", session_id, httpOnly=true)

// 이후 요청마다
sid = cookie["SID"]
user = store[sid]  // 서버가 매번 조회
JWT 방식
// 로그인 성공 시
token = JWT.sign({ sub: 42, exp: now+900 }, SECRET)
// 서버는 아무것도 저장 안 함

// 이후 요청마다
payload = JWT.verify(header["Authorization"], SECRET)
// 서명만 검증하면 user 정보 확보

두 방식의 근본적 차이 — 상태의 위치

세션은 "서버가 상태 소유", JWT는 "클라이언트가 상태 소유"

트레이드오프 비교표

linkcart는 왜 JWT인가 — 결정적 요소

linkcart는 웹(Next.js) + 모바일(Expo React Native) 2종 클라이언트
이게 전부다. 모바일이 있으면 세션 쿠키 기반은 관리 불편.

모바일 관점에서 쿠키의 어려움

  • 앱은 네이티브 HTTP 클라이언트 (fetch, axios RN). 쿠키 자동 관리 미미
  • 쿠키 저장 위치: 앱의 CookieManager, SecureStorage 중 어디? 플랫폼별 차이
  • 앱 재시작 후 쿠키 유지? 안드로이드/iOS 동작 다름
  • Bearer 헤더: Authorization: Bearer XXX → 단순하고 명시적. 모든 HTTP 클라이언트가 동일하게 지원

웹 관점

웹만 있다면 세션이 더 단순하고 안전할 수 있다. Django 개발자 배경이면 자연스럽게 세션. 하지만 두 클라이언트 통합 인증 전략을 위해 JWT로 통일.

XSS/CSRF 관점 비교

CSRF (Cross-Site Request Forgery)

CSRF 시나리오 — 사용자가 A은행에 로그인 중. 악성 사이트 방문. 악성 사이트에 <img src="https://a-bank.com/transfer?to=attacker&amount=100"> 있음. 브라우저가 A은행 쿠키를 자동 첨부해 요청 → 송금 일어남.
  • 세션 + 쿠키: 브라우저가 쿠키 자동 전송하므로 취약. CSRF 토큰 방어 필수.
  • JWT + Bearer 헤더: 브라우저가 Authorization 헤더 자동으로 보내지 않음. CSRF 근본 회피.

XSS (Cross-Site Scripting)

XSS 시나리오 — 댓글에 <script>fetch('/api/user', { credentials: 'include' })</script>가 이스케이프 없이 렌더됨. 피해자 브라우저가 그 JS 실행. 로그인 정보 유출.
  • 세션 + HttpOnly 쿠키: JS가 쿠키에 못 접근. 세션 ID 탈취 불가. 안전.
  • JWT + localStorage: JS가 localStorage 읽음. XSS 있으면 JWT 노출. 위험.
  • JWT + HttpOnly 쿠키: JS 못 읽음. 안전. 하지만 CSRF 다시 고민해야.
현재 linkcart의 입장 — 모바일 앱은 localStorage 개념 자체가 없고 SecureStorage에 저장하면 안전. 웹은 일단 memory 저장 + refresh로 실용화 (초심자 수준에서는 충분). XSS 자체 방어는 프론트의 역할.

Django 세션을 쓰던 사람의 "어색함" 짚기

  • Django에서 request.user는 로그인 상태면 User 객체, 아니면 AnonymousUser. Spring + JWT에선 @AuthenticationPrincipal이 null이거나 userId. User 전체를 매 요청마다 DB에서 재조회하지 않음 (성능).
  • Django는 django.contrib.auth.middleware가 쿠키→User 자동 변환. Spring은 JwtAuthenticationFilter를 직접 만들거나 Spring Security OAuth2 Resource Server를 쓴다.
  • 로그아웃: Django는 session 삭제 한 줄. Spring JWT에선 Refresh token을 DB에서 revoke (Access는 자연 만료 대기).

언제 세션이 더 맞는가 — 솔직히

이 프로젝트가 웹 한 플랫폼만이었다면:

  • Spring Session + Redis가 더 단순
  • Django 경험 살리기 좋음
  • 즉시 revoke, CSRF 토큰만 처리하면 보안 확실
  • JWT rotation 복잡도 불필요

그래서 현실에서 단일 웹 앱에는 여전히 세션이 많다. JWT는 흔한 기본값이지만 "무조건 옳음"은 아님.

정리

면접에서 이야기할 때 — "JWT를 선택한 이유는 모바일 앱이 있기 때문"이라고 시작하면 설득력 좋다. "그냥 JWT가 요즘 대세라서"는 얄팍한 답. 이 프로젝트는 모바일+웹 둘 다라 두 클라이언트 공통 전략이 필요했고, Bearer 헤더가 그 해답이었다는 서사가 구체적이다.

12. OAuth + Access JWT

Google 로그인은 어떻게 동작하고, JWT는 어떻게 서명되는가.

이 챕터의 핵심 용어 — JWT · HS256 · RS256 · Bearer · Access Token · Refresh Token

OAuth — 왜 이런 복잡한 흐름이 생겼나

서비스A(linkcart)가 사용자의 Google 정보(이메일, 이름)를 얻고 싶다. 가장 단순한 방법:

최악의 방법 (2000년대 초) — "Google 비밀번호를 linkcart에 입력하세요" → linkcart가 Google 서버에 그 계정으로 로그인 → 정보 긁어옴.
문제: linkcart가 사용자 Google 비번을 저장함. 사용자는 linkcart를 신뢰해야 함. 유출 시 Google 계정 전체가 털림.

OAuth 2.0은 이 문제를 해결한다:

  • 사용자는 Google 비번을 linkcart에 절대 주지 않는다
  • 사용자는 Google에만 로그인한다
  • Google이 "이 사람이 linkcart에게 이메일/이름 제공을 허락함"을 증명하는 짧은 수명의 토큰을 발급
  • linkcart는 그 토큰으로만 Google에 사용자 정보 요청

Authorization Code Flow — 이 프로젝트가 쓰는 방식

auth code 6. POST /auth/oauth/google {code} 7. code + client_secret 전달 8. id_token (JWT) 반환 9. ID Token 서명 검증 10. sub/email 추출 11. User 찾거나 생성 12. linkcart JWT (access+refresh) 반환 13. 로그인 완료
Google이 보증한 "ID Token"을 linkcart JWT로 교환하는 흐름

ID Token 검증이 왜 필요한가

누군가가 가짜 id_token을 "내가 Google에서 받은 거다"며 linkcart에 보낼 수 있다. 그래서 linkcart는 반드시 Google이 정말 서명했는지 검증한다.

Google의 ID Token은 JWT이고, RSA 서명이다. Google이 공개키를 jwks URL에 공개하고, 서비스들은 그 공개키로 서명 검증.

// GoogleOAuthAdapter.kt (이 프로젝트)
internal val idTokenVerifier: GoogleIdTokenVerifier = GoogleIdTokenVerifier.Builder(
    NetHttpTransport(),
    GsonFactory.getDefaultInstance(),
).setAudience(Collections.singletonList(clientId)).build()  // aud가 우리 clientId인지 체크

val idToken = idTokenVerifier.verify(idTokenString)
    ?: throw GoogleOAuthException("Google 인증에 실패했습니다")
// verify가 내부에서: 서명 체크 + exp 체크 + iss(=accounts.google.com) 체크 + aud 체크
aud(audience) 체크가 핵심 — 만약 이걸 안 하면, 다른 Google 앱(예: "악성앱A")을 위한 id_token을 linkcart에 보내도 통과된다. aud가 내 clientId인지 확인해야 진짜 나에게 온 토큰임이 보장.

linkcart가 발행하는 JWT

Google 검증 통과 후 linkcart는 자신의 Access JWT를 만든다. Google ID Token을 그대로 쓰면 될까? 안 된다:

  • Google 토큰은 수명이 짧음 (1시간). Refresh하려면 Google에 매번 요청 (부담)
  • Google 토큰의 sub은 Google 사용자 id. linkcart는 자기 DB의 user.id로 식별하고 싶음
  • 로그아웃, 권한 변경 등을 linkcart가 제어해야 함

JWT 구조 — 3 part

Header와 Payload는 Base64 디코딩만 하면 읽힘 — 암호화 아님. Signature만 위조 방지.

이 프로젝트의 JWT payload

{
  "sub": "42",                         // = linkcart user.id (내부 식별자)
  "iss": "linkcart",                   // issuer
  "aud": "linkcart-api",               // audience
  "iat": 1712937600,                   // issued at (epoch seconds)
  "exp": 1712938500                    // expires at = iat + 900 (15분)
}
payload에 PII 금지 — email, name 같은 개인정보를 JWT에 넣으면 로그/CDN 캐시/통신 내역에 흘러나감. JWT는 "이 사람은 userId 42다"만 말하고, 자세한 정보는 DB 조회로. 이 프로젝트의 JWT는 sub만 본다.

HMAC-SHA256 서명 — 어떻게 위조 방지?

Signature = HMAC-SHA256("<header>.<payload>", secret)

  • 서버만 secret을 안다 (환경변수)
  • 누군가 payload의 "sub"을 42→999로 바꾸면? Signature가 안 맞음
  • 클라이언트는 payload는 읽을 수 있지만 (base64 decode) 고치진 못함 (secret 없으니 재서명 불가)
  • secret 키 길이 ≥ 32 bytes (HMAC-SHA256 권장)

이 프로젝트의 발행 코드

// JwtAccessTokenIssuer.kt
override fun issue(userId: Long): AccessToken {
    val issuedAt = clock.instant()
    val expiresAt = issuedAt.plus(Duration.ofSeconds(ttlSeconds))  // 900s

    val token = Jwts.builder()
        .subject(userId.toString())
        .issuer(issuer)
        .audience().add(audience).and()
        .issuedAt(Date.from(issuedAt))
        .expiration(Date.from(expiresAt))
        .signWith(signingKey, Jwts.SIG.HS256)
        .compact()

    return AccessToken(token = token, expiresAt = expiresAt)
}

클라이언트가 JWT를 보낼 때 — Bearer 헤더

GET /api/v1/auth/me HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIi...

Authorization 헤더, Bearer prefix. 이게 업계 표준 (RFC 6750).

서버 측 검증 — JwtAuthenticationFilter

// JwtAuthenticationFilter.kt
override fun doFilterInternal(request, response, chain) {
    val token = extractBearerToken(request)  // "Bearer XXX" → "XXX"
    if (token != null) {
        try {
            val userId = accessTokenIssuer.verify(token)
            val authentication = UsernamePasswordAuthenticationToken(userId, null, emptyList())
            SecurityContextHolder.getContext().authentication = authentication
        } catch (_: InvalidAccessTokenException) {
            SecurityContextHolder.clearContext()  // 401로 이어짐
        }
    }
    chain.doFilter(request, response)
}

Controller에서는 @AuthenticationPrincipal userId: Long으로 주입받아 사용.

Spring Security FilterChain — 전체 그림

필터 체인: Spring Security가 제공하는 pipeline에 내 필터를 끼움

SecurityConfig 핵심 설정

@Bean
fun filterChain(http: HttpSecurity, ...) = http
    .csrf { it.disable() }                        // JWT는 쿠키 기반 아님 → CSRF 불필요
    .cors { }                                     // CORS는 WebConfig와 연동
    .sessionManagement { it.sessionCreationPolicy(STATELESS) }  // 세션 사용 안 함
    .authorizeHttpRequests {
        it.requestMatchers(
            "/api/v1/auth/oauth/**",                 // 로그인 전
            "/api/v1/products/parse", "/api/v1/images/proxy",  // Phase 1 공개 API
            "/openapi.json", "/docs/**",
        ).permitAll()
            .anyRequest().authenticated()          // 나머지는 JWT 필요
    }
    .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter::class.java)
    .exceptionHandling { it.authenticationEntryPoint(jsonAuthenticationEntryPoint) }
    .build()

정리

  • Google OAuth Authorization Code flow 선택 (FE가 code 전달 → BE가 토큰 교환)
  • ID Token은 Google 서명 검증 (google-api-client, aud=clientId 매칭)
  • linkcart 자체 Access JWT (HS256, 15분, sub=userId만)
  • Spring Security는 STATELESS + JwtAuthenticationFilter 추가
  • 401 응답은 JSON 포맷 통일 (JsonAuthenticationEntryPoint)
  • JWT payload에 PII 넣지 않음 (로그 유출 방어)

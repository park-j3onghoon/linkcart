10. SSRF 방어

Server-Side Request Forgery. 서버가 외부 URL을 fetch해야 하는 모든 서비스가 겪는 공격.

이 챕터의 핵심 용어 — SSRF · 핫링크 · OG parser · SafeUrlChecker · TOCTOU · DNS rebinding

SSRF가 뭔가

linkcart는 사용자가 준 URL을 서버가 fetch해서 파싱한다. 만약 사용자가 악의로 http://127.0.0.1/admin 같은 내부망 주소를 주면?

SSRF는 "서버를 프록시로 악용"하는 공격

공격 벡터와 방어 — 7단계

이 프로젝트는 단계적으로 방어를 강화했다. 각 벡터와 방어:

1. 비-HTTP 프로토콜 (javascript:, file:)

// SafeUrlChecker.kt
if (uri.scheme !in setOf("http", "https")) return false

allow-list 방식. javascript:, file:, ftp: 등 모두 차단.

2. Loopback (127.0.0.1, ::1)

val address = InetAddress.getByName(host)
return !address.isLoopbackAddress

IPv4/IPv6 모두 isLoopbackAddress로 통합 검출.

3. Any-local (0.0.0.0)

return !address.isAnyLocalAddress

0.0.0.0은 "모든 로컬 인터페이스". loopback과 별개 체크.

4. Link-local (169.254.x.x)

AWS/GCP의 metadata endpoint가 169.254.169.254. IAM 역할 자격증명, 인스턴스 메타 등 노출. 필수 차단.

return !address.isLinkLocalAddress

5. 사설 IP (10.x.x.x, 172.16-31.x.x, 192.168.x.x)

return !address.isSiteLocalAddress

회사 내부망 보호.

Java InetAddress API의 함정 — isSiteLocalAddress는 RFC 1918 기반이지만 완전하지 않다. 예를 들어 IPv4-mapped IPv6 (::ffff:127.0.0.1)이 loopback으로 인식되는지 등은 JDK 구현 의존. 이 프로젝트는 BE2에서 IP 주소 직접 사용으로 DNS 회피 테스트로 검증.

6. URL-encoded bypass

공격자가 http://%31%32%37%2e%30%2e%30%2e%31/ 보내면? URL decode 시 http://127.0.0.1/.

if (host.contains('%')) return false  // defense-in-depth
"defense-in-depth" — Java URI class가 대부분의 encoded host를 null로 처리하긴 한다. 하지만 JDK 버전/엣지 케이스를 100% 신뢰하지 말고 이중 방어. 실패해도 안전 쪽.

7. 짧은 IP 표기 (decimal, hex, octal)

표기실제
http://2130706433127.0.0.1 (32-bit decimal)
http://0x7f000001127.0.0.1 (hex)
http://0177.0.0.1127.0.0.1 (octal dotted)

InetAddress.getByName이 이들을 정상 IP로 파싱해준다. 그래서 isLoopbackAddress 체크를 통과할 수도. 예방 차원에서 표기 자체 거부:

private fun isSuspiciousNumericHost(host: String): Boolean {
    if (host.all { it.isDigit() }) return true         // decimal
    if (host.startsWith("0x", ignoreCase = true)) return true  // hex
    if (host.matches(Regex("^0\\d+(?:\\.\\d+){3}$"))) return true   // octal
    return false
}

최종 SafeUrlChecker 전체

@Component
class SafeUrlChecker {
    fun isSafe(url: String): Boolean {
        val uri = runCatching { URI(url) }.getOrNull() ?: return false
        if (uri.scheme !in ALLOWED_SCHEMES) return false

        val host = uri.host ?: return false

        if (host.contains('%')) return false              // URL-encoded
        if (isSuspiciousNumericHost(host)) return false  // 짧은 IP

        val address = runCatching { InetAddress.getByName(host) }.getOrNull() ?: return false
        return !address.isAnyLocalAddress &&
            !address.isLoopbackAddress &&
            !address.isLinkLocalAddress &&
            !address.isSiteLocalAddress
    }

    companion object {
        private val ALLOWED_SCHEMES = setOf("http", "https")
        // NOT defended: DNS rebinding (TOCTOU). 별도 대응 필요.
    }
}

이미지 프록시의 추가 방어 — SVG 차단

linkcart는 외부 이미지를 /api/v1/images/proxy?url=...로 프록시한다. 그런데 SVG 파일은 내부에 <script>를 가질 수 있다. SVG가 같은 오리진으로 서빙되면 XSS.

Before: deny-list
if (contentType?.type != "image") {
    throw BAD_GATEWAY
}
// image/svg+xml은 "image"라 통과 → XSS 위험
After: allow-list
if (contentType.subtype !in ALLOWED_IMAGE_SUBTYPES) {
    throw BAD_GATEWAY
}

companion object {
    private val ALLOWED_IMAGE_SUBTYPES = setOf(
        "png", "jpeg", "gif", "webp",
    )
}
allow-list vs deny-list — 보안 원칙: "모르는 건 막기". allow-list로 명시된 safe만 허용. 미래에 새 포맷(avif, heic)이 나와도 명시 전까지 자동 거부 → 안전 기본값.

방어하지 않는 것 — 정직한 경계

이 프로젝트가 방어하지 않는 것 (별도 PR 예정)
  • DNS rebinding (TOCTOU): 호스트 해석 시점과 실제 HTTP 요청 시점 사이에 DNS 응답이 바뀌는 공격. 방어 복잡 (실제 peer IP 재검증 등).
  • 리다이렉트 체이스: 공격자가 공개 URL을 주지만 그 URL이 302로 내부망 리디렉션. 방어는 "최종 URL도 SafeUrlChecker 통과 확인".
  • Content magic byte 검증: Content-Type만 신뢰 대신 파일 헤더(예: PNG 매직 89 50 4E 47) 직접 검사.
SafeUrlChecker companion에 주석으로 명시. "이게 한계"라고 문서화된 방어는 "완벽한 척 하다 터지는" 것보다 안전.

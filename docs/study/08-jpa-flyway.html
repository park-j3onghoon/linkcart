Django는 "Model = 도메인 = 테이블 = 마이그레이션 원천"이 한 몸. 이 프로젝트는 일부러 분리했다:

  • 도메인 User (domain/entity) — 프레임워크 독립. Jackson/JPA도 이상적으로는 몰라야.
  • UserEntity (infrastructure/adapter/persistence) — JPA 어노테이션 있음. DB 모양.
  • UserRepository 포트 (domain/port) — UseCase가 의존하는 계약.
  • UserRepositoryAdapter (infrastructure) — 포트 구현, Entity ↔ 도메인 변환.
왜 이렇게 번거롭게? Django 접근은 편하지만 도메인이 ORM에 묶인다. 이 프로젝트는 클린 아키텍처 학습 목적 + 포트폴리오 + 미래 DB 교체 가능성 어필. 실무에선 도메인 복잡도가 낮으면 Django 스타일이 더 합리적인 경우도 많다.

Spring Data JPA Repository — 쿼리 자동 생성

가장 놀라운 기능. 메서드 이름만 쓰면 구현이 자동 생성된다:

interface UserJpaRepository : JpaRepository<UserEntity, Long> {
    // 이름이 곧 쿼리 정의
    fun findByProviderAndProviderUserId(
        provider: AuthProvider,
        providerUserId: String,
    ): UserEntity?

    fun existsByUserIdAndSourceUrl(userId: Long, sourceUrl: String): Boolean

    fun findAllByUserIdOrderByCreatedAtDesc(userId: Long): List<UserProductEntity>
}

findByProviderAndProviderUserId는 "provider = ? AND providerUserId = ?" WHERE절 자동. findAllByUserIdOrderByCreatedAtDesc는 ORDER BY. 복잡한 쿼리는 @Query("JPQL...")로 직접.

복잡한 쿼리 — @Query + @Modifying

이 프로젝트에서 RefreshToken의 family revoke:

interface RefreshTokenJpaRepository : JpaRepository<RefreshTokenEntity, UUID> {
    @Modifying
    @Query(
        "UPDATE RefreshTokenEntity r " +
        "SET r.revokedAt = :revokedAt " +
        "WHERE r.userId = :userId AND r.revokedAt IS NULL",
    )
    fun revokeAllActiveForUser(
        @Param("userId") userId: Long,
        @Param("revokedAt") revokedAt: Instant,
    ): Int
}
JPQL vs native SQL — @Query는 기본이 JPQL(Java Persistence Query Language)이다. 테이블 이름이 아닌 Entity 클래스 이름을 쓴다 (RefreshTokenEntity). DB 이식성이 좋지만 Postgres 전용 기능(CTE, JSONB 등)은 못 씀. 그럴 땐 nativeQuery = true로 native SQL 사용.

이 프로젝트의 V1__create_users.sql

-- backend/src/main/resources/db/migration/V1__create_users.sql

-- updated_at 자동 갱신 트리거 (raw SQL로 UPDATE해도 갱신됨)
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- SQL 표준 (BIGSERIAL보다 권장)
    provider VARCHAR(32) NOT NULL,
    provider_user_id VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    display_name VARCHAR(100),
    avatar_url VARCHAR(500),
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_users_provider_user UNIQUE (provider, provider_user_id)
);

CREATE TRIGGER trg_users_updated_at
BEFORE UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
IDENTITY vs SERIAL — BIGSERIAL은 Postgres 전용 단축. BIGINT GENERATED ALWAYS AS IDENTITY는 SQL 표준 + 수동 id 주입 막아줌(OVERRIDING SYSTEM VALUE 명시 필요). 신규 프로젝트는 IDENTITY 권장.

중요한 설정 2가지

1. open-in-view: false

Spring Boot 기본값은 true. Controller가 응답 쓸 때까지 영속 컨텍스트(세션)가 열려 있어 lazy loading이 자동. 편하지만:

  • DB 커넥션을 view 렌더링 내내 잡고 있음 → 커넥션 풀 고갈 위험
  • N+1 쿼리가 조용히 숨어 발생
  • Controller가 lazy loading에 암묵 의존

이 프로젝트는 open-in-view: false. Service/UseCase가 필요한 데이터를 명시적으로 fetch해야 함. 약간 번거롭지만 문제 조기 노출.

2. ddl-auto: validate

Hibernate가 앱 시작 시 Entity 매핑과 DB 스키마 일치 검증만 한다. 차이 있으면 부팅 실패 → Flyway와 Entity가 어긋난 상태로 배포되는 사고 방지.

Testcontainers — 테스트에서 진짜 DB 쓰기

단위 테스트는 mock으로 충분하지만, Repository는 실제 DB에 붙어봐야 JPQL/쿼리/제약조건이 맞는지 검증된다. Docker 컨테이너로 Postgres 16 띄워 테스트:

심화 Q&A — 자주 헷갈리는 지점

Q. JPA 어노테이션 전체 정리

Hibernate(JPA 구현체)가 "객체 ↔ DB 테이블" 매핑할 때 사용하는 메타데이터. 이 프로젝트 UserEntity.kt에 실제 사용된 것들:

@Entity                              // "이 클래스는 DB 테이블이다"
@Table(name = "users")               // 테이블 이름 (없으면 클래스명 소문자)
class UserEntity(
    @Id                              // Primary Key
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // auto-increment
    val id: Long? = null,

    @Column(nullable = false, length = 32)
    @Enumerated(EnumType.STRING)     // enum을 문자열로 저장 (ORDINAL은 숫자)
    val provider: AuthProvider,

    @Column(name = "provider_user_id", nullable = false, length = 255)
    val providerUserId: String,   // 컬럼명 스네이크케이스 매핑

    @Column(name = "created_at", nullable = false, insertable = false, updatable = false)
    val createdAt: Instant? = null,  // DB가 DEFAULT로 세팅 (insert/update 무시)
)

자주 쓰이는 JPA 어노테이션 전체 목록:

어노테이션역할
@EntityJPA 관리 대상 선언
@Table(name=...)테이블명 지정
@IdPrimary Key
@GeneratedValuePK 생성 전략 (IDENTITY=auto-increment, SEQUENCE, UUID)
@Column컬럼 매핑 (name, nullable, length, unique 등)
@Enumerated(EnumType.STRING)enum을 문자열로 저장 (ORDINAL은 숫자, 순서 바뀌면 위험)
@ManyToOne, @OneToMany, @OneToOne, @ManyToMany연관관계
@JoinColumn(name="user_id")FK 컬럼
@Embedded, @EmbeddableVO를 컬럼으로 펼쳐서 저장
@TransientDB에 저장 안 함 (계산 필드)
@CreatedDate, @LastModifiedDateAuditing (자동 시간 기록)
@Version낙관적 락 (동시 수정 감지)

전부 jakarta.persistence.* 패키지 (구버전 javax.persistence.*). JPA 스펙이고 Hibernate가 구현.

Q. Spring Data JPA Repository는 어떻게 쿼리가 자동 생성돼?

메서드 이름 규칙(Query Method Naming)으로 자동 생성. 인터페이스 선언만 하면 Spring이 런타임에 구현체를 만들어 주입.

// UserJpaRepository.kt (실제 프로젝트)
interface UserJpaRepository : JpaRepository<UserEntity, Long> {
    fun findByProviderAndProviderUserId(
        provider: AuthProvider,
        providerUserId: String,
    ): UserEntity?
}

위 한 줄로 자동 실행되는 SQL:

SELECT * FROM users
WHERE provider = ? AND provider_user_id = ?

JpaRepository<T, ID>가 기본 제공하는 메서드:

  • save(entity), saveAll(list)
  • findById(id), findAll(), findAllById(ids)
  • deleteById(id), delete(entity), deleteAll()
  • count(), existsById(id)

메서드 이름 키워드 규칙:

키워드예시SQL
findBy[필드]findByEmail(email)WHERE email = ?
countBy[필드]countByActive(active)COUNT(*) WHERE active = ?
existsBy[필드]existsByEmail(email)SELECT EXISTS(...)
deleteBy[필드]deleteByEmail(email)DELETE WHERE email = ?
And / OrfindByNameAndEmail(n, e)WHERE name = ? AND email = ?
GreaterThan / LessThanfindByAgeGreaterThan(18)WHERE age > ?
BetweenfindByAgeBetween(10, 20)WHERE age BETWEEN ? AND ?
Like / StartingWithfindByNameStartingWith("김")WHERE name LIKE '김%'
InfindByIdIn(ids)WHERE id IN (?)
IsNull / IsNotNullfindByDeletedAtIsNull()WHERE deleted_at IS NULL
OrderBy...Asc/DescfindAllByOrderByCreatedAtDesc()ORDER BY created_at DESC

복잡한 쿼리는 @Query로 직접 작성:

@Query("SELECT u FROM UserEntity u WHERE u.email = :email AND u.provider = :p")
fun findActive(@Param("email") email: String, @Param("p") p: AuthProvider): UserEntity?

JPQL(객체 기준) 또는 nativeQuery = true로 순수 SQL.

Q. open-in-view: false면 커넥션 오버헤드가 크지 않아?

걱정 안 해도 된다. HikariCP 덕분에 실제 오버헤드는 거의 없음.

핵심 오해: "커넥션을 열고 닫는다"

❌ 오해: @Transactional 끝 → TCP FIN → 다시 TCP 핸드쉐이크 → 새 커넥션
✅ 실제: @Transactional 끝 → 풀에 "반납" → 다음 요청이 그 커넥션 재사용

Spring Boot 기본 풀은 HikariCP. 이미 열려 있는 물리 커넥션을 풀에 보관하고, 요청마다 빌려줬다 돌려받을 뿐. 마이크로초 단위.

Django CONN_MAX_AGE와의 관계: Django는 기본적으로 풀링을 안 해서 "요청 끝나도 커넥션 닫지 마"가 필요한 것. Spring은 HikariCP가 항상 풀링해서 이 문제 자체가 없음.

대응 설정:

spring:
  datasource:
    hikari:
      maximum-pool-size: 10        # 최대 커넥션
      minimum-idle: 10             # 최소 유지
      max-lifetime: 1800000        # 30분 — 물리 커넥션 최대 생존
      idle-timeout: 600000         # 10분 유휴 시 닫음
      connection-timeout: 30000    # 풀에서 못 빌리면 30초 대기 후 예외
      keepalive-time: 120000       # 2분마다 ping (방화벽 타임아웃 대응)

open-in-view: false는 오히려 성능에 유리:

  • 빨리 반납 → 풀 회전율 ↑ → 같은 풀 크기로 더 많은 요청 처리
  • true면 view 렌더링 끝날 때까지 커넥션 잡음 → DB가 아닌 view에 커넥션 묶임 → 풀 고갈 쉬움

비유: true = 도서관 책 들고 집까지 가서 반납, false = 도서관 안에서 다 읽고 반납. 후자가 책 회전율 높아서 더 많이 빌려줄 수 있음.

단점 (커넥션 아님, 코드 번거로움): Service에서 "한 트랜잭션 안에서 모든 lazy를 미리 fetch" 해야 함. 대신 N+1 쿼리가 조용히 숨지 못함 — 코드에 명시적으로 드러나니 리뷰에서 잡기 쉬움.

Q. Flyway는 왜 Spring 내장이 아닌 별도 라이브러리야?

Java 생태계의 "Composition" 철학 때문. Django는 "Batteries Included"(ORM+Migration 일체형)이고, Spring은 각 기능을 독립 라이브러리로 조립하는 방식.

측면DjangoSpring Boot
ORMDjango ORM (자체)JPA (스펙) + Hibernate (구현)
MigrationDjango Migration (자체)Flyway / Liquibase (서드파티)
생성 방식makemigrations 자동 생성수동 SQL 작성
실행manage.py migrate앱 기동 시 Flyway가 자동

Java 생태계 철학: (1) 스펙 vs 구현 분리 (교체 자유), (2) "DB는 ORM의 손님" (자동 생성은 prod 사고 원인), (3) 엔터프라이즈 환경에서 각 팀의 선택권 존중.

Spring에서 Django makemigrations와 비슷한 것:

  • JPA Buddy (IntelliJ 플러그인) — 엔티티 변경 → Flyway SQL 초안 자동 생성
  • Liquibase diffChangeLog — 현재 엔티티와 DB 비교해 변경 스크립트 생성
  • Hibernate ddl-auto: update — 편하지만 prod 금지 (데이터 손실 가능)

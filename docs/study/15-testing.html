15. 테스트 전략

JUnit 5 + MockMvc + Testcontainers. 단위 / 통합 / 슬라이스의 차이.

테스트 피라미드 — 이 프로젝트의 구성

위로 갈수록 느리고 많아 부담, 아래로 갈수록 빠르고 많이 작성

1. 단위 테스트 — 가장 많고 빠름

Spring 컨텍스트 없이 순수 객체만 조립. 실행 수십~수백 ms. 이 프로젝트 테스트의 약 70%.

// LoginWithGoogleUsecaseTest.kt
class LoginWithGoogleUsecaseTest {

    @Test
    fun `creates new user when google subject is unknown`() {
        val identity = GoogleIdentity("sub-new", "new@example.com", "New", null)
        val savedUser = User(id = 99L, ...)

        val useCase = LoginWithGoogleUsecase(
            googleOAuthClient = StubGoogleClient(identity),   // 수제 stub
            userRepository = StubUserRepository(savedId = savedUser),
            issueTokensUsecase = stubIssueTokens(),
        )

        val result = useCase.execute("code", "https://app/callback")

        assertEquals(99L, result.user.id)
    }

    // 의존성을 interface로 받기 때문에 stub 만들기 쉬움
    private class StubGoogleClient(private val identity: GoogleIdentity) : GoogleOAuthClient {
        override fun exchangeCodeForIdentity(...) = identity
    }
}
왜 Mockito 대신 수제 stub? Kotlin 문법으로 interface를 object : GoogleOAuthClient { ... }처럼 익명 구현하기 쉽다. Mockito 정적 메서드/final class 이슈 회피. 의도가 코드로 드러남.

2. 슬라이스 테스트 — 레이어 1개만 띄움

Spring의 일부만 띄우기 위한 어노테이션들:

어노테이션띄우는 것용도
@WebMvcTestController + MVC 관련만Controller 테스트 (HTTP 요청/응답)
@DataJpaTestJPA + DB만Repository 테스트
@RestClientTestRestTemplate 관련만외부 API 클라이언트
@JsonTestJackson만직렬화 검증

@WebMvcTest 예시 — ProductControllerTest

@WebMvcTest(
    controllers = [ProductController::class],
    excludeFilters = [Filter(type = FilterType.ASSIGNABLE_TYPE, classes = [WebConfig::class])],
)
@AutoConfigureMockMvc(addFilters = false)  // Security filter 건너뛰기
@Import(GlobalExceptionHandler::class)
class ProductControllerTest {

    @Autowired
    private lateinit var mockMvc: MockMvc

    @MockBean   // 실제 빈 대신 mock 주입
    private lateinit var parseProductUseCase: ParseProductUseCase

    @Test
    fun `successful parse returns 200 response`() {
        given(parseProductUseCase.execute("...")).willReturn(
            ParseResult.Success(...)
        )

        mockMvc.perform(post("/api/v1/products/parse")
                .contentType(MediaType.APPLICATION_JSON)
                .content("""{"url":"..."}"""))
            .andExpect(status().isOk)
            .andExpect(jsonPath("$.name").value("테스트 상품"))
            .andExpect(jsonPath("$.parser_used").value("coupang-api"))
    }
}
MockMvc가 하는 일 — 진짜 HTTP 서버를 띄우지 않고 Spring MVC의 요청 처리 파이프라인만 흉내. 빠르고, Controller + DTO 직렬화 + 예외 핸들러까지 한 번에 검증.

3. 통합 테스트 — @SpringBootTest + Testcontainers

Spring 전체 + 진짜 DB. 가장 신뢰 높고 가장 느림.

@Testcontainers
@SpringBootTest
class UserRepositoryAdapterIntegrationTest {
    companion object {
        @Container
        @JvmStatic
        val postgres = PostgreSQLContainer("postgres:16")
            .withDatabaseName("linkcart_test")

        @JvmStatic
        @DynamicPropertySource
        fun properties(registry: DynamicPropertyRegistry) {
            registry.add("spring.datasource.url", postgres::getJdbcUrl)
            registry.add("spring.datasource.username", postgres::getUsername)
            registry.add("spring.datasource.password", postgres::getPassword)
        }
    }

    @Autowired
    private lateinit var userRepository: UserRepository

    @Test
    fun `duplicate provider violates unique constraint`() {
        userRepository.save(newUser(providerUserId = "sub-x"))
        assertThrows<DataIntegrityViolationException> {
            userRepository.save(newUser(providerUserId = "sub-x"))
        }
    }
}

왜 필요한가: JPA mapping, Flyway SQL, DB 제약(unique, FK CASCADE), 트랜잭션 전파는 mock으로 잡기 어렵다. 진짜 Postgres로 검증.

이 프로젝트의 실전 패턴 — Stub 공유 헬퍼

여러 테스트가 같은 stub을 반복 작성하는 걸 방지:

// ParserTestStubs.kt (test 전용, internal)
internal fun dedicatedStub(
    canParse: (String) -> Boolean,
    parse: (String) -> ParseResult,
): DedicatedProductParser = object : DedicatedProductParser {
    override fun canParse(url: String) = canParse(url)
    override fun parse(url: String) = parse(url)
}

internal fun fallbackStub(
    parse: (String) -> ParseResult,
): FallbackProductParser = object : FallbackProductParser {
    override fun parse(url: String) = parse(url)
}

// 사용처
val dedicated = dedicatedStub(
    canParse = { it.contains("coupang.com") },
    parse = { ParseResult.Failure("fail", ParserName.COUPANG) },
)

테스트 네이밍 규칙 — 이 프로젝트의 관습

  • 메서드명: 영어, 자연문 (`duplicate provider violates unique constraint`)
  • Backtick으로 공백 포함 가능 (Kotlin의 JVM interop 문법)
  • 패턴: "<조건> <결과>" 또는 "<주체> <동사> <결과>"

테스트 금지 대상 — 의미 없는 테스트

쓰지 말아야 할 테스트들
  • 프레임워크 빌트인 기능 테스트 (Jackson 직렬화 자체, JPA save 자체): 우리 코드 아님
  • 단순 데이터 객체 단독 테스트: User data class의 equals 자체 테스트 — Kotlin이 보장
  • snapshot 테스트: "이 응답 JSON이 이렇게 생겼다"를 통째로 저장. 작은 변경에도 깨지고 의미 흐림
  • 무효 케이스 전수 테스트: enum 3개 모두 valid 검증은 불필요. 하나로 충분.

회귀 IRON RULE — "기존 동작 변경 + 기존 테스트 미커버 = 신규 테스트 필수"

이 프로젝트의 review 규칙 중 하나. 예:

  • BE5에서 UseCase.execute의 fallback 로직을 Pipeline으로 이동 → 기존 5개 UseCaseTest를 그대로 ParserPipelineTest로 이관. 동작 불변 보장.
  • BE3에서 === → is FallbackProductParser 판별 변경 → "primary가 fallback 자체일 때 parse 1회만 호출" 회귀 테스트 신규 추가.

정리

  • 피라미드: 단위 > 슬라이스 > 통합 > E2E
  • 단위: interface stub 주입 (Kotlin object 익명 구현)
  • 슬라이스: @WebMvcTest + @MockBean
  • 통합: @SpringBootTest + Testcontainers
  • 테스트 이름은 영어 자연문 (backtick)
  • 프레임워크 빌트인 테스트 금지
  • 회귀 IRON RULE: 동작 변경 시 신규 테스트

04. Spring Boot 기초

Django의 URLconf + View + Serializer가 Spring Boot에선 뭐로 대응되는지.

이 챕터의 핵심 용어 — IoC · DI · Bean · @Component · @Service · @Repository · @RestController · @Configuration · AOP

Spring / Spring Boot / Spring Framework — 이름 정리

"Spring"이라고만 하면 모호하다. 실제로는 3개 층을 구분해야 한다.
이름무엇인가Django 대응
Spring FrameworkIoC 컨테이너, DI, AOP 같은 기반 기술만 제공. 웹조차 옵션.없음 (Django는 처음부터 웹 프레임워크)
Spring BootSpring Framework + 수많은 라이브러리 + 자동 설정(auto-configuration)을 묶은 "시작 키트".Django 자체가 여기에 가까움
Spring Data JPA, Spring Security, ...Spring 생태계의 각 영역 전문 모듈.Django ORM, django-allauth, ...

이 프로젝트는 Spring Boot 3.5를 쓴다. spring-boot-starter-web, -data-jpa, -security 같은 starter 의존성을 build.gradle에 넣으면 자동으로 설정이 작동한다. Django에서 INSTALLED_APPS에 앱 넣는 것과 비슷한 효과를 starter가 해준다.

IoC / DI — Django와 가장 다른 지점

Django에선 객체를 직접 만들어 쓴다:

Django
class ParseProductView(APIView):
    def post(self, request):
        # 객체를 여기서 직접 만듦
        parser = ParserFactory.get(request.data['url'])
        cache = TTLCache(maxsize=100, ttl=300)
        result = parser.parse(...)
        ...
Spring Boot
// Spring이 의존성을 주입해준다
@RestController
class ProductController(
    private val useCase: ParseProductUseCase,  // ← 주입
    private val safeUrlChecker: SafeUrlChecker, // ← 주입
) {
    @PostMapping("/parse")
    fun parse(...) { // 객체는 이미 준비됨 }
}

IoC (Inversion of Control) = 객체 생성을 개발자가 하지 않고 컨테이너에 맡긴다는 개념.
DI (Dependency Injection) = IoC를 구현하는 방법 중 하나. 의존성을 주입받는다.

앱 시작 시 컨테이너가 모든 @Component를 한 번씩 생성 → 다른 컴포넌트 생성자에 주입

왜 이게 좋나

  • 테스트 용이: ProductController를 테스트할 때 useCase를 mock으로 만들어 주입하면 된다. Django에서 view를 테스트할 때 내부 객체 생성을 모킹하는 것보다 깔끔.
  • 교체 가능: 인터페이스(포트)에 의존하고 구현체를 바꿔 끼울 수 있다. 이 프로젝트의 ProductParser 포트가 그 예.
  • 생명주기 관리: 싱글톤 / 요청당 / 세션당 등 컨테이너가 결정.

DI는 정확히 어디로 주입되는가 — 3가지 방법

핵심 — "구현체를 메서드 내부에서 선택"하는 게 아니라, 컨테이너가 객체를 만들 때 외부에서 꽂아 넣는다. 꽂는 지점이 3가지: 생성자 / 필드 / 세터. 추가로 @Bean 메서드 파라미터도 주입 지점이다.

① 생성자 주입 (Constructor Injection) — 권장. 이 프로젝트가 거의 다 쓰는 방식

Kotlin에서는 primary constructor 파라미터에 val을 붙이면 자동으로 클래스 프로퍼티가 된다. 즉 "메서드 파라미터로 주는 것"과 "클래스 속성으로 두는 것"이 한 줄에서 동시에 일어난다.

@Service
class ParseProductUsecase(
    private val parserResolver: ParserResolver,  // ← 생성자 파라미터 + 클래스 프로퍼티
    private val safeUrlChecker: SafeUrlChecker,  // ← 같음
    private val cache: ParseCache,
) {
    fun execute(url: String): Product {
        // 메서드 안에서는 "이미 주입된 프로퍼티"를 쓴다. 메서드 파라미터로 주입받는 게 아님.
        safeUrlChecker.check(url)
        val parser = parserResolver.resolve(url)  // 구현체 선택은 Resolver가
        return cache.getOrCompute(url) { parser.parse(url) }
    }
}

Java 버전으로 펼쳐 보면:

@Service
public class ParseProductUsecase {
    private final ParserResolver parserResolver;  // 클래스 필드 (= 속성)
    private final SafeUrlChecker safeUrlChecker;
    private final ParseCache cache;

    // 생성자. Spring이 이 파라미터를 보고 컨테이너에서 찾아 넣는다.
    public ParseProductUsecase(
        ParserResolver parserResolver,
        SafeUrlChecker safeUrlChecker,
        ParseCache cache
    ) {
        this.parserResolver = parserResolver;
        this.safeUrlChecker = safeUrlChecker;
        this.cache = cache;
    }

    public Product execute(String url) {
        // 메서드는 그냥 this.parserResolver를 쓴다.
    }
}

즉 답: "클래스 속성(필드)에 넣는다". 넣는 통로가 "생성자 파라미터"일 뿐. 메서드 내부에서 주입되는 게 아니다.

② 필드 주입 (Field Injection) — 안티패턴. 쓰지 마라

// Java 관례. Kotlin에선 lateinit var 써야 하는 번거로움.
@Service
public class BadUsecase {
    @Autowired              // 런타임에 리플렉션으로 필드에 값을 넣는다
    private ParserResolver parserResolver;
}
단점설명
테스트 어려움new BadUsecase()로 만들면 필드가 null. Reflection 써서 주입해야 함.
final 불가필드에 final/val을 못 붙임 → 불변성 깨짐
의존성 숨김생성자만 보면 의존성이 안 보여 "이 클래스가 뭐에 의존하는지" 파악이 어려움
순환 참조 늦게 터짐생성자 주입이면 앱 시작 때 터지지만, 필드 주입은 런타임에 NPE

③ 세터 주입 (Setter Injection) — 거의 안 씀. 선택적 의존성일 때만

@Autowired
fun setMetrics(metrics: MetricsService?) {
    this.metrics = metrics  // optional한 경우 (없으면 null)
}

④ @Bean 메서드 파라미터 — "수동 Bean을 만들 때 다른 Bean이 필요하면"

사용자가 "메서드 파라미터로 주는 거야?"라고 물은 건 아마 이 패턴을 본 것. @Configuration 안의 @Bean 메서드는 그 메서드의 파라미터가 주입 지점이다.

@Configuration
class SecurityConfig {

    // ↓ 이 메서드의 "리턴값"이 Bean으로 등록된다. 파라미터는 다른 Bean을 주입받는 통로.
    @Bean
    fun jwtAuthenticationFilter(
        accessTokenIssuer: AccessTokenIssuer,   // ← 메서드 파라미터 = 주입 지점
        userRepository: UserRepository,          // ← 여기도
    ): JwtAuthenticationFilter {
        return JwtAuthenticationFilter(accessTokenIssuer, userRepository)
    }

    // 보통 filterChain이 위의 jwtAuthenticationFilter Bean을 다시 파라미터로 받는다.
    @Bean
    fun filterChain(
        http: HttpSecurity,                        // Spring Boot가 기본 제공
        jwtFilter: JwtAuthenticationFilter,        // 위에서 내가 만든 Bean
    ): SecurityFilterChain = http
        .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter::class.java)
        .build()
}

이건 "메서드 내부에서 구현체 선택"처럼 보이지만 사실은 컨테이너가 메서드를 대신 호출하고, 그 파라미터에 다른 Bean을 주입한다. 메서드 안에서 new로 만드는 건 단지 "어떻게 조립할지"만 개발자가 통제하는 것.

구현체는 어떻게 "선택"되는가

"인터페이스 ProductParser에 구현체가 OgParser, CoupangParser가 있다. Spring은 누구를 주입하나?"

상황규칙방법
구현체 1개그냥 그거아무 annotation 필요 없음
구현체 N개 + "대표 1개"@Primary가 주입@Primary on one impl
구현체 N개 + 이름으로 고름@Qualifier("name")로 지정주입 지점에 qualifier 명시
전부 다 필요List<ProductParser>로 받음Spring이 모든 구현체 collect
// 이 프로젝트의 ParserResolver 방식: 모두 주입받고, 런타임에 골라 씀
@Component
class ParserResolver(
    private val parsers: List<ProductParser>,  // ← 모든 @Component ProductParser가 다 들어옴
) {
    fun resolve(url: String): ProductParser =
        parsers.find { it.supports(url) } ?: parsers.first { it is OgParser }
}

// 반대로 "특정 구현체 하나만 필요"하면 @Qualifier:
class SomeService(
    @Qualifier("coupang") private val parser: ProductParser,
)
정리 — 주입 지점은 클래스 속성(필드)이다. 생성자 파라미터는 그 필드를 초기화하는 통로. @Bean 메서드의 파라미터는 "그 메서드로 만들 Bean을 조립할 때 필요한 재료"를 주입받는 또 다른 지점. 메서드 내부 로직이 구현체를 고르는 게 아니라, 컨테이너가 타입·이름·@Primary·@Qualifier를 보고 결정한다.

핵심 어노테이션 4종

어노테이션의미이 프로젝트 예시
@Component"이건 Spring이 관리할 Bean"OgParser, CoupangParser, UserRepositoryAdapter
@Service@Component와 기능 동일. "비즈니스 로직 층"이라는 의미 전달용.ParseProductUseCase, LoginWithGoogleUsecase
@Repository@Component + DB 예외 변환. "영속성 층" 의미.Spring Data JPA가 자동. 직접 붙일 일 적음.
@ConfigurationBean을 수동으로 정의하는 설정 클래스.SecurityConfig, WebConfig

기능적으론 모두 @Component와 동일하지만 의미 전달이 다르다. 코드를 읽는 사람이 이게 "컨트롤러인가, 서비스인가, DB 어댑터인가"를 한눈에 알 수 있다. Kotlin 컴파일러도 이 구분을 쓴다 (예: @Repository는 DB 예외를 Spring 표준으로 변환).

@Bean 수동 등록 — @Configuration 안에서

서드파티 라이브러리 객체, 조건부 Bean 등은 @Component를 못 붙이므로 @Bean으로 직접 선언:

// SecurityConfig.kt (이 프로젝트)
@Configuration
@EnableWebSecurity
class SecurityConfig {

    @Bean
    fun jwtAuthenticationFilter(
        accessTokenIssuer: AccessTokenIssuer,  // 다른 Bean 주입 가능
    ): JwtAuthenticationFilter = JwtAuthenticationFilter(accessTokenIssuer)

    @Bean
    fun filterChain(http: HttpSecurity, ...): SecurityFilterChain = ...
}
왜 JwtAuthenticationFilter를 @Bean으로? 이 프로젝트에서 원래 @Component로 했다가 수동 @Bean으로 바꿨다. 이유: @Component면 컴포넌트 스캔이 닿는 테스트(예: @WebMvcTest)에서도 자동 로드되어 의존성 실패로 컨텍스트가 안 뜬다. @Bean으로 SecurityConfig 안에 두면 SecurityConfig를 @Import한 테스트에서만 로드된다.

REST API 작성 — 가장 자주 나오는 패턴

Django + DRF
# urls.py
urlpatterns = [
    path('products/parse', ParseView.as_view()),
]

# views.py
class ParseView(APIView):
    def post(self, request):
        serializer = ParseRequestSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        result = service.parse(serializer.validated_data['url'])
        return Response(ParseResponseSerializer(result).data)
Spring Boot
// ProductController.kt
@RestController
@RequestMapping("/api/v1/products")
class ProductController(
    private val useCase: ParseProductUseCase,
) {
    @PostMapping("/parse")
    fun parse(
        @Valid @RequestBody req: ParseRequest,
    ): ResponseEntity<ParseResponse> {
        val result = useCase.execute(req.url)
        return ResponseEntity.ok(ParseResponse.from(result))
    }
}

각 어노테이션 역할

Spring의미Django/DRF 대응
@RestController이 클래스의 모든 핸들러가 JSON을 반환 (자동 직렬화)DRF APIView의 기본
@RequestMapping("/path")클래스 전체 prefixDjango path() prefix
@PostMapping("/sub")POST 핸들러 경로DRF def post()
@RequestBodyJSON body를 객체로 역직렬화DRF Serializer(data=request.data)
@Valid역직렬화한 객체에 Bean Validation 적용DRF is_valid()
@RequestParamquery string 값 바인딩DRF request.query_params
@PathVariableURL path 변수 바인딩Django <int:id>

Jackson — DTO ↔ JSON 자동 직렬화

Django REST Framework에선 Serializer를 별도 클래스로 만든다. Spring Boot는 Jackson 라이브러리가 DTO 클래스를 자동으로 JSON 변환한다. 

@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy::class)  // camelCase → snake_case
data class ParseResponse(
    val name: String?,
    val imageUrl: String?,      // → "image_url": "..."
    val parserUsed: ParserName,  // → "parser_used": "og"
)

// enum은 @JsonValue로 직렬화 값 지정
enum class ParserName(val code: String) {
    OG("og"), COUPANG("coupang-api"), ELEVENST("11st-api");
    @JsonValue
    fun toJson(): String = code
}

application.yml — 설정 파일

Django의 settings.py는 Python 코드다. Spring Boot의 application.yml은 YAML이다. 그 대신 환경변수 주입(${LINKCART_DB_PASSWORD}) 같은 기능을 내장.

spring:
  datasource:
    url: ${LINKCART_DB_URL}         # 환경변수 필수
    username: ${LINKCART_DB_USERNAME}
  jpa:
    hibernate:
      ddl-auto: validate         # 스키마 변경 불허 (Flyway 담당)

linkcart:                        # 커스텀 prefix
  jwt:
    secret: ${LINKCART_JWT_SECRET}
    access-token-ttl-seconds: ${LINKCART_JWT_ACCESS_TTL:900}  # :뒤 = default

코드에서는 @Value("\${linkcart.jwt.secret}")로 주입받거나, @ConfigurationProperties 클래스에 bind.

Spring Boot 자동 설정 — "내가 한 게 없는데 왜 돌아가?"

개념 — classpath에 spring-boot-starter-web이 있으면 Spring Boot가 "아, 웹 앱이구나" 판단하고 Tomcat embedded server, Jackson 설정, @RestController 스캐너 등을 자동으로 켠다. -data-jpa가 있으면 DataSource, EntityManagerFactory, Transactional 매니저 자동 설정. 개발자는 application.yml만 쓰면 된다.

Django에서 INSTALLED_APPS에 앱을 추가하면 middleware, URL, model 등이 자동 등록되는 것과 비슷하다. 차이점: Django는 명시적으로 앱을 추가해야 하고, Spring Boot는 의존성이 있으면 자동.

심화 Q&A — 자주 헷갈리는 지점

Q. Bean이 도대체 뭐야?

Bean = Spring IoC 컨테이너가 생성·보관·주입을 관리하는 객체. 그 이상도 이하도 아니다.

이름의 기원 — 1997년 JavaBeans 규약(POJO + getter/setter + no-arg 생성자 + Serializable)에서 유래. Spring이 "관리 대상 객체"를 Bean으로 부르면서 의미가 일반화됨. 지금은 꼭 JavaBeans 규약을 따를 필요는 없고, 그냥 "컨테이너가 관리하는 객체"로 이해하면 된다.

// "이건 Bean이다" 라고 선언하는 3가지 방법

① @Component/@Service/@Repository/@Controller 등 stereotype
@Service
class LoginUsecase(...)    // 이 클래스의 인스턴스 1개가 Bean

② @Configuration 안의 @Bean 메서드
@Configuration
class AppConfig {
    @Bean
    fun objectMapper(): ObjectMapper = ObjectMapper()  // 리턴값이 Bean
}

③ Spring Boot auto-config가 자동 등록 (DataSource, HikariCP 등)

Bean으로 등록되면 뭐가 되나?

  • 앱 시작 시 한 번만 생성 (기본 scope=singleton)
  • 다른 Bean이 "나 이거 필요해"라고 생성자 파라미터에 적으면 컨테이너가 찾아 꽂아줌
  • 앱 종료까지 그 인스턴스가 유지됨
  • @Autowired로 꺼내 쓸 수 있음 (Kotlin에선 거의 안 씀 — 생성자 주입으로 자동)

Django로 비유하면 settings.py에서 만들어지는 DATABASES['default'] 커넥션 풀, CACHES 등이 Bean 비슷한 개념. 앱 시작 시 한 번 만들고 전역에서 쓴다. 차이점: Django는 개발자가 from django.db import connection으로 전역에서 가져오고, Spring은 생성자로 주입받는다.

Q. @Component, @Service, @Repository는 기능이 같은데 왜 나눠?

기능적으로는 거의 같다 — 네 개 다 "이건 Bean이다" 마커. 그럼 왜 4개?

어노테이션정체의미 전달기능 차이
@Component루트 어노테이션"컴포넌트다" (중립)기본 동작만
@Service@Component의 메타 어노테이션 (상속)"비즈니스 로직 층"기능은 @Component와 동일
@Repository@Component의 메타 어노테이션"영속성 층"+ DB 예외를 Spring 표준(DataAccessException)으로 변환
@Controller / @RestController@Component의 메타 어노테이션"HTTP 진입점"+ 웹 요청 매핑 활성화 + (Rest는) @ResponseBody 자동

즉 네 개 다 "@Component"다. @Service의 소스 코드를 열어보면:

// org/springframework/stereotype/Service.java
@Target(ElementType.TYPE)
@Component          // ← 여기! @Service는 @Component를 "달고" 있음
public @interface Service { ... }

그래서 기능은 똑같다. 차이는 세 가지:

  1. 읽는 사람에게 의도를 전달. 파일 열자마자 "이건 서비스구나 / DAO구나" 파악.
  2. @Repository만 예외 변환 AOP가 동작. 영속성 구현체에 붙여야 JPA/JDBC의 벤더별 예외가 Spring 표준으로 변환됨.
  3. @RestController만 웹 매핑 활성화. @Service 붙인 클래스에 @GetMapping 써봐야 라우팅 안 됨.

언제 무엇을 쓰나 (이 프로젝트 관례)

  • application/usecase/ → @Service
  • infrastructure/adapter/persistence/의 Repository 구현 → @Component (Spring Data JPA가 생성하는 JpaRepository는 자동 @Repository, Adapter는 @Component로 충분)
  • infrastructure/adapter/parser/, auth/ → @Component
  • presentation/api/의 Controller → @RestController
  • infrastructure/config/의 설정 클래스 → @Configuration

Q. 서드파티 라이브러리에 @Component를 왜 못 붙여?

이유 1: 소스 코드를 수정할 수 없다. @Component는 클래스 선언 위에 달린다.

@Component            // ← 이건 "Kotlin/Java 소스 파일"을 수정해야 붙일 수 있다
class MyClass(...)

Jackson의 ObjectMapper, Apache HttpClient, Google API의 GoogleIdTokenVerifier는 이미 컴파일된 jar 파일 안에 있다. 그 소스에 @Component를 넣을 수 없다. Maven Central에서 받은 jar를 수정할 수 없기 때문.

이유 2: 생성 시 복잡한 설정이 필요하다. @Component는 "no-arg 생성자 또는 Spring이 자동 주입 가능한 파라미터만 가진 생성자"여야 바로 작동. 서드파티 객체는 종종:

  • Builder 패턴으로만 생성 가능 (GoogleIdTokenVerifier.Builder(...).setAudience(...).build())
  • 외부 설정값이 필요 (@Value("\${linkcart.jwt.secret}")에서 꺼내야 함)
  • 조건부로 다르게 만들어야 함 (prod면 실제, dev면 mock)

이런 조립은 메서드 바디에서 개발자가 직접 코드로 해야 한다. 그게 @Bean 메서드.

@Configuration
class GoogleConfig(
    @Value("\${linkcart.google.client-id}")
    private val clientId: String,
) {
    @Bean
    fun googleIdTokenVerifier(): GoogleIdTokenVerifier =
        GoogleIdTokenVerifier.Builder(NetHttpTransport(), GsonFactory())
            .setAudience(listOf(clientId))  // Builder 패턴 + 외부 설정값
            .build()
}

Q. "수동 @Bean"이라는 건 뭐야? 자동 @Bean도 있나?

용어 정리:

구분실체누가
자동 (관례적 표현)@Component/@Service 등이 붙은 클래스 — 앱 시작 시 Spring이 스캔해서 자동 Bean 등록개발자가 어노테이션만 붙이면 끝
수동 @Bean@Configuration 클래스 안의 @Bean 메서드 — 개발자가 메서드 바디에서 직접 조립개발자가 메서드 바디 작성
Spring Boot auto-config스타터 의존성만 추가하면 Spring이 미리 작성해둔 @Configuration이 자동 적용 (DataSource, HikariCP 등)Spring Boot 프레임워크가 제공

"자동 @Bean"은 정식 용어가 아니다. 보통 "@Component 계열 = 컴포넌트 스캔으로 자동 등록", "@Bean 메서드 = 개발자가 수동 정의"로 구분한다. 둘의 결과물(컨테이너에 Bean으로 등록)은 같다.

Q. 컴포넌트 스캔(component scan)은 뭐야?

컴포넌트 스캔 = Spring이 앱 시작 시 특정 패키지 하위를 클래스패스 스캐닝으로 뒤져서 @Component(및 @Service, @Repository, @Controller, @Configuration) 붙은 클래스를 자동으로 Bean으로 등록하는 과정.

누가 언제 무슨 목적으로?

  • 누가: Spring IoC 컨테이너 (AnnotationConfigApplicationContext)
  • 언제: 앱 시작 직후 (main 함수 → SpringApplication.run() 안에서)
  • 목적: 개발자가 하나하나 @Bean으로 등록하지 않아도, 어노테이션만 붙이면 자동으로 Bean이 되게 해 보일러플레이트를 줄이는 것

스캔 대상 패키지

// 이 프로젝트의 메인 클래스
package com.linkcart                           // ← 여기가 base package

@SpringBootApplication                       // = @Configuration + @EnableAutoConfiguration + @ComponentScan
class LinkcartBackendApplication

fun main(args: Array<String>) {
    runApplication<LinkcartBackendApplication>(*args)
}

@SpringBootApplication은 메타 어노테이션. 그 안에 @ComponentScan이 들어있고, 기본 스캔 루트 = 이 클래스가 있는 패키지 하위 전체. 즉 com.linkcart.* 전부. 그래서 com.linkcart.application.auth.usecase.LoginWithGoogleUsecase가 @Service만 붙여도 자동 발견된다.

그래서 지켜야 할 관례 — 메인 Application 클래스는 가장 바깥 패키지에 둬라. com.linkcart.backend.MyApp으로 두면 com.linkcart.application.*이 스캔 밖으로 빠진다.

Q. @EnableWebSecurity, @Import, @WebMvcTest는 뭐야?

어노테이션한 줄 요약이 프로젝트 쓰임
@EnableWebSecurity"Spring Security 웹 설정 활성화"SecurityConfig에 붙어 있음
@Import"다른 @Configuration 클래스를 명시적으로 끌어와라"슬라이스 테스트에서 SecurityConfig 등 필요한 설정만 선택적 로드
@WebMvcTest"웹 계층(Controller/Filter/Advice)만 로드하는 슬라이스 테스트"Controller 테스트가 DB·Service 없이 빠르게 돔

@EnableWebSecurity — "@Enable*" 계열은 "이 기능 켜"라고 Spring에 신호를 보낸다. 내부적으로는 @Import로 필요한 Configuration을 들여온다. 다른 예: @EnableCaching, @EnableScheduling, @EnableAsync, @EnableJpaRepositories.

@Configuration
@EnableWebSecurity    // ← 이걸 넣으면 SecurityFilterChain 정의가 작동
class SecurityConfig { ... }

@Import — 테스트에서 특정 Configuration만 가져오고 싶을 때.

@WebMvcTest(AuthController::class)   // Controller 하나만 로드
@Import(SecurityConfig::class)       // + SecurityConfig 추가 로드 (필터 체인 필요)
class AuthControllerTest {
    @Autowired lateinit var mockMvc: MockMvc
    @MockBean lateinit var loginWithGoogleUsecase: LoginWithGoogleUsecase
    ...
}

@WebMvcTest — @SpringBootTest가 전체 컨텍스트(전체 Bean)를 로드한다면, @WebMvcTest는 웹 관련 Bean만 로드한다. 대략 로드되는 것: @RestController, @ControllerAdvice, Filter, HandlerInterceptor, Jackson 설정. 로드 안 되는 것: @Service, @Repository, DataSource, JPA. → 훨씬 빠르다 (수 초 vs 수십 초).

Q. Bean Validation이 뭐야?

Bean Validation = JSR-380 (Jakarta Validation) 표준 스펙. DTO/엔티티 필드에 @NotBlank, @Email, @Size(min=1) 같은 어노테이션을 붙여 선언적으로 검증 규칙을 명시하는 것. 구현체는 대부분 Hibernate Validator (이름에 속지 마라 — ORM과 무관).

import jakarta.validation.constraints.*

data class OAuthLoginRequest(
    @field:NotBlank
    val code: String,

    @field:NotBlank
    @field:Pattern(regexp = "^https?://.+")
    val redirectUri: String,
)

// Controller
@PostMapping("/oauth/google")
fun loginWithGoogle(
    @Valid @RequestBody req: OAuthLoginRequest,    // ← @Valid 있으면 자동 검증
) { ... }

@Valid 트리거 → Hibernate Validator가 req.code, req.redirectUri를 검사 → 위반 시 MethodArgumentNotValidException을 던진다. 이 프로젝트는 @RestControllerAdvice에서 잡아 400 응답으로 변환.

Kotlin 주의 — @field: 접두사. Kotlin val은 "private field + public getter"로 컴파일되는데, 어노테이션은 둘 중 어디로 갈지 애매하다. @field:NotBlank로 명시해 필드에 붙인다. 없으면 검증이 누락될 수 있음.

Django DRF의 Serializer.validate()와 유사하지만, Bean Validation은 어노테이션 선언만으로 끝나고 코드를 거의 안 쓴다는 점이 다르다.

Q. Kotlin에서 어노테이션 여러 개 쓸 때 공백으로 구분? 순서 상관있어?

공백 기준 — Kotlin/Java 어노테이션은 공백 하나 이상이면 된다. 줄바꿈도 허용. 보통 취향 따라:

// 한 줄에 나열 — 간결 (이 프로젝트 Controller 파라미터)
@Valid @RequestBody req: OAuthLoginRequest

// 줄바꿈 — 어노테이션이 많거나 길 때
@Operation(summary = "Google 로그인")
@ApiResponses(...)
@PostMapping("/oauth/google")
fun loginWithGoogle(...)

순서 — Python 데코레이터와 다르다.

Python 데코레이터Kotlin/Java 어노테이션
실행 주체함수/클래스를 감싸는 실제 로직 (return wrapper)메타데이터 일 뿐. 프레임워크가 나중에 읽어 처리
순서 영향영향 있음. @retry 밑에 @login_required면 재시도할 때마다 로그인 체크 등기본적으로 영향 없음. 단 프레임워크가 순서를 특별히 해석하는 경우만 예외
예@app.route("/x") ↔ @login_required 순서 주의@Valid @RequestBody든 @RequestBody @Valid든 동일

Kotlin 어노테이션은 기본적으로 메타데이터. 순서로 동작이 바뀌지 않는다. 예외: Spring AOP의 @Order, 여러 @Aspect 간의 우선순위, Jackson의 @JsonDeserialize 체인 등 프레임워크가 순서를 규칙으로 쓰는 경우만. 대부분의 @Valid/@RequestBody/@PathVariable은 상관없다.

팀 관례로는 보통 "의미 → 매핑" 순으로 배치한다: @Valid @RequestBody(의미)가 req: OAuthLoginRequest(매핑) 앞에. 이 프로젝트 스타일도 그대로.

Q. @RequestBody / @RestController가 JSON 직렬화 못 하면 어떻게 돼?

답: 예외를 던진다. 단, 요청/응답 방향에 따라 예외 타입과 상태 코드가 다르다.

역직렬화 실패 (요청 JSON → 객체)

상황예외기본 HTTP 응답
JSON 문법 자체가 깨짐 (예: {"code": })HttpMessageNotReadableException400 Bad Request
필수 필드 누락 (Kotlin non-null인데 없음)MissingKotlinParameterException (위 예외가 이걸 감쌈)400 Bad Request
타입 불일치 (price에 문자열)InvalidFormatException → HttpMessageNotReadableException400 Bad Request
@Valid 검증 실패MethodArgumentNotValidException400 Bad Request

직렬화 실패 (객체 → 응답 JSON)

상황예외기본 HTTP 응답
순환 참조 (A→B→A)JsonMappingException + StackOverflowError 계열500 Internal Server Error
Jackson이 모르는 타입 (커스텀 객체 + getter도 없음)InvalidDefinitionException500

이 프로젝트의 처리 방식 — @RestControllerAdvice에서 일관된 에러 응답으로 변환. Spring 기본 400보다 더 보기 좋은 JSON으로:

@RestControllerAdvice
class GlobalExceptionHandler {
    @ExceptionHandler(HttpMessageNotReadableException::class)
    fun handleNotReadable(e: HttpMessageNotReadableException) =
        ResponseEntity.badRequest().body(ErrorResponse("INVALID_JSON", e.message ?: "malformed request"))
}

Q. @RequestParam, @PathVariable 실제 사용 예시

둘 다 HTTP 요청의 특정 부분을 메서드 파라미터로 바인딩한다. 무엇을 바인딩하느냐가 다르다.

어노테이션무엇을예 URLDjango 대응
@PathVariableURL 경로 세그먼트/products/42 → id=42<int:id>
@RequestParam쿼리 스트링 또는 form-data/products?page=2&size=20request.GET['page']
@RestController
@RequestMapping("/api/v1/products")
class ProductController(...) {

    // ① @PathVariable — URL에서 값 꺼내기
    // GET /api/v1/products/42
    @GetMapping("/{id}")
    fun getProduct(
        @PathVariable id: Long,          // → 42 (자동 형변환)
    ): ProductResponse { ... }

    // ② @PathVariable이 여러 개
    // GET /api/v1/products/42/reviews/7
    @GetMapping("/{productId}/reviews/{reviewId}")
    fun getReview(
        @PathVariable productId: Long,
        @PathVariable reviewId: Long,
    ) { ... }

    // ③ @RequestParam — query string
    // GET /api/v1/products?page=2&size=20&mall=COUPANG
    @GetMapping
    fun list(
        @RequestParam(defaultValue = "0") page: Int,
        @RequestParam(defaultValue = "20") size: Int,
        @RequestParam(required = false) mall: Mall?,    // 없으면 null
    ): PageResponse<ProductResponse> { ... }

    // ④ @RequestParam 이름 다르게 매핑
    // GET /api/v1/products?q=ipad
    @GetMapping("/search")
    fun search(
        @RequestParam("q") query: String,    // URL의 q → 파라미터 query
    ) { ... }

    // ⑤ 혼합
    // POST /api/v1/products/42/reviews?notify=true
    // body: { "text": "좋아요" }
    @PostMapping("/{id}/reviews")
    fun addReview(
        @PathVariable id: Long,
        @RequestParam(defaultValue = "false") notify: Boolean,
        @Valid @RequestBody req: ReviewRequest,
    ) { ... }
}

자동 형변환 — URL은 본질적으로 문자열인데 Long, Boolean, 심지어 enum까지 Spring이 변환. 실패 시 400. 형변환 실패는 MethodArgumentTypeMismatchException으로 잡을 수 있다.

Q. @JsonNaming / @JsonValue — Jackson을 import 안 해도 되나?

답: "import는 해야 하지만 의존성 추가는 이미 돼 있다". 이 둘을 분리해서 이해해야 한다.

  1. 라이브러리(jar) 의존성 — build.gradle.kts에 Jackson이 있어야 함. 이 프로젝트는 spring-boot-starter-web이 Jackson을 transitive dependency로 끌고 온다. 추가로 jackson-module-kotlin을 명시적으로 넣어 Kotlin data class를 잘 읽게 함. 따로 implementation("com.fasterxml...")를 또 쓸 필요는 없음.
  2. 소스 import — 사용하는 Kotlin 파일 최상단에 import com.fasterxml.jackson.annotation.JsonValue 같이 써야 함. IDE가 자동으로 넣어줌.
import com.fasterxml.jackson.annotation.JsonValue          // ← 이건 필요
import com.fasterxml.jackson.databind.PropertyNamingStrategies
import com.fasterxml.jackson.databind.annotation.JsonNaming

@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy::class)
data class ParseResponse(
    val name: String?,
    val imageUrl: String?,       // → "image_url"
    val parserUsed: ParserName,   // → "parser_used"
)

@JsonNaming — 클래스 단위로 "필드명을 어떻게 JSON 키로 변환할지" 지정. SnakeCaseStrategy, KebabCaseStrategy, LowerCamelCaseStrategy 등. 이 프로젝트는 application.yml에 spring.jackson.property-naming-strategy: SNAKE_CASE를 전역 기본값으로 설정했으므로 클래스에 따로 안 붙여도 됨. (위 예시는 설명용)

@JsonValue — enum이나 일반 클래스에서 "JSON으로 직렬화할 때 이 메서드의 반환값만 써라" 지시. enum이 기본적으로 name()(예: "OG", "COUPANG")으로 직렬화되는데, 소문자 코드("og", "coupang-api")로 바꾸고 싶어서 씀.

enum class ParserName(val code: String) {
    OG("og"), COUPANG("coupang-api"), ELEVENST("11st-api");

    @JsonValue                          // 직렬화 시 이 메서드 결과가 JSON 값
    fun toJson(): String = code
}

// 결과: {"parser_used": "og"}  (ParserName.OG.toJson() = "og")
// @JsonValue 없으면: {"parser_used": "OG"}  (enum의 name)

역방향 — JSON 문자열 "og"를 다시 ParserName.OG로 읽어들이려면 @JsonCreator가 붙은 factory가 필요하다. 이 프로젝트는 응답에만 쓰므로 생략.

Q. application.yml 환경변수를 ${VAR}로 썼는데 값을 안 주면?

default 유무에 따라 동작이 다르다.

# 이 프로젝트 application.yml의 두 패턴

# ① default 없음 — 필수
datasource:
  url: ${LINKCART_DB_URL}             # 환경변수 없으면 앱 시작 실패

# ② default 있음 (: 뒤)
access-token-ttl-seconds: ${LINKCART_JWT_ACCESS_TTL:900}    # 없으면 900
base-url: ${LINKCART_COUPANG_BASE_URL:https://api-gateway.coupang.com}

# ③ 빈 default — "있어도 되고 없어도 됨"
access-key: ${LINKCART_COUPANG_ACCESS_KEY:}    # 없으면 빈 문자열
상황결과
${FOO} + FOO 환경변수 없음앱 시작 실패. IllegalArgumentException: Could not resolve placeholder 'FOO'
${FOO:default} + FOO 없음"default" 값이 들어감
${FOO:} + FOO 없음빈 문자열 ""
${FOO:default} + FOO=actual"actual" 값이 우선

값을 안 준 채로 실행하면 — Spring Boot는 앱 시작 시점에 전부 resolve를 시도한다. 빠진 게 있으면 UnsatisfiedDependencyException으로 기동 실패 (이른 실패 — fail-fast). 실행 중이 아니라 시작 시 걸리므로 프로덕션 배포 전 파이프라인에서 잡힌다.

이 프로젝트 관례 — 시크릿(DB 비번, JWT secret, Google client secret)은 default 없이 필수로, 선택 설정(TTL, base-url)은 default 제공. README에 필수 환경변수를 명시.

Q. JDBC가 뭐야?

JDBC = Java Database Connectivity. Java가 어떤 RDB(Postgres, MySQL, Oracle 등)와도 같은 코드로 통신할 수 있게 한 표준 API 스펙. JVM 생태계의 ODBC라고 보면 된다.

구조: 3단 분리

JDBC의 3단 구조. 스펙(API)과 구현(Driver)이 분리돼 DB 독립성 확보.

레이어별 역할

레이어무엇인가이 프로젝트 예
JDBC APIJava 표준 스펙 (java.sql.Connection, PreparedStatement, ResultSet). JDK에 포함.JDK 21 기본
JDBC DriverJDBC API의 벤더별 구현. DB마다 다른 jar.org.postgresql:postgresql (runtimeOnly)
상위 추상화JDBC 위에 얹힌 편의 레이어JPA/Hibernate/Spring Data JPA → 개발자가 쿼리 대신 Entity로 대화

왜 runtimeOnly? — 컴파일 시점엔 Driver의 구체 타입을 몰라도 된다. JDBC API(Connection 등)만으로 코드가 돈다. 앱이 실행되면 Hibernate가 DriverManager.getConnection("jdbc:postgresql://...")을 호출 → JDK가 classpath에서 "postgresql"을 처리할 Driver를 찾음 → Driver가 응답. 그래서 jar는 실행 시에만 있으면 충분.

연결 URL 포맷

# application.yml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/linkcart
    #    └────┬────┘ └─────┬─────┘ └───┬───┘
    #      스킴           호스트:포트         DB명
    driver-class-name: org.postgresql.Driver    # Driver 클래스 full name

스킴이 jdbc:postgresql://이면 postgresql driver, jdbc:mysql://이면 mysql driver가 선택된다. DB 교체 = 의존성 교체 + URL 스킴 교체. 코드는 거의 그대로.

Django/Python 비교: DB-API 2.0(PEP 249)이 비슷한 역할. psycopg2, pymysql이 Driver에 해당. Django ORM이 JPA에 해당.

Q. "리플렉션 로드"가 뭐야?

Reflection(리플렉션) = 런타임에 클래스/메서드/필드 정보를 프로그램이 자기 자신을 들여다보며 조회·조작하는 기능. Java/Kotlin 기본 내장.

"리플렉션 로드"는 보통 앱 시작 시 리플렉션으로 어노테이션을 읽어 Bean을 등록/연결하는 과정을 일컫는다. Spring이 이걸 광범위하게 쓴다.

Spring이 리플렉션으로 하는 일 (단계별)

  1. 클래스패스 스캔 — classpath 하위 .class 파일의 바이트코드를 읽어 어노테이션 확인. 이때 ASM 라이브러리로 바이트코드 레벨 파싱 (리플렉션 이전 단계)
  2. 클래스 로드 — @Component 붙은 것만 Class.forName()으로 로드 → 이제 리플렉션 API 사용 가능
  3. 생성자 확인 — clazz.declaredConstructors로 생성자 파라미터 타입 조회
  4. 의존성 해결 — 각 파라미터 타입으로 컨테이너에서 Bean 찾음
  5. 인스턴스화 — constructor.newInstance(deps...) 호출로 객체 생성
  6. 필드/세터 주입 — @Autowired 붙은 필드가 있으면 field.set(instance, bean)으로 값 주입 (생성자 주입만 있으면 이 단계 생략)
// 개념 코드 — Spring이 내부에서 대략 이런 일을 한다
val clazz = Class.forName("com.linkcart.presentation.api.AuthController")  // ① 로드
val ctor = clazz.declaredConstructors[0]                                // ② 생성자 조회
val paramTypes = ctor.parameterTypes                                     // ③ 필요 타입 파악
val deps = paramTypes.map { container.getBean(it) }                      // ④ 타입으로 Bean 찾기
val controller = ctor.newInstance(*deps.toTypedArray())                  // ⑤ 인스턴스 생성

리플렉션이 없으면 못 하는 것

기능리플렉션 필요성
Jackson이 data class 필드 이름을 알아서 JSON 키로 사용Jackson이 clazz.declaredFields로 필드명 읽음
@PostMapping(...)로 URL → 메서드 매핑Spring이 메서드의 어노테이션을 읽어 라우팅 테이블 구성
JPA가 @Entity에서 컬럼 추론Hibernate가 필드/어노테이션 리플렉션
@Valid가 @NotBlank 필드 검증Validator가 필드 어노테이션 스캔
테스트의 @MockBeanSpring이 컨텍스트 Bean을 프록시로 대체

비용과 주의

  • 시작 지연 — 대규모 프로젝트(수백 Bean)는 앱 시작에 수 초~수십 초가 리플렉션 스캔에 쓰임
  • 런타임 실패 — 컴파일엔 문제없지만 리플렉션 해석 시 처음 발견되는 오류들이 있음 (예: 생성자에 필요한 Bean 부재)
  • Kotlin 추가 비용 — Kotlin 리플렉션(KClass)은 Java보다 정보가 풍부해 kotlin-reflect.jar를 런타임에 추가로 로드. 이 프로젝트도 implementation("org.jetbrains.kotlin:kotlin-reflect") 포함.
  • 대안 — GraalVM Native Image, Spring AOT(Ahead-of-Time) 컴파일은 빌드 시점에 리플렉션 결과를 메타데이터로 미리 저장해 시작 속도 극단적으로 단축

이 프로젝트의 allOpen 플러그인과도 관련 — Kotlin 클래스는 기본이 final이라 Hibernate가 lazy proxy를 만들 수 없다. Hibernate는 Entity를 상속해 proxy 객체를 런타임에 생성(= 리플렉션 + 바이트코드 조작)하는데, final이면 상속 불가. 그래서 build.gradle.kts에서 allOpen { annotation("jakarta.persistence.Entity") }로 @Entity 클래스만 open으로 컴파일되게 지정한다.

Q. Controller 생성자에 타입만 써도 어떻게 @Service/@Component를 아는가?

class AuthController(
    private val loginWithGoogleUsecase: LoginWithGoogleUsecase,  // @Service 명시 안 함
    private val userRepository: UserRepository,                   // 포트 interface만 명시
) { ... }

답: 대상 클래스(LoginWithGoogleUsecase)에 이미 @Service가 붙어 있다. 주입받는 쪽에선 타입만 적으면 된다. Spring은 앱 시작 시:

  1. 컴포넌트 스캔으로 @Service 붙은 LoginWithGoogleUsecase를 찾음 → Bean 등록 (타입: LoginWithGoogleUsecase)
  2. AuthController 생성 차례에 생성자 파라미터를 봄 → "LoginWithGoogleUsecase 타입 필요"
  3. 컨테이너에서 그 타입의 Bean을 찾아 꽂아줌

주입받는 쪽에 어노테이션을 쓰면? — 의미 없다. @Service는 "이 클래스 자체를 Bean으로 등록해줘" 선언이지, "이걸 여기로 주입해줘" 선언이 아니다.

// 잘못된 기대
class AuthController(
    @Service private val loginWithGoogleUsecase: LoginWithGoogleUsecase,  // ❌ 무시됨. 에러는 안 나지만 효과 없음
)

대상 클래스에 @Service를 안 붙이면? — 그 클래스는 Bean으로 등록되지 않는다. AuthController 생성할 때 컨테이너가 "LoginWithGoogleUsecase 타입의 Bean이 없다" → NoSuchBeanDefinitionException → 앱 시작 실패.

포트(interface) 케이스 — UserRepository는 interface이므로 @Component를 붙일 곳이 없다. 대신 구현체인 UserRepositoryAdapter(infrastructure)에 @Component가 붙어 있다. Spring은 "타입=UserRepository" 요청에 대해 "이 타입으로 할당 가능한 Bean = UserRepositoryAdapter 하나 있네" → 그걸 주입.

// domain/port/UserRepository.kt — 포트 (어노테이션 없음)
interface UserRepository { ... }

// infrastructure/adapter/persistence/user/UserRepositoryAdapter.kt — 구현
@Component    // ← 이게 Bean 등록 선언
class UserRepositoryAdapter(
    private val jpa: UserJpaRepository,
) : UserRepository { ... }

즉 주석 // @Component Adapter는 "이 interface를 구현하는 클래스에 @Component가 붙어 있다는 뜻"이라는 독자 안내였다.

심화 Q&A — 자주 헷갈리는 지점

Q. 어노테이션이 붙으면 다 Bean인가?

아니다. 어노테이션은 메타데이터(태그)일 뿐이고, 그 태그를 보고 누가 무엇을 할지는 프레임워크마다 다르다.

@Entity          ← Hibernate(JPA)가 읽고 "DB 테이블로 매핑"
@Component       ← Spring이 읽고 "Bean으로 등록"
@Transactional   ← Spring AOP가 읽고 "트랜잭션으로 감쌈"
@JsonValue       ← Jackson이 읽고 "JSON 직렬화 방식 변경"
@RequestMapping  ← Spring MVC가 읽고 "URL → 메서드 라우팅"

Bean을 만드는 어노테이션 (스테레오타입 + @Bean):

어노테이션용도Spring의 처리
@Component범용 Bean스캔되어 Bean 등록
@Service비즈니스 로직 레이어@Component + 의미 전달
@Repository데이터 접근 레이어@Component + JPA 예외를 Spring 예외로 변환
@Controller전통 MVC (View 반환)@Component + MVC 핸들러 스캔
@RestControllerREST API@Controller + @ResponseBody 자동
@Configuration설정 클래스@Component + 내부 @Bean 메서드 인식
@Bean (메서드)외부 라이브러리 객체 등록@Configuration 안의 메서드 반환값을 Bean으로

Bean이 아닌 어노테이션 (메타데이터만):

어노테이션처리 주체
@Entity, @Table, @Id, @ColumnJPA / Hibernate
@Autowired, @Qualifier, @ValueSpring DI (Bean을 "주입받는" 쪽)
@Transactional, @AsyncSpring AOP
@RequestMapping, @GetMappingSpring MVC
@Valid, @NotNullBean Validation (javax.validation)
@JsonValue, @JsonPropertyJackson

Q. @Component와 @Service 차이가 뭐야?

기능적으로는 동일. @Service는 내부적으로 @Component 별칭이다. 차이는 의미 전달 + 관례.

@Service@Component
메시지"이건 비즈니스 로직이다""Spring이 관리할 일반 Bean"
위치 관례application/, usecase/어디든 (infra 많음)
리뷰어 시각"유스케이스구나""뭐 하는 Bean이지? 열어봐야"

LinkCart 실전 판단:

  • OgParser, ParserFactory, GoogleOAuthAdapter → 기술적 조립/변환이므로 @Component
  • LoginWithGoogleUsecase, SaveUserProductUsecase → 비즈니스 플로우이므로 @Service
  • @Repository는 직접 작성할 일 거의 없음 (Spring Data JPA가 자동 생성)

Q. @Value는 어떻게 application.yml 값을 주입받아?

Spring의 Property Placeholder 문법으로 외부 설정을 Bean 필드에 꽂는다.

@Component
class GoogleOAuthAdapter(
    @Value("\${linkcart.google.client-id}")
    private val clientId: String,
    @Value("\${linkcart.google.client-secret}")
    private val clientSecret: String,
) : GoogleOAuthClient { ... }

흐름:

application.yml:
  linkcart.google.client-id: ${"$"}{LINKCART_GOOGLE_CLIENT_ID}   ← 환경변수 참조
         ↓ Spring Boot가 로드
환경변수 LINKCART_GOOGLE_CLIENT_ID=abcd1234
         ↓ @Value가 읽음
GoogleOAuthAdapter.clientId = "abcd1234"

Kotlin에서 $는 문자열 템플릿 예약 문자라 \$로 이스케이프. 기본값 문법: @Value("\${key:default}").

이 프로젝트 주요 설정 키 (application.yml):

  • linkcart.google.client-id / client-secret — OAuth
  • linkcart.jwt.secret — JWT 서명
  • linkcart.coupang.access-key / secret-key — 어필리에이트 API

Q. Bean을 함수 안에서 직접 new 해도 되나?

일반 객체(DTO/VO/Entity)는 OK, Bean은 절대 금지.

Bean (주입)일반 객체 (new)
생성 횟수앱당 1번 (싱글톤)매번
상태공유 (stateless 권장)독립
예시OgParser, Service, RepositoryParseResult, Money, DTO

잘못된 예 — Bean을 함수 안에서 new:

// 나쁜 예
class ParseProductUseCase {
    fun execute(url: String) {
        val factory = ParserFactory(listOf(OgParser()))  // ❌ 직접 생성
    }
}

문제: Spring이 관리하는 인스턴스와 별개의 인스턴스가 생겨 싱글톤 깨짐, AOP 프록시(@Transactional 등) 동작 안 함, Mock 주입 불가.

반대로 이건 OK — 매 호출마다 새로 만드는 데이터 객체:

override fun parse(url: String): ParseResult {
    return ParseResult.Success(                          // 매번 new — OK
        product = Product(name = name, price = Money(0), ...),  // VO new — OK
        parserUsed = "og",
    )
}

Q. 인터페이스 구현이 여러 개면 뭘 주입받지?

방법언제 쓰나이 프로젝트 예
@Primary하나를 기본으로 지정기본 캐시 = Caffeine
@Qualifier("name")주입 시점에 명시적 지정구현체 여러 개 중 지정
List<Interface>여러 구현체 다 받아 런타임 선택ParserFactory, ParserResolver
Map<String, Interface>이름 키로 조회쓰지 않음
@Profile("dev")환경별 구현체Mock vs Real
@ConditionalOnProperty설정값 기반cache.enabled 조건부

이 프로젝트 List<ProductParser> 실전 — PR3에서 CoupangApiClient, ElevenStApiClient 추가 시 ParserResolver 코드 수정 없이 자동 등록. OCP 구조.

Q. IoC와 DI는 같은 거야?

  • IoC (Inversion of Control) = 상위 원칙. "제어권을 프레임워크에 넘긴다"
  • DI (Dependency Injection) = IoC를 실현하는 구체적 기법 중 하나

모든 DI는 IoC지만, IoC의 수단이 DI만 있는 건 아니다 (서비스 로케이터, 이벤트 기반 등도 IoC). IoC Container의 공식 이름은 ApplicationContext.

Q. Servlet과 Tomcat은 뭐야?

Servlet = 자바의 HTTP 처리 스펙(인터페이스). Tomcat = 그 스펙의 구현체(런타임). JPA↔Hibernate와 같은 구조.

[브라우저] → HTTP → [Tomcat (Servlet Container)]
                     ↓ Servlet 스펙 호출
                   [DispatcherServlet (Spring MVC가 구현한 Servlet)]
                     ↓ @RequestMapping 확인
                   [Controller]
                     ↓
                   [Service/UseCase]

Spring Boot는 내장 Tomcat을 포함 (spring-boot-starter-web). server.port: 8080이 바로 내장 Tomcat 포트.

Tomcat 대신 Jetty/Undertow로 교체 가능:

// build.gradle.kts
implementation("org.springframework.boot:spring-boot-starter-web") {
    exclude(module = "spring-boot-starter-tomcat")
}
implementation("org.springframework.boot:spring-boot-starter-jetty")

이것이 "스펙 vs 구현" 분리의 실질적 이득.

Q. Django는 Migration이 포함되어 있는데 왜 Spring은 Flyway가 별도야?

Java 생태계의 "Composition" 철학 때문. Spring은 엄밀히 "풀스택 프레임워크"가 아니라 "IoC 컨테이너 + DI + 웹" 프레임워크고, 나머지는 각자 성숙한 라이브러리를 통합해서 쓰는 구조.

측면DjangoSpring Boot
ORMDjango ORM (자체)JPA (스펙) + Hibernate (구현)
MigrationDjango Migration (자체)Flyway / Liquibase (서드파티)
생성 방식makemigrations 자동 생성수동 SQL 작성
철학Batteries Included (일체형)Composition (조립형)

각 도구 출처가 다 다름: Spring(2003, VMware) / JPA 스펙(2006, Jakarta EE) / Hibernate(2001, Red Hat) / Flyway(2010, Redgate). 각자 독립 진화.

왜 이 방식이 유리한가: (1) 교체 자유도 (Tomcat↔Jetty, Hibernate↔EclipseLink), (2) 엔터프라이즈 채택 용이 (각 팀 선호 도구 조합 가능), (3) "DB는 ORM의 손님" 철학 (자동 생성 = prod 사고 원인이라 수동 SQL 선호).

단점: 초심자 학습 곡선이 가파르고, Django처럼 매끄러운 manage.py migrate 없음. 익숙해지면 교체 자유도가 주는 이득이 보임.

정리 — 이 프로젝트의 컨트롤러 한 조각

@RestController
@RequestMapping("/api/v1/auth")
class AuthController(                              // 생성자 주입 (Kotlin primary constructor)
    private val loginWithGoogleUsecase: LoginWithGoogleUsecase,  // @Service
    private val refreshTokensUsecase: RefreshTokensUsecase,        // @Service
    private val userRepository: UserRepository,                   // 포트 (구현체는 @Component Adapter)
) {
    @PostMapping("/oauth/google")
    fun loginWithGoogle(
        @Valid @RequestBody req: OAuthLoginRequest,
    ): ResponseEntity<OAuthLoginResponse> {
        val result = loginWithGoogleUsecase.execute(req.code, req.redirectUri)
        return ResponseEntity.ok(OAuthLoginResponse(...))
    }
}

여기 보이는 거의 모든 게 이 문서에서 다룬 것들이다: data class, @RestController, 생성자 주입, @Valid, @RequestBody, 자동 JSON 직렬화.

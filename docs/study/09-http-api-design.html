DTO를 도메인 모델과 왜 분리하는가

Django REST Framework에선 ModelSerializer로 model을 그대로 직렬화하는 경우가 많다. 이 프로젝트는 Presentation DTO와 Domain을 분리했다.

이 프로젝트의 DTO 3종 구조

// presentation/dto/ParseRequest.kt
data class ParseRequest(
    @field:NotBlank(message = "url은 비어 있을 수 없습니다")
    @field:Pattern(regexp = "^https?://.+")
    val url: String,
)

// presentation/dto/ParseResponse.kt
@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy::class)  // camelCase → snake_case
data class ParseResponse(
    val name: String?,       // OG partial 대응 nullable
    val price: Money?,
    val imageUrl: String?,   // → "image_url"
    val sourceUrl: String?,  // → "source_url"
    val mall: Mall?,
    val partial: Map<String, Any>?,  // 부분 성공 표시
    val parserUsed: ParserName,
    val fallbackUsed: Boolean,
) {
    companion object {
        fun from(result: ParseResult): ParseResponse = when (result) {
            is ParseResult.Success -> // 모든 필드 non-null
            is ParseResult.Partial -> // 일부 nullable + partial
            is ParseResult.Failure -> throw IllegalArgumentException(...)
        }
    }
}

// presentation/dto/ErrorResponse.kt
data class ErrorResponse(
    val code: String,      // "validation_error", "upstream_error", ...
    val message: String,   // 사용자 친화
)

Partial 처리가 이 설계의 묘미. OG 파서가 상품명만 얻은 경우, Success로 표현할 수 없고 Failure도 아니다. DTO는 top-level을 nullable로 열고 어떤 필드가 채워졌는지를 partial 맵으로 함께 전달. 프론트가 "일부 정보라도 표시" 처리 가능.

@Valid + Jakarta Validation — Django serializer.is_valid() 대응

Django REST Framework
class ParseRequestSerializer(Serializer):
    url = serializers.URLField()

class ParseView(APIView):
    def post(self, request):
        ser = ParseRequestSerializer(data=request.data)
        ser.is_valid(raise_exception=True)  # 수동 호출
        url = ser.validated_data['url']
        ...
Spring + Jakarta Validation
@PostMapping("/parse")
fun parse(
    @Valid                    // ← 자동 검증
    @RequestBody
    request: ParseRequest,
) {
    // 여기 도달하면 이미 검증됨
    val url = request.url
    ...
}
// 실패 시 MethodArgumentNotValidException 자동 발생
@field:NotBlank의 field: 의미 — Kotlin data class는 생성자 파라미터가 property로 변환되면서 field/getter/constructor parameter 3개로 확장된다. @NotBlank만 붙이면 어디에 적용되는지 모호. @field:NotBlank는 "field에 적용"이라고 명시 → Jakarta Validation이 정확히 찾음.

GlobalExceptionHandler — 일관된 에러 응답

Django에선 middleware로 전역 예외 잡음. Spring은 @RestControllerAdvice:

@RestControllerAdvice
class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException::class)
    fun handleValidation(e: MethodArgumentNotValidException): ResponseEntity<ErrorResponse> =
        ResponseEntity.badRequest().body(
            ErrorResponse(code = "validation_error", message = e.message ?: "잘못된 요청"),
        )

    @ExceptionHandler(ResponseStatusException::class)
    fun handleStatus(e: ResponseStatusException): ResponseEntity<ErrorResponse> =
        ResponseEntity.status(e.statusCode).body(
            ErrorResponse(code = resolveCode(e.statusCode), message = e.reason ?: ""),
        )
    ...
}

원문 (pr4.html): "요청이 잘못됐을 때 각 컨트롤러마다 try/catch를 반복하면, 에러 포맷이 조금씩 달라진다. 그래서 GlobalExceptionHandler에서 한 번에 모아 통일했다."

CORS — Same-Origin Policy가 만든 불편과 CORS가 이를 푸는 방식

이 설명은 CLAUDE.md가 원하는 "문제 배경 → 막는 규칙 → 그 규칙이 만든 불편 → 다음 규칙" 패턴으로 간다.

배경 문제 → SOP → SOP 불편 → CORS

이 프로젝트의 CORS 설정

// infrastructure/config/WebConfig.kt
@Configuration
class WebConfig : WebMvcConfigurer {
    override fun addCorsMappings(registry: CorsRegistry) {
        registry.addMapping("/api/**")
            .allowedOrigins("http://localhost:3000", "exp://...")
            .allowedMethods("GET", "POST", "DELETE", "OPTIONS")
            .allowedHeaders("*")
            .allowCredentials(true)
    }
}
Spring Security와 공존 시 함정 — WebMvcConfigurer.addCorsMappings만 설정하면, Spring Security 필터 체인은 CORS를 모름. Security의 http.cors { }를 추가로 호출해야 필터 체인에 연동. 이 프로젝트 P2-2에서 이 이슈 발견 → SecurityConfig에 .cors { } 명시 추가.

이미지 프록시 — 왜 필요한가

OG 이미지를 프론트가 <img src="https://other-mall.com/image.jpg">로 직접 열면 문제 3가지:

  1. CORS: 다른 origin 이미지 허용 안 될 수 있음
  2. Hotlink 차단: 쇼핑몰이 "내 이미지 다른 사이트에서 못 쓰게" Referer 헤더로 차단
  3. HTTPS 불일치: 상품 이미지가 http면 https 페이지에서 mixed content 경고

해결: 백엔드가 이미지를 받아서 프록시:

// 프론트
<img src="/api/v1/images/proxy?url=https://mall.com/image.jpg" />

// 백엔드 (presentation/api/ImageProxyController.kt)
@GetMapping("/proxy")
fun proxy(@RequestParam url: String): ResponseEntity<ByteArray> {
    if (!safeUrlChecker.isSafe(url)) throw BAD_REQUEST("허용되지 않는 URL")

    val response = restTemplate.exchange(url, GET, ...)
    val contentType = response.headers.contentType
    if (contentType.subtype !in ALLOWED_IMAGE_SUBTYPES) throw BAD_GATEWAY
    return ResponseEntity.ok().contentType(contentType).body(response.body)
}
프록시가 만든 새 문제 — SSRF — "서버가 임의 URL을 fetch하는" 순간, 공격자가 url=http://127.0.0.1/admin을 보내면 서버가 내부망을 대신 접근. 이것이 Server-Side Request Forgery. 13 챕터에서 별도로 다룸.

snake_case JSON — Jackson 전역 설정

Django는 Python이라 원래 snake_case. Kotlin은 camelCase. 프론트(JSON)는 관례상 snake_case. 자동 변환:

# application.yml
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE

이 한 줄로 모든 DTO 필드가 JSON 직렬화 시 자동 변환. imageUrl → "image_url".

OpenAPI / Swagger — 자동 문서화

Django DRF는 drf-spectacular 같은 별도 설치 필요. Spring Boot는 springdoc-openapi-starter-webmvc-ui 의존성만 넣으면 자동:

  • /openapi.json — 스펙 JSON (codegen에 사용)
  • /docs — Swagger UI (브라우저에서 API 탐색)
왜 중요? 프론트가 OpenAPI JSON → TypeScript 타입 자동 생성. "BE가 바뀌면 FE 타입도 자동 동기화". 16번 챕터에서 상세.

MockMvc로 Contract 테스트

@WebMvcTest(ProductController::class)
class ProductControllerTest {
    @Autowired
    private lateinit var mockMvc: MockMvc

    @MockBean
    private lateinit var useCase: ParseProductUseCase

    @Test
    fun `successful parse returns 200 with snake_case JSON`() {
        given(useCase.execute("https://...")).willReturn(Success(...))

        mockMvc.perform(post("/api/v1/products/parse")
            .contentType(APPLICATION_JSON)
            .content("""{"url":"https://..."}"""))
            .andExpect(status().isOk)
            .andExpect(jsonPath("$.image_url").value("https://..."))  // snake_case 확인
            .andExpect(jsonPath("$.parser_used").value("coupang-api"))
    }
}

핵심: 프론트엔드가 받을 JSON 모양을 검증하는 contract test. 내부 구현 바뀌어도 이게 통과하면 FE 안 깨짐.

심화 Q&A

Q. DTO가 맞아, Payload가 맞아? 선호 차이?

둘 다 쓰인다. 하지만 뜻이 같지 않다. 문맥에 따라 골라 쓴다.

용어풀네임강조하는 것적용 범위
DTOData Transfer Object"레이어/프로세스 경계를 넘을 때 쓰는 객체 형태"코드 관점. 클래스 단위. 네트워크/레이어 무관.
Payload—"HTTP 요청/응답의 body 안의 내용물"네트워크 관점. 전송 중의 바이트/JSON.

관계 — DTO 객체가 JSON으로 직렬화되어 HTTP body의 Payload가 된다. 같은 것을 다른 층위에서 본 명칭이다.

// 개발자가 쓰는 코드 관점 = DTO
data class ParseRequest(
    val url: String,
)

// 네트워크 위에서의 관점 = Payload (request body)
POST /api/v1/products/parse
Content-Type: application/json

{                            // ← 이 JSON이 "payload"
  "url": "https://shop.example.com/p/1"
}

네이밍 관례

  • Java/Kotlin/C# 세계에선 DTO가 압도적. 클래스 이름에도 ...Dto, 폴더명 dto/로 쓴다 (이 프로젝트도).
  • Node.js/Python/REST 문서 세계에선 "payload", "request body", "response body"를 더 자주 쓴다. OpenAPI 스펙도 requestBody.
  • Request DTO와 Response DTO로 나누는 게 흔함: ParseRequest, ParseResponse.

이 프로젝트 결정 — Spring/Kotlin 팀 관례에 맞춰 presentation/dto/ + ...Request/...Response. API 문서나 PR 본문에서 "요청 payload는 …"처럼 말할 때는 payload도 자연스럽게 혼용.

혼동 피하는 간단 규칙

  • 코드 안에서 클래스 가리킬 때 → DTO ("ParseRequest DTO")
  • 네트워크 트래픽/스펙 문서 설명할 때 → payload ("요청 payload에 url 포함")
  • 둘 다 맞고, 의미가 정확히 같지는 않으니 문맥만 신경 쓰면 됨

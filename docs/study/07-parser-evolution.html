07. 파서 설계의 진화 (Phase 1)

OgParser 1개 → Factory → Resolver + Pipeline. 각 단계에서 무엇을 고치고 왜 그렇게 고쳤는가.

이 챕터의 목표 — "완벽한 설계를 한 번에 그린 게 아니다. 필요가 드러날 때마다 리팩토링했다"는 걸 보여주는 것. 설계 결정 6건의 트레이드오프를 따라간다.
이 챕터의 핵심 용어 — OG parser · 핫링크 · Port · Adapter · Factory · Resolver · Pipeline · Fallback Chain

초기 버전 (PR 2) — 포트 1개 + 구현 1개

// domain/port/ProductParser.kt
interface ProductParser {
    fun canParse(url: String): Boolean
    fun parse(url: String): ParseResult
}

// infrastructure/adapter/parser/OgParser.kt
@Component
class OgParser(...) : ProductParser {
    override fun canParse(url: String) = true  // 모든 URL을 폴백으로 처리
    override fun parse(url: String): ParseResult = ...
}

이 시점엔 OG 파서(Open Graph meta 태그 파싱)만 있었다. 모든 URL이 canParse=true를 반환하니 canParse는 무의미했다. 하지만 쿠팡/11번가 전용 파서가 곧 추가될 거라 인터페이스엔 미리 둠.

쿠팡 · 11번가 추가 (PR 3) — Factory 패턴 등장

Factory가 URL 도메인을 보고 어느 파서를 쓸지 선택

Factory 구현:

@Component
class ParserFactory(
    private val parsers: List<ProductParser>,     // Spring이 모든 ProductParser 빈을 수집 주입
    @Qualifier("ogParser")
    private val fallbackParser: ProductParser,
) {
    fun getParser(url: String): ProductParser =
        parsers.filter { it !== fallbackParser }
               .firstOrNull { it.canParse(url) }
            ?: fallbackParser
}
여기에 3가지 냄새가 있다 (BE3 리팩토링의 트리거)
  1. canParse=true인 OgParser가 parsers에 섞여 있어 filter { it !== fallbackParser }로 제외해야 한다. 인스턴스 동일성 비교.
  2. @Qualifier("ogParser")로 Bean 이름 문자열에 의존. 타입 안전하지 않음.
  3. ProductParser 인터페이스가 "라우팅(canParse)"과 "실행(parse)" 두 책임을 섞어 둠.

// application/parser/ParserResolver.kt
@Component
class ParserResolver(
    private val dedicatedParsers: List<DedicatedProductParser>,  // 2개: Coupang, 11st
    val fallbackParser: FallbackProductParser,                  // 1개: Og
) {
    fun resolve(url: String): ProductParser =
        dedicatedParsers.firstOrNull { it.canParse(url) } ?: fallbackParser
}

이제 filter가 사라졌다. 타입이 다르므로 애초에 dedicatedParsers에 OgParser는 안 섞인다. @Qualifier 문자열도 제거.

리팩토링 3: String → Enum (PR BE4)

ParseResult.parserUsed가 String이면 "og", "coupang-api", "cupang-api"(오타!) 어느 값이든 들어간다. 컴파일러 보호 부재.

Before: String 상수
object ParserNames {
    const val OG = "og"
    const val COUPANG = "coupang-api"
}

data class Success(
    val parserUsed: String,  // "cupang-api" 같은 오타 허용
)
After: Enum
enum class ParserName(val code: String) {
    OG("og"), COUPANG("coupang-api"), ELEVENST("11st-api");

    @JsonValue
    fun toJson(): String = code
}

data class Success(
    val parserUsed: ParserName,  // 오타 불가
)

주의할 점 — Mall 선례를 따랐다. 이 프로젝트에 이미 domain/vo/Mall.kt가 @JsonValue로 lowercase 직렬화하는 패턴이 있었다. 새 enum(ParserName, AuthProvider)도 동일 패턴으로 통일해 팀 관행 일관성 확보.

왜 @JsonValue가 필요한가 — Jackson의 enum 기본 직렬화는 name()을 쓴다. 즉 ParserName.OG가 JSON에 "OG"로 나간다. 프론트엔드는 "og"를 기대. @JsonValue로 직렬화 값 커스터마이징.

리팩토링 4: Fallback 정책을 UseCase에서 Pipeline으로 (PR BE5)

BE3까지 UseCase가 이렇게 길었다:

@Service
class ParseProductUseCase(private val parserResolver: ParserResolver) {
    @Cacheable(...)
    fun execute(url: String): ParseResult {
        val primaryParser = parserResolver.resolve(url)
        val primaryResult = primaryParser.parse(url)

        if (primaryResult !is ParseResult.Failure || primaryParser is FallbackProductParser) {
            return primaryResult
        }

        val fallbackResult = parserResolver.fallbackParser.parse(url)
        return when (fallbackResult) {
            is ParseResult.Success -> fallbackResult.copy(fallbackUsed = true)
            ...
        }
    }
}

문제: UseCase가 "파서 오케스트레이션 + 캐싱 + 횡단 관심사(@Cacheable)" 여러 책임. SRP 흔들림.

면접에서 이야기할 포인트

"완성된 설계"가 아닌 "진화한 설계"로 설명하면 설득력이 커진다.
"처음엔 OgParser만이라 Factory가 없어도 됐다. 쿠팡 추가하면서 Factory 넣었다. 그 Factory가 Bean 이름에 의존하는 게 불편해서 포트 분리하고 Resolver로 바꿨다. 그 과정에서 UseCase가 비대해져 Pipeline으로 분리했다."
이게 "나는 설계 결정을 근거 있게 내린다"는 증거가 된다.

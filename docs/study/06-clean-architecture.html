06. 클린 아키텍처 4 레이어

domain / application / infrastructure / presentation. 왜 이 4단계로 나누는가.

이 챕터의 핵심 용어 — Clean Architecture · Hexagonal (Ports & Adapters) · DDD · DIP · DI · IoC

문제의 원인 — "다 한 파일에 뭉치면 왜 안 되나"

초기에는 한 파일/한 클래스에 다 넣는 게 빠르다. 규모가 커지면:

  • DB가 바뀌면 비즈니스 로직 코드까지 전부 수정해야 한다 (MySQL → Postgres, ORM 교체 등)
  • 외부 API가 바뀌면 (쿠팡 API 개편) 도메인 규칙까지 흔들린다
  • 테스트가 어렵다: 로직 하나 테스트하려고 DB·네트워크·프레임워크를 전부 띄워야
  • 프레임워크 업그레이드 시 앱 전체 재작성

클린 아키텍처는 이걸 "변하는 속도가 다른 것은 따로 둔다"는 원리로 해결한다.

4 레이어 — "안쪽이 가장 중요하고 오래 간다"

동심원 다이어그램. 의존 화살표는 항상 안쪽을 향한다.

핵심 개념 — 포트 & 어댑터 (의존성 역전)

클린 아키텍처의 가장 미묘하지만 중요한 부분. "application이 DB를 알면 안 되는데 어떻게 DB를 쓰나" 문제.

❌ 잘못된 구조 (의존 방향 역전)
// application
class LoginWithGoogle(
    private val userJpaRepository: UserJpaRepository,  // ❌ JPA 직접
) {
    fun execute(...) {
        userJpaRepository.saveAndFlush(...)  // JPA 호출
    }
}

// DB를 JPA에서 MyBatis로 바꾸면? UseCase까지 수정
✅ 포트 & 어댑터
// domain/port — "나는 save만 있으면 된다"
interface UserRepository {
    fun save(user: User): User
    fun findById(id: Long): User?
}

// application — 포트만 안다
class LoginWithGoogle(
    private val userRepository: UserRepository,
) { ... }

// infrastructure — 포트를 구현
@Component
class UserRepositoryAdapter(
    private val jpa: UserJpaRepository,
) : UserRepository { ... }
의존 방향이 뒤집힌다 — 원래 "application이 infrastructure를 쓴다"는 자연스러운 방향 같다. 그러나 포트를 domain/application에 두고 infrastructure가 포트를 구현하게 하면 의존 방향이 infrastructure → application이 된다. 이걸 DIP (Dependency Inversion Principle)이라 부른다.

실전 사례 — 이 프로젝트의 LoginWithGoogleUsecase

파일 하나를 보면 이 아키텍처가 어떻게 구현되는지 선명해진다:

package com.linkcart.application.auth.usecase  // application 레이어

import com.linkcart.application.auth.port.GoogleOAuthClient  // 같은 레이어의 포트
import com.linkcart.domain.entity.User                         // domain 엔티티
import com.linkcart.domain.model.AuthProvider                   // domain enum
import com.linkcart.domain.port.UserRepository                  // domain 포트
// ⬆ Jpa/Spring Security/Google SDK 같은 infrastructure는 하나도 import 안 함

@Service
class LoginWithGoogleUsecase(
    private val googleOAuthClient: GoogleOAuthClient,   // 포트 (인터페이스)
    private val userRepository: UserRepository,         // 포트
    private val issueTokensUsecase: IssueTokensUsecase,
) {
    fun execute(code: String, redirectUri: String): LoginResult {
        val identity = googleOAuthClient.exchangeCodeForIdentity(code, redirectUri)
        val user = userRepository.findByProviderAndProviderUserId(AuthProvider.GOOGLE, identity.subject)
            ?: userRepository.save(User(...))
        val tokens = issueTokensUsecase.execute(userId = user.id!!)
        return LoginResult(user, tokens)
    }
}

이 UseCase는 Google을 어떻게 호출하는지, DB가 뭔지, JWT가 어떻게 서명되는지 모른다. 포트(interface)만 알고, 그 뒤의 구체 구현은 Spring DI 컨테이너가 런타임에 연결해준다.

왜 이게 좋나 — 실전 이득 4가지

  1. 테스트 용이: LoginWithGoogleUsecaseTest에서 GoogleOAuthClient, UserRepository를 간단한 stub로 주입. DB·네트워크 없이 유스케이스 로직 검증.
  2. 교체 가능: PostgreSQL → MySQL로 바꿔도 UserRepositoryAdapter 하나만 고친다.
  3. 이해 쉬움: UseCase 파일을 열면 "이 기능이 무슨 단계를 거쳐 일어나는가"가 한 흐름으로 읽힘. 인프라 잡음 없음.
  4. 의도 표현: "우리 UseCase는 Google에서 신원을 가져오고, DB에서 유저를 찾거나 만든다"는 계약이 타입으로 드러남.

Clean vs Hexagonal vs Layered vs DDD — 자주 혼동되는 네 단어

네 개가 경쟁하는 "다른 아키텍처"인 것처럼 쓰이지만 실제로는 층위가 다르다. Layered는 구성(N층으로 쌓기), Hexagonal/Clean은 의존 방향 원칙(안쪽으로), DDD는 도메인 모델링 언어. 이 프로젝트는 네 가지를 동시에 쓴다.
이름핵심 주장제안자층위이 프로젝트
LayeredPresentation / Business / Persistence로 쌓는다관례 (80년대~)구성 방식presentation/application/infrastructure 3층으로 쌓아 씀
Hexagonal (Ports & Adapters)도메인을 중심에 두고 주변 모든 외부는 Port(interface) + Adapter(impl)로 격리Alistair Cockburn (2005)의존 방향 원칙UserRepository(port) + UserRepositoryAdapter(adapter) 등 전부 이 구조
Clean ArchitectureHexagonal + 레이어를 동심원(도메인→앱→인프라→프레젠테이션)으로 명시Robert C. Martin (2012)의존 방향 원칙 + 레이어domain/application/infrastructure/presentation 4 레이어가 이거
DDD도메인을 Ubiquitous Language로 모델링 (Entity / VO / Aggregate / Repository / Domain Event)Eric Evans (2003)모델링 언어domain/에 Entity(User), VO(Money, Mall), Repository(port) 사용

관계: Hexagonal ⊂ Clean. Clean Architecture는 Hexagonal의 아이디어를 레이어 명칭으로 정리한 것. DDD는 "도메인을 어떻게 쪼개 쓸지"를 정하고, Hexagonal/Clean은 "그 도메인을 외부와 어떻게 격리할지"를 정한다.

Spring이 기본적으로 헥사고날인가?

결론 — 아니다. Spring Boot는 기본적으로는 Layered Architecture에 가깝다. 헥사고날은 개발자가 "포트 interface를 어디에 둘지"를 스스로 결정해야 하는 구조이며, Spring이 강제하지 않는다.

Spring Boot 기본 관례 (표준 튜토리얼이 가르치는 것)

com.example.app/
├── controller/      // @RestController — Presentation
├── service/         // @Service — Business Logic
├── repository/      // interface extends JpaRepository — Persistence
└── entity/          // @Entity — JPA 엔티티 (= 도메인 모델 + DB 스키마 뒤섞임)

이게 Spring Boot의 "즉석 시작" 구조다. 이 구조의 특징:

  • entity 폴더의 @Entity는 "도메인 모델"이자 동시에 "JPA 스키마 매핑". 두 역할이 한 클래스에 섞여 있음.
  • Repository interface는 JpaRepository를 상속. 즉 이미 JPA에 묶여 있음. 도메인이 "JPA 밖 구현체"를 받을 여지가 없음.
  • service가 repository를 직접 import. 의존 방향이 상→하로 그대로 내려감 (Layered).
  • 포트 interface는 없음. UserRepository는 domain의 포트가 아니라 JPA의 Repository.

이 프로젝트가 Layered를 왜 버렸나

Layered 기본 구조의 문제이 프로젝트의 해결
@Entity 클래스가 도메인 로직도 담고 DB 컬럼도 담음 → 단위 테스트가 DB를 띄워야domain.entity.User (순수 Kotlin) + infrastructure.adapter.persistence.UserEntity (@Entity) 분리
Service가 JpaRepository를 직접 import → JPA → Hibernate에 묶임application은 domain.port.UserRepository (interface)에만 의존. 구현은 infrastructure
도메인 로직 테스트에도 Spring 컨텍스트 필요UseCase 테스트에 Spring 불필요. 포트를 Stub으로 넣고 @Test 하나면 끝
외부 API(쿠팡/Google) 클라이언트를 Service에 직접 심음application에 GoogleOAuthClient 포트 → infrastructure에 GoogleOAuthAdapter 구현

그래서 Spring에서 헥사고날을 하려면 뭐가 필요한가

Spring이 안 해주는 것을 개발자가 규율로 지켜야 한다:

  1. 도메인 폴더에 프레임워크 import 금지. org.springframework.*, jakarta.persistence.*가 도메인 코드에 들어가면 안 됨. ArchUnit 테스트로 강제 가능.
  2. Repository를 2개로 쪼갠다. domain.port.UserRepository(포트 interface)와 infrastructure.UserJpaRepository extends JpaRepository(JPA 인터페이스). 사이에 UserRepositoryAdapter가 bridge.
  3. @Entity와 도메인 엔티티를 분리. User(domain) ↔ UserEntity(infra) 사이에 .toDomain() / .fromDomain() 매핑 함수.
  4. application 레이어에 별도 포트 패키지. 외부 서비스(Google OAuth, 결제, SMS 등)마다 port interface.
  5. 의존성 주입은 Spring에 맡기되, 주입받는 타입은 항상 포트. 어댑터는 Spring이 포트 타입으로 찾아 주입.
요약 — Spring은 "헥사고날을 가능하게" 하지만 "강제하지" 않는다. DI 컨테이너가 있어 포트/어댑터 패턴이 쉽게 성립하긴 하지만, 기본 관례는 Layered. 헥사고날로 갈지 말지는 프로젝트 복잡도가 이 추가 구조를 정당화하는가로 판단. 작은 CRUD면 기본 Layered로 충분하다 (다음 섹션의 YAGNI 참고).

심화 Q&A — 엔티티 이중성과 레이어 개수

Q. "@Entity가 도메인 모델이자 JPA 스키마 매핑"이 무슨 뜻이야? JPA 스키마는 DB 모델이란 소리인가? DB 모델과 Entity는 별개여야 하지 않나?

질문이 곧 정답. "DB 모델과 도메인 Entity는 별개여야 한다"가 이 프로젝트가 지키려는 원칙이고, "Spring 기본 튜토리얼은 그걸 안 지킨다"가 위 섹션의 요지다. 용어부터 정리.

용어의미성격
JPA 스키마 매핑"이 Kotlin 클래스 = 이 DB 테이블, 이 필드 = 이 컬럼"이라는 번역 규칙. @Entity, @Table, @Column, @Id 어노테이션으로 표현ORM(Hibernate)이 읽는 기술 메타데이터 — DB 모델과 거의 같은 말
도메인 모델"User는 이메일과 공급자를 가진다" 같은 업무 개념. 업무 규칙을 담은 순수 객체비즈니스 언어, 프레임워크 무관

Spring 기본 튜토리얼이 한 클래스에 섞는 모습

// Spring 튜토리얼 스타일 — entity/User.kt
@Entity                                  // JPA: "나 DB 테이블이야"
@Table(name = "users")                   // JPA: "테이블 이름은 users"
class User(
    @Id @GeneratedValue                  // JPA: "PK 자동생성"
    val id: Long? = null,
    @Column(nullable = false)              // JPA: "NOT NULL 컬럼"
    val email: String,
) {
    fun canWithdraw(): Boolean = ...   // 도메인 로직: 탈퇴 가능 여부
}

이 한 클래스가 두 관객을 동시에 섬긴다:

  • Hibernate가 읽음 — "users 테이블, id PK, email NOT NULL 컬럼"으로 해석해 SQL 생성
  • UseCase가 씀 — user.canWithdraw(), User.create(...) 같은 업무 호출

이게 왜 문제인가

  1. 도메인 테스트가 DB를 필요로 한다. 단순히 val user = User(email = "a@b.com")만 해도 Hibernate 컨텍스트가 의미를 가지려면 준비가 필요. 순수 단위 테스트가 사실상 통합 테스트로 부풀어오름.
  2. DB 스키마 변경이 도메인 언어를 침범. DBA가 "email 컬럼을 email_address로 바꾸자"고 하면 도메인 코드의 필드명까지 바꿔야 함. 업무 용어는 안 바뀌었는데.
  3. 도메인이 JPA 관습을 삼킴. id: Long? = null이 되는 건 "JPA가 저장 전엔 ID가 없어서"지, 업무 개념에 "User는 id가 nullable"이라는 속성이 있는 게 아니다.
  4. 교체 불가. JPA를 MyBatis나 Exposed로 바꾸려면 도메인 클래스를 전부 뜯어야 함.

이 프로젝트의 해결 — 두 클래스로 쪼갬

domain/entity/User.kt — 순수 도메인
package com.linkcart.domain.entity

// JPA/Spring import 0개
data class User(
    val id: Long? = null,
    val email: String,
    val provider: AuthProvider,
    ...
)
infrastructure/.../UserEntity.kt — JPA 스키마
package com.linkcart.infrastructure.adapter.persistence.user

@Entity
@Table(name = "users")
class UserEntity(
    @Id @GeneratedValue
    val id: Long? = null,
    @Column(nullable = false)
    val email: String,
    ...
) {
    fun toDomain() = User(id, email, ...)
    companion object {
        fun fromDomain(u: User) = UserEntity(u.id, u.email, ...)
    }
}
다시 정리 — 질문자의 "DB 모델과 Entity는 별개여야 한다"는 직관이 정확히 이 프로젝트의 원칙. "JPA 스키마"는 DB 모델과 거의 같은 말 — ORM이 객체↔테이블을 매핑하기 위한 기술 정보. Spring 기본 튜토리얼이 이걸 도메인 클래스 하나에 묶어 쓰니까 "두 역할 섞임" 문제가 생기는 것이고, 이 프로젝트는 두 클래스로 쪼개 해결.

Q. "이 프로젝트가 Layered를 버렸다"는데, 지금도 레이어 4개 아니야? Layered 맞잖아?

핵심 혼동 — "레이어가 있다"와 "Layered Architecture"는 다르다. Layered는 그냥 "층이 있다"가 아니라 특정 스타일의 이름. 이 프로젝트도 레이어는 있지만 Layered 스타일이 아니라 Clean/Hexagonal 스타일.

Layered (Spring 튜토리얼 기본)이 프로젝트 (Clean + Hexagonal)
레이어 개수보통 3층 (Controller / Service / Repository)4층 (domain / application / infrastructure / presentation)
의존 방향위→아래 단방향. Controller가 Service를, Service가 Repository를 직접 import항상 안쪽으로만. application이 infrastructure를 모름. infra가 도메인 port를 구현(역방향)
도메인의 프레임워크 의존Entity에 @Entity, Repository에 JpaRepository 상속 — 프레임워크가 도메인에 스며듦도메인은 JPA/Spring import 0개. 순수 Kotlin
Service가 아는 것JpaRepository<User> 직접 주입 → JPA에 묶임도메인 port(interface)만 주입 → 구현체가 뭔지 모름
단위 테스트Service 하나 테스트해도 @SpringBootTest 또는 H2 필요UseCase 테스트에 Spring 불필요, 포트 stub 주입으로 끝

"Layered를 버렸다"의 진짜 의미 — 레이어 자체를 버린 게 아니라 Spring 튜토리얼이 기본으로 깔아주는 Layered 스타일(위 표 좌측 특성 묶음)을 안 쓴다는 뜻. "층을 쌓는다"는 아이디어는 그대로 유지하고, 거기에 의존 방향 규칙(DIP)과 도메인 순수성을 얹은 것.

비유 — 층이 있다고 다 "아파트"는 아니다. 주상복합·단독주택·빌라 모두 층이 있지만 설계 원칙이 다르다. Layered, Clean, Hexagonal은 같은 "다층 건물"이지만 서로 다른 설계 스타일. 이 프로젝트는 Clean + Hexagonal 스타일.

Q. entity라는 말이 domain에도 infra에도 있잖아? 4계층인데 DB까지 하면 5계층 아니야?

두 개의 엔티티, 같은 이름, 다른 역할. 용어 혼란이 맞다. 그러나 레이어 수는 그대로 4개.

"entity"가 쓰이는 두 맥락

도메인 엔티티 (DDD 용어)JPA Entity (Jakarta Persistence 용어)
의미ID로 식별되고 상태가 변하는 업무 개념@Entity가 붙어 DB 테이블로 매핑되는 기술 클래스
출처Eric Evans, DDD (2003)JPA 스펙 (Java Persistence API, 2006)
이 프로젝트 위치domain/entity/User.ktinfrastructure/adapter/persistence/user/UserEntity.kt
파일명 관례User, RefreshToken — 순수 이름UserEntity, RefreshTokenEntity — Entity 접미사로 구분
어노테이션없음 (data class)@Entity, @Table, @Column, @Id...
존재 이유업무 규칙 표현객체↔DB 변환 (ORM)

"DB까지 하면 5계층?" — 아니다. 코드 레이어와 외부 시스템은 다른 것.

DB는 코드 레이어가 아니라 외부 시스템. infrastructure 레이어가 그 외부와 대화하는 코드.

정리:

  • 레이어 = 코드의 논리적 묶음 (domain / application / infrastructure / presentation). 여전히 4개.
  • 외부 시스템 = Postgres 프로세스, Google 서버, 쿠팡 API 서버. 이들은 다른 프로세스/다른 회사의 시스템. 이 프로젝트의 "레이어 카운트"에 안 들어감.
  • UserEntity(@Entity 붙은 JPA Entity)는 "infrastructure가 Postgres와 대화하기 위한 매핑 클래스". infra 레이어 안의 한 파일일 뿐 별도 레이어가 아니다.
  • User(domain 엔티티)와 UserEntity(JPA 엔티티)는 같은 "entity" 단어를 쓰지만 다른 개념. 그래서 이 프로젝트는 파일명에 Entity 접미사를 붙여 명시적 구분.
왜 하필 같은 이름을 썼나 — DDD(2003)가 "Entity"를 도입한 뒤, JPA(2006)가 그 용어를 가져와 어노테이션 이름으로 재사용했다. 같은 단어를 두 커뮤니티가 다른 의미로 쓰게 된 역사적 혼선. 그래서 Clean Architecture 프로젝트는 대부분 User vs UserEntity 같은 접미사로 구분한다.

심화 Q&A — 디렉토리 구조 헷갈리는 지점

Q. domain/model/이 뭔데? entity/vo/port만 있어야 하는 거 아니야?

결론부터 — "entity / vo / port만"이 "DDD 교과서의 최소 집합"은 맞다. 하지만 실제 코드에는 그 셋 중 어디에도 정확히 맞지 않는 도메인 개념들이 있고, 이 프로젝트는 그걸 model/이라는 네 번째 폴더에 모았다.

이 프로젝트 domain/model/의 실제 내용

domain/model/
├── AccessToken.kt       // data class (token: String, expiresAt: Instant)
├── AuthProvider.kt      // enum { GOOGLE }
├── GoogleIdentity.kt    // data class (subject, email, displayName, avatarUrl)
├── ParseResult.kt       // sealed interface { Success, Partial, Failure }
└── ParserName.kt        // enum { OG, COUPANG, ELEVENST }

왜 entity/도 vo/도 아닌가?

파일entity가 아닌 이유vo가 아닌 이유 (이 프로젝트 관례)
AccessTokenDB에 저장 안 함. ID 없음 (Access JWT는 서버에 저장 X)재사용되는 값 타입이 아님 (특정 유스케이스의 산출물)
GoogleIdentitylinkcart 도메인 식별자가 아님 (외부 소스 Google의 신원 정보)Entity의 일부 필드로 쓰이지 않음 (유스케이스 경유 객체)
ParseResult식별자 없음. Success/Partial/Failure의 합집합sealed interface — 단순 값이 아닌 상태 분기 표현
AuthProvider, ParserNameenum, 인스턴스가 고정enum은 "여러 Entity 필드로 들어가 재사용되는 값 타입"인 Mall/Money과 달리 "제공자/파서 선택" 의미 전달용

vs domain/vo/의 실제 내용

domain/vo/
├── Mall.kt     // enum { GENERIC, COUPANG, ELEVENST, ... } — Product.mall 필드로 쓰임
└── Money.kt    // data class (amount: Long) — Product.price 필드로 쓰임

이 프로젝트의 관례적 구분:

  • entity/ — ID로 식별되고 상태가 변하며 DB에 저장되는 "업무의 주인공" (User, Product, RefreshToken, UserProduct)
  • vo/ — Entity의 필드로 들어가는 불변 값 타입 (Money, Mall). 여러 Entity가 공유.
  • model/ — 도메인 개념이지만 Entity도 VO도 아닌 것 — 유스케이스 결과, 외부 시스템의 신원, 상태 합집합(sealed), 선택지 enum
  • port/ — 외부 세계와의 계약 interface
엄밀 DDD 관점에서는 이 model/ 전부를 "VO"로 묶는 게 정답. 실무에선 "여러 Entity가 공유하는 값 타입(vo)" vs "유스케이스 흐름에서 태어나는 결과/신원/enum(model)"을 분리하면 의도가 선명해져서 이 구분을 쓰는 팀이 많다. 팀 관례 중 하나일 뿐, 표준은 아니다.

API 응답값이냐는 질문 — 아니다. API 응답은 presentation/dto/에 있다. domain/model/은 내부 도메인 객체. 예를 들어 ParseResult.Success는 UseCase 내부에서 흐르는 결과이고, presentation은 이걸 ParseResponse DTO로 변환해서 내려준다.

// application/usecase/ParseProductUseCase.kt
fun execute(url: String): ParseResult { ... }   // ← domain.model 반환

// presentation/api/ProductController.kt
val result: ParseResult = useCase.execute(req.url)
val response: ParseResponse = ParseResponse.from(result)  // ← DTO로 변환
return ResponseEntity.ok(response)

Q. application 안에 port/가 있는 건 이상하지 않아? port는 domain에만 있는 거 아닌가?

아주 좋은 질문. 이건 Hexagonal 원론에선 모호한 지점인데, 실무에선 "도메인 포트" vs "애플리케이션 포트"로 구분하는 스타일이 널리 쓰인다. 이 프로젝트도 그 스타일.

도메인 포트와 앱 포트 — 위치와 의도의 차이
구분domain/port/application/<도메인>/port/
대표 예UserRepository, ProductRepository, ProductParserGoogleOAuthClient, AccessTokenIssuer, RefreshTokenGenerator
소유자도메인 자체 — "사용자 개념은 어딘가 저장되어야 한다"특정 유스케이스 — "로그인 흐름은 Google 토큰을 교환해야 한다"
재사용여러 유스케이스가 공유 (SaveUser, LoginWithGoogle, DeleteUser 등 전부 UserRepository 씀)보통 1~2개 유스케이스만 씀 (GoogleOAuthClient는 LoginWithGoogleUsecase만)
DDD 용어"Repository" 전술적 패턴과 대응"Application Service Port" — DDD 원론엔 없음, Hexagonal에서 인정

원론에 가까운 스타일에선 포트를 domain에만 두고, application은 UseCase만 두기도 한다. 이 프로젝트가 둘을 분리한 건:

  1. GoogleOAuthClient를 domain/port/에 두면 "도메인이 Google이란 특정 제공자를 아는 것"이 되어 오염.
  2. application/auth/port/에 두면 "auth 유스케이스 묶음이 이 외부 서비스를 필요로 한다"고 의도가 선명.
  3. 도메인은 "User/AuthProvider/RefreshToken" 같은 본질 개념만 알면 되고, "Google OAuth"는 구체 선택이므로 한 칸 바깥.
실무 판단 기준 — "이 포트를 만약 우리 앱이 Google 말고 Apple 로그인으로 바꾸면 폐기하나?" YES면 application 포트. "User는 어느 제공자든 필요하므로 폐기 안 함" → UserRepository는 domain 포트.

Q. infrastructure도 도메인별로 쪼개야 하지 않아? config가 여기 있는 것도 일관성 없어 보여

infra는 도메인 단위가 아니라 "외부 시스템/기술 단위"로 쪼개는 게 헥사고날 관례. 그 이유는 infra가 담당하는 게 "도메인 관심사"가 아니라 "어떤 기술로 외부와 말할지"이기 때문.

infrastructure/
├── adapter/
│   ├── parser/          // "HTML/외부 API 파싱" 기술 묶음
│   ├── auth/            // "JWT/OAuth" 기술 묶음
│   └── persistence/     // "JPA/Postgres" 기술 묶음
│       ├── user/
│       ├── refreshtoken/
│       └── userproduct/ // ← persistence 내부에서는 도메인별로 다시 쪼갬
└── config/              // Spring 설정 (프레임워크 어댑터의 조립)

즉 1차 구분은 기술, 2차 구분은 도메인. 이 프로젝트도 persistence/ 안은 user/, refreshtoken/, userproduct/로 도메인별로 나뉜다.

왜 application과 infra의 구조가 대칭이 아닌가

레이어1차 분류 기준근거
application도메인 (auth, user, parser)"이 유스케이스들은 같은 업무를 다룬다"가 단위
infrastructure기술/외부 시스템 (parser=HTML/HTTP, auth=JWT/OAuth, persistence=JPA)"같은 기술 스택을 쓴다"가 단위 — 한 팀이 소유하면 좋고 라이브러리 버전도 묶임

config가 왜 infrastructure 안? — SecurityConfig, WebConfig는 Spring 프레임워크 어댑터의 조립이다. 도메인 로직이 아니고, 외부 프레임워크에 "이렇게 동작하라"고 설정하는 코드라서 infra 성격. 헥사고날 관점에서 "Spring = 외부 프레임워크 = infrastructure"라고 본다.

다른 배치 스타일과의 비교

A. 이 프로젝트 — config를 infra 안
infrastructure/
├── adapter/
└── config/
    ├── WebConfig.kt
    └── security/SecurityConfig.kt
B. config를 최상위 5번째 레이어로
domain/
application/
infrastructure/
presentation/
config/                 // 5번째
├── WebConfig.kt
└── SecurityConfig.kt

B 스타일도 유효하지만, Spring 설정은 사실상 "필터/서블릿/Bean 조립"이라 infra와 성격이 거의 같다 → 이 프로젝트는 A 선택. 구분 기준:

  • config가 대부분 Spring Bean 조립이면 → infrastructure/config (이 프로젝트)
  • config에 도메인 정책도 섞이면 (예: 비즈니스 규칙 기반 feature flag) → 최상위 분리가 낫다

Q. DDD니까 port보단 repository가 낫지 않나? domain에선 interface, infra에선 구현체로 보면 되지 않아?

맞는 말이다. 그리고 실제로 그렇게 쓴다. 용어만 명확히 나눠보자.

용어출처범위
PortHexagonal (Alistair Cockburn)도메인이 외부에 요구하는 모든 interface — DB, HTTP 클라이언트, 메시지 큐 등 전부 포함
RepositoryDDD (Eric Evans)Aggregate(Entity 묶음)의 영속성만 담당하는 특수한 Port. DB 저장/조회에 한정

즉 Repository ⊂ Port. Repository는 "DB용 Port"라고 봐도 된다. 그래서 이 프로젝트도 UserRepository, RefreshTokenRepository로 Repository 네이밍을 쓴다. interface는 domain, 구현체는 infra — 질문의 멘탈 모델이 정확히 맞다.

// domain/port/UserRepository.kt — "Port이지만 Repository로 이름 지음"
interface UserRepository {
    fun save(user: User): User
    fun findById(id: Long): User?
}

// infrastructure/adapter/persistence/user/UserRepositoryAdapter.kt — 구현
@Component
class UserRepositoryAdapter(
    private val jpa: UserJpaRepository,
) : UserRepository { ... }

그럼 왜 폴더 이름이 port/일까?

  • domain/port/에는 Repository만 있는 게 아니다. ProductParser 같은 "HTML 파싱 서비스 interface"도 있다. Parser는 Repository라고 부르면 어색 — 영속성이 아니기 때문.
  • 여러 성격의 interface(Repository, Parser, Client, Gateway)를 한 폴더에 두려면 상위 개념인 port/가 자연스럽다.
  • 이름이 port여도 내부 파일 이름은 UserRepository.kt처럼 DDD 용어를 쓴다. 이 프로젝트도 그대로.

구현체 이름의 관례

구현체 위치이름 관례예
port의 1차 어댑터XxxAdapterUserRepositoryAdapter, GoogleOAuthAdapter
Spring Data JPA interfaceXxxJpaRepositoryUserJpaRepository (Adapter가 내부적으로 사용)
특정 제공자별이름 + 제공자JwtAccessTokenIssuer, SecureRandomRefreshTokenGenerator

Q. Spring은 interface 받으면 구현체를 자동 선택하잖아. 그럼 헥사고날 아니야?

이 질문이 핵심이다. 답은 "Spring DI는 어댑터 주입을 쉽게 해주지만, 그게 헥사고날 구조를 만드는 건 아니다". 분해해서 보자.

Spring이 실제로 해주는 것

// Spring은 이 정도까지만 해준다:
interface Foo
@Component class FooImpl : Foo

@Service
class MyService(private val foo: Foo)    // ← FooImpl을 자동으로 찾아 주입

맞다. 이것만 봐도 interface/구현체 분리가 자동으로 되는 것처럼 보인다. 그런데 헥사고날이 요구하는 건 interface/impl 분리 그 자체가 아니라 "분리가 어디에 이뤄졌는가"이다.

Spring은 interface/impl 분리를 "연결"만 해준다. 어디에 둘지는 개발자 판단.

Spring이 안 해주는 것 (= 헥사고날을 위해 개발자가 결정해야 할 것)

  1. interface를 어디에 둘지 — repository/UserRepository.java(Spring Data JPA 상속)에 둘지, domain/port/UserRepository.kt(순수 Kotlin)에 둘지 Spring은 무관심.
  2. interface가 프레임워크에 묶이지 않게 할지 — extends JpaRepository를 쓰면 Spring Data가 구현체를 자동 생성해 주기 편하다. 하지만 이러면 interface가 이미 JPA 스펙에 묶여 JPA 없이 테스트할 수 없다. 헥사고날 원칙에 어긋남.
  3. 도메인 엔티티와 JPA Entity를 분리할지 — @Entity class User 한 클래스로 쓸지, domain/entity/User.kt(순수) + infrastructure/.../UserEntity.kt(@Entity) 두 클래스로 쓸지 Spring은 강제 안 함.
  4. 구현체 방향 — 헥사고날은 "infra → domain 방향 의존"이 필수. Spring은 반대 방향("service가 repository impl에 의존")도 허용.
흔한 오해 — "Spring에서 interface/impl 쓰면 헥사고날이다"는 아니다. Spring Data JPA의 UserRepository extends JpaRepository도 interface + 구현체 분리지만 헥사고날 아니다. 이유: 그 interface는 이미 JPA에 결합돼 있고, 도메인이 아닌 repository/ 폴더에 있고, 바꿀 수 있는 어댑터가 아니다.

비유 — Spring DI는 콘센트 연결선이다. 가전제품(어댑터)을 콘센트(생성자 파라미터)에 꽂아주는 일만 한다. 콘센트 규격이 유럽식인지 한국식인지(포트 설계), 어느 방에 몇 개 둘지(레이어 배치)는 건축가(개발자)의 결정. Spring은 규격을 정해주지 않는다.

주의 — 과하면 독

YAGNI — 작은 CRUD 앱에 포트·어댑터를 다 만들면 파일 수가 4배로 늘고 오히려 어려워진다. 이 프로젝트가 굳이 이렇게 한 이유는: (1) 티니어 면접 어필 (2) 외부 의존성이 많아 분리 이득이 실재 (3) Kotlin/Spring 패턴 학습.
실무에서는 도메인 복잡도가 이 구조를 정당화할 수준일 때만 도입한다.

심화 Q&A — AI 시대에도 이 구조가 항상 정답일까

Q. 파일 수가 늘어도 관심사가 분리되면 읽고 수정하기 편하지 않아? AI가 코드 작성 비용을 낮춘 지금은 항상 클린 아키텍처가 정답 아닌가?

방향성은 맞다. 그러나 "항상 정답"은 아니다. 질문 속 전제를 분해해서 이득과 비용을 하나씩 보자.

AI가 정말 낮춘 것 vs 그대로인 것

비용 항목AI 이전AI 도입 후감소 폭
작성 (타이핑)높음 — 포트·어댑터·매핑 함수 매번 손으로낮음 — 보일러플레이트는 생성됨크게 ↓ ✓
이해 (읽기/흐름 추적)높음 — 파일 3~4개 거쳐 로직 따라감높음 — 사람이 여전히 읽어야 함거의 동일
탐색 (어디 뭐 있는지)높음 — 네이밍 관례 학습 필요중간 — grep/LSP로 찾긴 함조금 ↓
변경 추적 (한 개념 수정 시 몇 파일)높음 — User 필드 하나가 3~5 파일중간 — AI가 전파 보조, 리뷰/검증은 사람조금 ↓
교체 이득 (DB/API 바꿀 때)높음 — 어댑터 하나만 교체높음 — 그대로동일

결론 — AI가 낮춘 건 작성 비용뿐. 이해/탐색/리뷰/판단 비용은 거의 그대로. "항상 클린이 정답"이 되려면 이해 비용까지 자동화돼야 하는데 아직 그 단계가 아니다.

반례 — 과잉 추상화가 오히려 독인 경우

  1. 단순 CRUD 프로젝트. 업무 규칙이 사실상 없는데 User → UserEntity → UserJpaRepository → UserRepositoryAdapter → UserRepository(port) → UseCase → Controller → DTO 7 파일을 거치는데 실제 로직은 save(user) 한 줄. 파일이 많은 만큼 리뷰 비용과 실수 여지도 늘고, 팀원은 "왜 이렇게 돌아가죠"를 반복 질문.
  2. 외부 의존성이 적은 앱. DB는 Postgres 하나만 평생 쓸 예정, 외부 API 없음, 결제 없음 → 포트의 교체 이득이 0. 테스트 용이성만 남는데 그건 @DataJpaTest와 H2로도 충분. 클린 구조의 이득 기둥 중 하나가 통째로 빠짐.
  3. 팀 학습 비용. 모두가 클린 아키텍처를 이해하지 못하면 껍데기만 클린인 코드가 태어난다. 포트는 있는데 UseCase가 JPA Exception을 그대로 흘려보내거나, 어댑터가 도메인 규칙을 담거나. 이러면 이득은 없고 파일 수 비용만 남음.
  4. 변경 추적의 역설. "User에 phoneNumber 추가" 한 변경이 User + UserEntity + toDomain/fromDomain + Flyway 마이그레이션 + UserResponse DTO를 동시에 건드림. AI 도움 있어도 5개 파일 diff를 사람이 리뷰. Layered였다면 Entity 겸 도메인 1파일 + Flyway 1파일로 끝.

"AI가 쓰는 코드는 일관된 패턴일 때 더 잘 쓴다"는 맞다. 다만 그 패턴이 적절한 복잡도일 때만. 필요 없는 추상화까지 규칙으로 깔면 AI는 그 규칙을 무조건 따라가며 단순한 문제를 복잡하게 해결하려 든다. "파일 개수 = 품질"이 아니다.

그래서 판단 기준은 근본적으로 바뀌지 않음 — 세 질문에 YES가 많을수록 클린이 이득:

  1. 외부 의존성이 많은가? (결제 / 다중 DB / 외부 파싱 API / 인증 제공자 여러 개) — 이 프로젝트는 OG + 쿠팡 + 11번가 + Google + JWT만큼 YES.
  2. 제품 수명이 긴가? (5년+ 예상 / 라이브러리/DB가 바뀔 가능성) — 길수록 교체 이득이 누적.
  3. 테스트가 품질 기준인가? (단위 테스트 비율이 높은 팀 / 빠른 피드백 루프가 핵심) — 포트 stub 주입의 이득이 바로 나옴.
AI 시대의 조정된 권고 — "작성 비용이 낮아졌으니 경계선이 약간 이동했다"가 정확한 표현. 예전엔 "외부 의존성 3개+일 때 클린"이었다면 이제 "2개+일 때도 고려할 만함" 정도. 하지만 단순 CRUD에도 항상 클린을 넣으라는 결론은 과잉. YAGNI는 여전히 유효. 특히 팀이 구조를 이해하는가는 AI가 해결해주지 않는다.

이 프로젝트가 그래도 클린을 쓴 이유 — 바로 위 "주의 — 과하면 독"에 이미 답: (1) 면접 어필 (2) 외부 의존성 다수(OG·쿠팡·11번가·Google·JWT) (3) Kotlin/Spring 헥사고날 학습. 실무 관점에선 (2)가 실재하므로 분리 이득이 있음. 단, 회사 실무에서 CRUD 수준의 앱이라면 Layered가 더 나은 선택일 수 있다는 균형 감각은 계속 유지할 것.

정리

  • 레이어 4개: domain / application / infrastructure / presentation
  • 의존 방향: 항상 안쪽으로만
  • domain은 프레임워크·DB·외부 API 어디에도 의존 안 함
  • 포트(interface)를 안쪽 레이어에 두고 바깥이 구현 (DIP)
  • 장점: 교체 가능, 테스트 쉬움, 의도 드러남
  • 주의: 도메인이 단순하면 이 구조 자체가 부담

⚙️ 0. 환경 설정

JDK란?

JDK (Java Development Kit)는 Kotlin/Java 코드를 실행하기 위한 "런타임 + 도구 모음"입니다.

Python과 비교 Python에서 python3를 설치해야 .py 파일을 실행할 수 있듯이, JDK를 설치해야 .kt(Kotlin) 파일을 컴파일하고 실행할 수 있습니다.
PythonKotlin/Java
python3 설치JDK 설치
python3 app.py 실행java -jar app.jar 실행
소스 → 바로 실행소스 → 컴파일 → 실행

JDK 버전 이해하기

Java는 6개월마다 새 버전이 나오지만, LTS(Long Term Support) 버전만 장기 지원됩니다.

버전LTS?상태
Java 17✅ LTS많은 프로젝트가 사용 중
Java 21✅ LTS이 프로젝트가 사용 — 현재 권장
Java 22, 23, 24❌단기 지원 (6개월)
Java 25✅ LTS최신이지만 일부 도구가 아직 미지원
왜 25가 아니라 21? JDK 25가 설치되어 있었지만, 빌드 도구(Gradle)가 아직 25를 지원하지 않아서 21을 사용합니다. 실무에서도 "최신"보다 "안정적인 LTS"를 쓰는 것이 일반적입니다.

JAVA_HOME — "어떤 JDK를 쓸지" 지정

JDK가 여러 개 설치되어 있을 때, 어떤 걸 사용할지 환경 변수로 지정합니다.

# 설치된 JDK 목록 확인
/usr/libexec/java_home -V
# 결과:
# 25.0.2 (arm64) "Eclipse Adoptium" - "OpenJDK 25.0.2"
# 21.0.10 (arm64) "Eclipse Adoptium" - "OpenJDK 21.0.10"  ← 우리가 쓸 것

# JDK 21을 기본으로 설정 (이 터미널 세션에서)
export JAVA_HOME=$(/usr/libexec/java_home -v 21)

# 확인
java -version
# openjdk version "21.0.10" ← OK!
매번 치기 귀찮다면 쉘 설정 파일(~/.zshrc)에 추가하면 터미널 열 때마다 자동 적용됩니다: 
echo 'export JAVA_HOME=$(/usr/libexec/java_home -v 21)' >> ~/.zshrc
source ~/.zshrc

🟣 1. Kotlin 기초

Kotlin은 JetBrains(IntelliJ 만든 회사)이 만든 프로그래밍 언어입니다. Java와 100% 호환되면서 훨씬 간결합니다. Android 공식 언어이기도 합니다.

Python과의 관계 Python처럼 간결한 문법을 추구하지만, 컴파일 타임에 모든 타입을 검사합니다. Python의 mypy를 "필수"로 켜놓고, 그걸 어기면 아예 실행이 안 되는 것과 비슷합니다.

변수와 타입

Kotlin에는 변수 선언이 두 가지입니다:

// val = 불변 (한 번 넣으면 못 바꿈). Python에서 UPPER_CASE로 상수 관례 쓰는 것과 비슷
val name: String = "iPhone 16"
val price: Int = 1500000
// name = "Galaxy"  ← 컴파일 에러! val은 재할당 불가

// var = 가변 (바꿀 수 있음). Python의 일반 변수
var count: Int = 0
count = 1  // OK

// 타입 추론 — 타입을 안 써도 Kotlin이 알아서 파악
val currency = "KRW"       // String으로 자동 추론
val quantity = 3            // Int로 자동 추론
Python 비교 
# Python — 타입 힌트는 선택사항이고 런타임에 강제 안 됨
name: str = "iPhone 16"
price: int = 1500000
차이점: Kotlin은 타입이 맞지 않으면 아예 컴파일(빌드)이 안 됩니다. 실행 전에 에러를 잡아줌.

기본 타입

Longint큰 정수 (Python은 자동)
Doublefloat소수점

문자열 템플릿

val name = "쿠팡"
val price = 15900

// $ 로 변수 삽입 (Python의 f-string과 동일)
val message = "$name 에서 ${price}원"   // "쿠팡 에서 15900원"
Python 비교

거의 동일! f"..." 대신 그냥 "..." 안에 $ 를 씁니다.

null 안전성 — Kotlin의 가장 중요한 특징

Python에서는 아무 변수나 None이 될 수 있어서, AttributeError: 'NoneType' has no attribute 에러를 런타임에 만납니다. Kotlin은 이걸 컴파일 타임에 원천 차단합니다. 

// 기본: null 불가능
val name: String = "iPhone"
// name = null  ← 컴파일 에러!

// ? 를 붙이면 null 가능
val discount: Int? = null    // OK — Int? 는 "Int 또는 null"

// null일 수 있는 값을 쓸 때는 안전 호출 필요
val length = name.length          // OK — name은 null이 아님이 보장됨
// val x = discount.toString()     ← 컴파일 에러! discount가 null일 수 있음
val x = discount?.toString()      // ?. = null이면 전체가 null 반환
val y = discount ?: 0             // ?: = null이면 기본값 0 사용
요약 String = 절대 null 아님  |  String? = null일 수 있음  |  ?. = 안전 호출  |  ?: = null이면 대체값

함수

// 기본 함수
fun calculateTotal(price: Int, quantity: Int = 1): Int {
    return price * quantity
}

// 한 줄이면 = 으로 축약 가능
fun double(n: Int): Int = n * 2

// 반환값 없는 함수 (Python의 -> None)
fun printHello() {
    println("Hello!")
}

// 사용
val total = calculateTotal(15900)           // 15900 (quantity 기본값 1)
val total2 = calculateTotal(15900, 3)       // 47700
val total3 = calculateTotal(price = 15900, quantity = 3)  // 이름 지정 호출
Python 비교 
def calculate_total(price: int, quantity: int = 1) -> int:
    return price * quantity
거의 동일합니다. def → fun, -> → : (콜론 뒤에 반환 타입).

클래스

// Kotlin 클래스 — 생성자가 클래스 선언부에 포함!
class Product(
    val name: String,           // val = 읽기 전용 속성
    val price: Int,
) {
    fun displayPrice(): String = "${price}원"
}

// 사용 — new 키워드 불필요!
val product = Product("iPhone", 1500000)
println(product.name)            // "iPhone"
println(product.displayPrice())  // "1500000원"
Python 비교 
class Product:
    def __init__(self, name: str, price: int):
        self.name = name
        self.price = price

    def display_price(self) -> str:
        return f"{self.price}원"

product = Product("iPhone", 1500000)
Kotlin은 __init__과 self.xxx = xxx가 필요 없습니다. 클래스 선언부의 val name: String이 속성 선언 + 생성자 + 대입을 한 번에 합니다.

data class — 데이터 담는 클래스

data class는 class 앞에 data만 붙이면 됩니다. 그러면 Kotlin이 자동으로 만들어주는 것들:

자동 생성Python 대응하는 일
equals()__eq__내용이 같으면 같은 객체로 판단
hashCode()__hash__dict의 key로 사용 가능
toString()__repr__출력 시 읽기 좋은 문자열
copy()없음일부 필드만 바꿔서 새 객체 만들기
data class Money(
    val amount: Int,
    val currency: String = "KRW",
)

val a = Money(15900)
val b = Money(15900)
println(a == b)         // true! (내용이 같으므로)
println(a)              // "Money(amount=15900, currency=KRW)"

// copy — 일부 필드만 바꿔서 새 객체 (불변 객체에서 매우 유용)
val discounted = a.copy(amount = 12900)  // Money(amount=12900, currency=KRW)
이 프로젝트에서 data class 사용처 Product (상품 엔티티), Money (가격 값 객체) — 모두 data class입니다. 데이터를 담는 용도의 클래스는 무조건 data class로 만든다고 생각하면 됩니다.

enum class — 정해진 값 중 하나

// Mall(쇼핑몰)은 쿠팡, 11번가, 기타 중 하나만 가능
enum class Mall(val displayName: String) {

val mall = Mall.COUPANG
println(mall.displayName)  // "쿠팡"

Python 비교

class Mall(Enum):
    COUPANG = "쿠팡"

거의 동일합니다. Kotlin은 각 값에 여러 속성을 붙일 수 있다는 차이가 있습니다.

sealed class — "이 중 하나" (가장 강력한 기능)

Python에는 완벽한 대응 개념이 없습니다. Union[A, B, C]와 비슷하지만, 컴파일러가 모든 경우를 처리했는지 강제합니다. 

// 파싱 결과는 반드시 이 3가지 중 하나
sealed class ParseResult {
    data class Success(
        val product: Product,
        val parserUsed: String,
    ) : ParseResult()

    data class Partial(
        val fields: Map<String, Any>,
        val parserUsed: String,
    ) : ParseResult()

    data class Failure(
        val reason: String,
    ) : ParseResult()
}
sealed class의 핵심 가치 when 식에서 모든 경우를 처리하지 않으면 컴파일 에러가 납니다. 새로운 케이스를 추가하면, 처리 안 한 곳이 자동으로 에러 표시됩니다. → "실수로 빠뜨리는 것"이 불가능!

interface — 계약서

"이 메서드들을 반드시 구현해야 합니다"라는 계약입니다. 구현 방법은 자유. 클린 아키텍처에서 레이어 간 의존성을 끊는 핵심 도구입니다. 

// 계약: "URL을 파싱할 수 있는 무언가"
interface ProductParser {
    fun canParse(url: String): Boolean
    fun parse(url: String): ParseResult
}

// 구현 1: OG 태그 파서
class OgParser : ProductParser {
    override fun canParse(url: String): Boolean = true
    override fun parse(url: String): ParseResult {
        // Jsoup으로 OG 태그 파싱하는 로직...
    }
}

// 구현 2: 쿠팡 API 클라이언트
class CoupangApiClient : ProductParser {
    override fun canParse(url: String): Boolean = url.contains("coupang.com")
    override fun parse(url: String): ParseResult {
        // 쿠팡 어필리에이트 API 호출 로직...
    }
}
Python 비교 
class ProductParser(Protocol):
    def can_parse(self, url: str) -> bool: ...
    def parse(self, url: str) -> ParseResult: ...
Python의 Protocol과 같지만, Kotlin에서는 구현 안 하면 컴파일 에러.

when 식 — 패턴 매칭

Python의 match/case(3.10+)와 비슷하지만, sealed class와 결합하면 훨씬 강력합니다.

fun handleResult(result: ParseResult): String = when (result) {
    is ParseResult.Success -> "성공: ${result.product.name}"
    is ParseResult.Partial -> "부분: ${result.fields.size}개 필드"
    is ParseResult.Failure -> "실패: ${result.reason}"
    // 3개 다 처리했으므로 else 불필요!
    // 만약 하나라도 빠지면 컴파일 에러
}

// 일반 값에도 사용 가능
val emoji = when (mall) {
    Mall.COUPANG  -> "🟥"
    Mall.ELEVENST -> "🟧"
    Mall.GENERIC  -> "⬜"
}

컬렉션

// 리스트 (불변)
val fruits = listOf("사과", "바나나", "포도")
// fruits.add("귤")  ← 컴파일 에러! 불변 리스트

// 가변 리스트

val prices = listOf(15900, 23000, 8900)

it은 람다의 기본 파라미터명입니다. Python의 리스트 컴프리헨션 대신 .filter, .map 체이닝을 씁니다.

🟢 2. Gradle 이해하기

Gradle이란?

Python 세계의 도구들을 하나로 합친 것입니다:

PythonGradle역할
pip installgradle build의존성 다운로드 + 빌드
requirements.txtbuild.gradle.kts의존성 목록
pytestgradle test테스트 실행
python manage.py runservergradle bootRun서버 실행
없음gradle build소스 코드 → 실행파일로 컴파일
왜 "빌드"가 필요한가? Python은 인터프리터가 소스 코드를 직접 실행합니다. Kotlin은 소스 코드를 먼저 바이트코드로 컴파일해야 합니다. 이 과정에서 타입 에러, 문법 에러를 모두 잡아냅니다. gradle build = 컴파일 + 테스트 + 패키징 을 한 번에 해주는 명령입니다.

build.gradle.kts 한 줄씩 설명

// ① 플러그인 — "이 프로젝트는 Kotlin + Spring Boot 프로젝트입니다"

// ③ Java 버전 설정 — JDK 21을 사용

// ④ 의존성 저장소 — 라이브러리를 어디서 다운로드할지

    mavenCentral()   // PyPI 같은 곳. Java/Kotlin 라이브러리 중앙 저장소
}

// ⑤ 의존성 목록 — pip install 할 패키지 목록

    testImplementation("org.jetbrains.kotlin:kotlin-test-junit5")            // Kotlin 테스트

./gradlew build 명령어 해부

./gradlew build
│    │     │

│    └── gradlew = Gradle Wrapper 스크립트

./gradlew build 가 내부적으로 하는 일 (순서대로)

① 의존성 다운로드
build.gradle.kts의 dependencies에 적힌 라이브러리들을 인터넷에서 다운로드
(처음 한 번만. 이후엔 캐시 사용)

▼
② 컴파일 (compileKotlin)
src/main/kotlin/ 아래의 .kt 파일들을 JVM 바이트코드(.class)로 변환
여기서 타입 에러, 문법 에러가 발견됨 → 에러 있으면 여기서 멈춤!
Python 비교: Python은 이 단계가 없음 (실행 시 에러 발견)
▼
③ 리소스 처리 (processResources)
src/main/resources/ 의 application.yml 등 설정 파일을 빌드 결과에 포함
▼
④ 테스트 컴파일 (compileTestKotlin)
src/test/kotlin/ 아래의 테스트 코드도 컴파일
▼

컴파일된 테스트를 JUnit 5로 실행
하나라도 실패하면 → 빌드 실패!
Python 비교: pytest
▼
⑥ 검사 (check)
코드 스타일, 정적 분석 등 추가 검사 (설정된 경우)
▼
⑦ 패키징 (jar)
컴파일된 코드 + 리소스 + 라이브러리를 하나의 .jar 파일로 묶음
.jar = Java ARchive. 실행 가능한 파일 하나로 배포 가능

▼

모든 단계 통과! build/libs/에 .jar 파일 생성됨
Python과의 핵심 차이 Python은 "컴파일" 단계가 없어서 pip install + pytest로 끝나지만,
Kotlin은 소스코드 → 바이트코드 변환(컴파일)이 필수입니다.
이 컴파일 과정에서 타입 에러를 잡아주는 것이 Kotlin의 최대 장점입니다.

요약: ./gradlew build = pip install + mypy --strict + pytest + 패키징 을 한 번에.

어노테이션 (Annotation)

@로 시작하는 표시입니다. 코드의 메타데이터로, Spring에게 "이 클래스/메서드는 이런 역할이야"라고 알려줍니다.

Django와의 핵심 차이 Django는 urls.py에서 "이 URL은 이 함수가 처리해"라고 별도 파일에서 연결합니다.
Spring은 코드에 직접 @GetMapping("/health")를 붙여서 코드 자체가 라우팅 정보를 가짐. 
@RestController                          // "이 클래스는 API 엔드포인트입니다"
@RequestMapping("/api/v1/products")      // "기본 URL 경로"
class ProductController(
    private val useCase: ParseProductUseCase,  // 생성자에 넣으면 자동 주입!
) {
    @PostMapping("/parse")                  // "POST /api/v1/products/parse 를 처리"
    fun parse(
        @RequestBody request: ParseRequest,  // "요청 본문(JSON)을 이 객체로 변환"
    ): ParseResponse {
        // 비즈니스 로직 호출
        val result = useCase.execute(request.url)
        return ParseResponse.from(result)
    }
}
Django DRF 비교 
# urls.py
path('api/v1/products/parse', views.parse_product)

# views.py
@api_view(['POST'])
def parse_product(request):
    url = request.data['url']
    result = parse_use_case.execute(url)
    return Response(ParseSerializer(result).data)
Spring은 이 두 파일의 내용이 하나의 클래스에 어노테이션으로 들어갑니다.

의존성 주입 (DI) — Spring의 핵심 중 핵심

이것을 이해하면 Spring의 80%를 이해한 것입니다.

문제 상황: Django 방식 
# views.py
from parsers.og_parser import OgParser  # 구체적 구현에 직접 의존!

def parse_view(request):
    parser = OgParser()        # 직접 생성
    result = parser.parse(url)
문제: OgParser를 CoupangApiClient로 바꾸려면 이 파일을 수정해야 합니다. 테스트할 때도 진짜 OgParser를 쓰게 됩니다 (네트워크 호출 발생).
해결: Spring DI 방식 
// Controller는 인터페이스에만 의존
@RestController
class ProductController(
    private val parser: ProductParser,  // ← interface!
)
// Spring이 알아서 OgParser나 CoupangApiClient를 넣어줌
장점: 1. 구현체를 바꿔도 Controller 코드 수정 불필요
2. 테스트 시 가짜(mock) 파서를 주입 가능
3. "이 interface를 구현하는 클래스가 뭔지"는 Spring이 자동으로 찾아줌

DI가 작동하는 과정

① Spring이 프로젝트의 모든 클래스를 스캔
▼
② @Component, @Service, @RestController 가 붙은 클래스를 발견
▼
③ 각 클래스의 인스턴스를 생성하여 "컨테이너"에 보관
▼
④ 생성자에 interface 타입이 있으면 → 해당 interface를 구현한 클래스를 찾아서 주입
▼
⑤ 모든 의존성이 자동으로 연결된 상태에서 앱 시작! 🚀

이 프로젝트의 DI 체인

@RestController
ProductController
    │ 생성자에 ParseProductUseCase 필요
    ▼
@Service
ParseProductUseCase
    │ 생성자에 ParserFactory 필요
    ▼
@Component
ParserFactory
    │ 생성자에 List<ProductParser> 필요
    ▼
@Component                      @Component                   @Component
CoupangApiClient                ElevenStApiClient            OgParser
  (implements ProductParser)    (implements ProductParser)   (implements ProductParser)

→ Spring이 이 체인을 자동으로 조립합니다!

컨트롤러 상세

// JSON 요청을 받기 위한 DTO (Data Transfer Object)
data class ParseRequest(
    @field:NotBlank(message = "URL은 필수입니다")  // 유효성 검증
    val url: String,
)

// JSON 응답을 위한 DTO
data class ParseResponse(
    val name: String,
    val price: Money,
    val imageUrl: String,
    val sourceUrl: String,
    val mall: String,
    val parserUsed: String,
    val fallbackUsed: Boolean,
)
JSON 변환은 자동! Spring + Jackson(JSON 라이브러리)이 ParseRequest ↔ JSON 변환을 자동으로 합니다. Django DRF의 Serializer를 쓸 필요 없이, data class만 정의하면 끝.

캐싱

// 메서드에 @Cacheable 붙이면 끝!
@Service
class ParseProductUseCase(...) {

    @Cacheable("products", key = "#url")  // 같은 URL이면 캐시된 결과 반환
    fun execute(url: String): ParseResult {
        // 이 로직은 같은 URL에 대해 5분간 한 번만 실행됨
        val parser = parserFactory.getParser(url)
        return parser.parse(url)
    }
}
Python 비교 
# Python — 직접 캐시 로직 작성
from cachetools import TTLCache
cache = TTLCache(maxsize=100, ttl=300)

def execute(url):
    if url in cache:
        return cache[url]
    result = parser.parse(url)
    cache[url] = result
    return result
Spring에서는 @Cacheable 한 줄이면 위의 코드 전체를 대체합니다.

🔵 4. 아키텍처 패턴

이 프로젝트는 여러 아키텍처 패턴을 조합합니다. 각각이 무엇이고, 어떻게 합쳐지는지 설명합니다.

아키텍처 패턴들의 관계

이 프로젝트가 따르는 패턴들
패턴핵심 아이디어한 줄 요약
레이어드 아키텍처코드를 수평 계층으로 나눔"위에서 아래로만 호출"
클린 아키텍처의존성이 안쪽으로만 향함"비즈니스 규칙이 프레임워크를 모름"
헥사고날 아키텍처포트(규격)와 어댑터(구현체)로 분리"플러그를 갈아끼울 수 있다"
DDD비즈니스 도메인 중심으로 설계"코드가 비즈니스 언어를 쓴다"
CQS명령(변경)과 조회(읽기)를 분리"바꾸는 함수와 읽는 함수를 섞지 마라"
이것들은 서로 배타적이지 않습니다. 전부 합쳐서 하나의 구조로 만들 수 있습니다.

헥사고날 아키텍처 (Ports & Adapters)

2005년 Alistair Cockburn이 제안한 아키텍처. "포트와 어댑터"라고도 부릅니다.

핵심 아이디어

애플리케이션을 육각형(hexagon)으로 그립니다. 육각형 안에 비즈니스 로직이 있고, 바깥 세계와는 포트(port)를 통해 연결됩니다. 포트에 어떤 어댑터(adapter)를 꽂느냐에 따라 동작이 바뀝니다. 

                        [바깥 세계]

   🌐 웹 브라우저          📱 모바일 앱          ⌨️ CLI
        │                      │                    │
        ▼                      ▼                    ▼
   ┌─ Controller ──── Controller ──── CLI Handler ─┐
   │          Driving Adapters (들어오는 쪽)          │
   │   ═══════════════════════════════════════════   │
   │        ▼ Driving Port (inbound interface)        │
   │                                                 │
   │              ┌───────────────┐                  │
   │              │   Application   │  ← 비즈니스     │
   │              │   + Domain     │     로직        │
   │              └───────────────┘                  │
   │                                                 │
   │       ▼ Driven Port (outbound interface)        │
   │   ═══════════════════════════════════════════   │
   │        Driven Adapters (나가는 쪽)              │
   └─ DB Adapter ──── API Client ──── Parser ──┘
        │                   │                │
        ▼                   ▼                ▼
   🗄️ PostgreSQL     🌐 쿠팡 API      📄 HTML

                        [바깥 세계]

포트(Port)와 어댑터(Adapter)

개념비유코드에서예시
Port 콘센트 규격 interface ProductParser, ProductRepository
Driving Adapter
(들어오는 쪽)		 전자제품을 켜는 스위치 Controller, CLI ProductController — 웹에서 요청이 들어옴
Driven Adapter
(나가는 쪽)		 콘센트에 꽂는 플러그 구현체 (@Component) OgParser, CoupangApiClient — 밖으로 나감
헥사고날의 핵심 가치

"어댑터를 갈아끼울 수 있다"

지금은 OgParser(HTML 파싱)를 쓰다가, 나중에 CoupangApiClient(API 호출)로 바꿔도 비즈니스 로직은 한 줄도 바뀌지 않습니다.
지금은 Controller(웹)로 들어오지만, 나중에 CLI(터미널)나 배치 Job으로 들어와도 비즈니스 로직은 동일합니다.

테스트할 때도 "가짜 어댑터"를 꽂아서 실제 DB나 API 없이 테스트 가능합니다.

클린 아키텍처 (Clean Architecture)

2012년 Uncle Bob(Robert C. Martin)이 제안. 헥사고날과 매우 비슷하지만, 동심원 다이어그램으로 의존성 방향을 강조합니다.

동심원 — 안쪽이 더 중요하고, 안쪽은 바깥을 모른다

    ┌──────────────────────────────────────────────┐
    │  Presentation / Infrastructure               │  바깥 (프레임워크, DB, 웹)
    │    ┌──────────────────────────────────────┐   │
    │    │  Application                          │   │  중간 (유스케이스)
    │    │    ┌──────────────────────────────┐   │   │
    │    │    │  Domain                       │   │   │  안쪽 (엔티티 + 인터페이스)
    │    │    │  Entity, VO, Port(interface) │   │   │
    │    │    └──────────────────────────────┘   │   │
    │    │  UseCase, Service, DTO               │   │
    │    └──────────────────────────────────────┘   │
    │  Controller, OgParser, DB Adapter, Config     │
    └──────────────────────────────────────────────┘

    규칙: 화살표는 반드시 안쪽을 향한다 (바깥 → 안쪽)
    ✅ Presentation → Application → Domain
    ✅ Infrastructure → Domain (의존성 역전)
    ❌ Domain → Application/Infrastructure/Presentation

DDD (Domain-Driven Design)

Eric Evans가 제안. "코드가 비즈니스 언어를 쓰게 하라"는 철학입니다.

DDD에서 가져온 개념들
개념이 프로젝트에서의미
EntityProduct고유 식별자를 가진 도메인 객체
Value Object (VO)Money, Mall값으로 비교되는 불변 객체. Money(15900) == Money(15900)
RepositoryProductRepository엔티티의 저장/조회 계약 (interface)
Domain Service(필요 시 추가)특정 엔티티에 속하지 않는 도메인 로직
Ubiquitous LanguageProduct, Parse, Mall개발자와 비개발자가 같은 용어 사용

CQS (Command Query Separation)

Bertrand Meyer가 제안. "바꾸는 함수와 읽는 함수를 섞지 마라"는 원칙입니다.

Command (명령)Query (조회)
하는 일상태를 변경한다상태를 읽어서 반환한다
반환값없음 (void/Unit)있음 (데이터)
부작용있음 (DB 저장, API 호출 등)없음 (읽기만)
예시saveProduct(product)findProductByUrl(url): Product?
// ✅ CQS를 따르는 Repository interface
interface ProductRepository {
    fun save(product: Product)                  // Command: 저장 (반환 없음)
    fun findByUrl(url: String): Product?         // Query: 조회 (데이터 반환)
}

// ❌ CQS 위반 — 저장하면서 동시에 결과를 반환
fun saveAndReturn(product: Product): Product    // 변경 + 반환을 한 함수에서!
Phase 2+에서 CQS 확장 지금은 파싱(조회)만 있어서 단순하지만, Phase 2에서 장바구니 저장이 추가되면: 
// Command UseCase — 상태를 변경
class AddToCartUseCase    → save(product)

// Query UseCase — 상태를 조회
class GetCartItemsUseCase  → findAll(): List<Product>

이 패턴들이 합쳐지면?

각 패턴이 담당하는 영역
패턴결정하는 것
레이어드코드를 몇 개의 층으로 나눌지 → 4개 (Domain, Application, Infrastructure, Presentation)
클린 아키텍처의존성 방향 → 바깥에서 안쪽으로만
헥사고날경계를 어떻게 연결할지 → Port(interface) + Adapter(구현체)
DDDDomain 안에 뭘 넣을지 → Entity, VO, Repository interface
CQS함수를 어떻게 설계할지 → Command(변경)와 Query(조회) 분리

왜 레이어를 나누는가?

레이어 없이 코드를 짜면 Controller 안에 API 호출, HTML 파싱, JSON 변환, 에러 처리가 뒤섞입니다.
→ 테스트하려면 진짜 API를 호출해야 함
→ 쿠팡 파서를 바꾸면 Controller도 수정해야 함
→ 코드 500줄짜리 "갓 클래스"가 탄생
레이어를 나누면 각 레이어는 자기 책임만 집니다.
→ 파서를 바꿔도 Controller 수정 불필요 (interface로 연결)
→ 테스트 시 가짜 파서를 끼울 수 있음
→ 각 파일이 100줄 이내로 관리 가능

4개 레이어 상세

Presentation — "사용자와 만나는 곳"
Controller (URL/요청 처리), Request/Response DTO
Django의 views.py + urls.py
▼ 호출
Application — "비즈니스 로직"
UseCase (워크플로우 조합), Service (개별 비즈니스 로직)
UseCase는 여러 Service를 조합할 수 있음
▼ 사용 (interface를 통해)
Domain — "핵심 규칙 + 계약서"
Entity (data class), Value Object, Interface (계약)
"상품이란 무엇인가" + "파서는 이런 규격을 따라야 한다"
▲ 구현 (의존성 역전!)
Infrastructure — "외부 세계와 연결"
Domain의 interface를 구현하는 구현체
DB, API 호출, HTML 파싱, 캐시 등

위의 패턴들(헥사고날 + 클린 + DDD + CQS + 레이어드)을 모두 조합한 이 프로젝트의 이상적 구조입니다.

왜? interface(포트)는 "비즈니스가 요구하는 규격"입니다. "상품을 파싱할 수 있어야 한다", "상품을 저장할 수 있어야 한다"는 도메인 요구사항이지, 애플리케이션 요구사항이 아닙니다. DDD에서 Repository interface가 Domain에 위치하는 것도 같은 이유입니다.

→ PR 2에서 application/port/ → domain/port/로 이동 예정

각 패턴이 이 구조에 어떻게 반영되었는가

패턴구조에서 보이는 곳
레이어드 4개 패키지(domain/application/infrastructure/presentation)로 수평 분리
클린 아키텍처 import 방향이 항상 domain을 향함. Domain은 아무것도 import 안 함
헥사고날 domain/port/ = Port, infrastructure/adapter/ = Driven Adapter, presentation/api/ = Driving Adapter
DDD domain/entity/ = Entity, domain/vo/ = Value Object, domain/port/ProductRepository = Repository
CQS Repository interface의 save()(Command)와 findByUrl()(Query) 분리

의존성 규칙 (상세)

이것이 클린 아키텍처의 가장 중요한 규칙입니다. 코드를 잘 짜는 것보다 의존성 방향을 지키는 것이 더 중요합니다.

규칙: 안쪽 레이어는 바깥쪽을 절대 모른다

누가 누구를 알 수 있는가? (→ = "알고 있다" = import 할 수 있다)

Presentation → Application → Domain ← Infrastructure
                                       ↑
                                Infrastructure가 Domain의
                                interface를 구현 (의존성 역전)

화살표 방향 = import 방향 = 의존성 방향

✅ 허용                          ❌ 금지
Presentation → Application       Application → Infrastructure
Presentation → Domain            Domain → Application
Application → Domain             Domain → Presentation
Infrastructure → Domain          Domain → Infrastructure

구체적인 예시: "이 import가 왜 금지인가?"

✅ 올바른 의존: Application → Domain

UseCase가 Domain의 엔티티와 인터페이스를 사용합니다.

// application/usecase/ParseProductUseCase.kt
package com.linkcart.application.usecase

import com.linkcart.domain.entity.Product         // ✅ Domain 엔티티 사용 OK
import com.linkcart.domain.port.ProductParser      // ✅ Domain 인터페이스 사용 OK

@Service
class ParseProductUseCase(
    private val parser: ProductParser,  // interface! 구현체가 뭔지 모름
) {
    fun execute(url: String): Product {
        return parser.parse(url)  // interface의 메서드 호출
    }
}
핵심: UseCase는 ProductParser라는 interface(계약)만 알고 있습니다. 실제로 쿠팡 API를 호출하는지, OG 태그를 파싱하는지 전혀 모릅니다.
✅ 올바른 의존 (의존성 역전): Infrastructure → Domain

Infrastructure가 Domain에서 정의한 interface를 구현합니다.

// infrastructure/parser/OgParser.kt
package com.linkcart.infrastructure.parser

import com.linkcart.domain.port.ProductParser      // ✅ Domain 인터페이스 가져오기 OK

import org.jsoup.Jsoup                              // ✅ 외부 라이브러리 사용 OK (Infrastructure니까)

@Component
class OgParser : ProductParser {       // Domain의 interface를 구현!
    override fun parse(url: String): Product {
        val doc = Jsoup.connect(url).get()  // Jsoup은 Infrastructure에서만 사용
        // ... OG 태그 파싱 로직 ...
    }
}
핵심: OgParser는 Domain의 ProductParser interface를 구현(implements)합니다. 이것이 "의존성 역전"입니다 — 구현체(Infrastructure)가 계약(Domain)에 의존합니다.
❌ 금지: Application → Infrastructure (직접 의존)

package com.linkcart.application.usecase

class ParseProductUseCase {
    private val parser = OgParser()  // ❌ 구현체를 직접 생성!
}
왜 금지?
UseCase가 "OgParser"라는 구체적 구현에 묶여버립니다.
나중에 쿠팡 API 파서로 바꾸려면? UseCase 코드를 수정해야 합니다.
테스트하려면? 진짜 HTTP 요청이 발생합니다.
→ interface를 통해 간접적으로 사용해야 합니다.
❌ 금지: Domain → 아무 바깥 레이어

package com.linkcart.domain.entity

import org.springframework.stereotype.Component    // ❌ Domain에서 Spring import 금지!

// Domain은 순수 Kotlin만 사용. 프레임워크, 외부 라이브러리 의존 없음.
왜 금지?
Domain은 "비즈니스의 핵심 규칙"입니다.
Spring을 FastAPI로 바꿔도, Jsoup을 다른 라이브러리로 바꿔도
Domain은 한 글자도 바뀌면 안 됩니다.

의존성 역전 — 왜 필요한가?

"의존성 역전"이 어려운 이유는 실행 흐름과 의존성 방향이 반대이기 때문입니다. 

실행 흐름 (런타임에 코드가 실행되는 순서)
Controller → UseCase → OgParser → 인터넷에서 HTML 가져옴
                          ↑ 실제로 실행되는 건 OgParser

의존성 방향 (코드에서 import하는 방향)
Controller → UseCase → ProductParser (interface) ← OgParser
                          ↑ UseCase가 아는 건 interface뿐!
                                                        ↑ OgParser가 interface를 구현

핵심: 실행은 → 방향이지만, OgParser의 의존성은 ← 방향 (역전!)
비유: 콘센트와 플러그

Domain의 interface = 콘센트(규격)입니다.
"이 구멍 모양에 맞는 플러그만 꽂을 수 있어"라는 계약.

Infrastructure의 구현체 = 플러그(제품)입니다.
삼성 충전기든, LG 충전기든, 콘센트 규격만 맞으면 꽂을 수 있습니다.

Application의 UseCase = 전자제품입니다.
"전기가 필요해"라고만 말하고, 어떤 충전기가 꽂혀있는지 신경 안 씁니다.

Spring DI = 누군가 알아서 플러그를 꽂아주는 사람입니다.
OgParser를 꽂을지, CoupangApiClient를 꽂을지 Spring이 결정해서 넣어줍니다.

// UseCase = 워크플로우. 여러 Service를 조합하는 오케스트레이터
@Service
class ParseProductUseCase(
    private val parserFactory: ParserFactory,   // 파서 선택
    private val cacheService: CacheService,     // 캐시 확인
) {
    fun execute(url: String): ParseResult {
        // 1. 캐시 확인
        cacheService.get(url)?.let { return it }

        // 2. 파서 선택 + 파싱
        val parser = parserFactory.getParser(url)
        val result = parser.parse(url)

        // 3. 캐시 저장
        cacheService.put(url, result)
        return result
    }
}

// Service = 개별 비즈니스 로직 단위. UseCase에 의해 조합됨
// 예: 가격 비교 Service, 알림 Service 등 (Phase 2+에서 추가 가능)

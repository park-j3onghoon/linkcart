# 티니어 Back-end 지원용 준비 시험지

대상 공고:

- `[글로벌 앱 플랫폼] 유틸리티 앱 Back-end 개발자`
- `[글로벌 앱 플랫폼] 날씨 앱 Back-end 개발자`

이 시험지는 단순 Kotlin 문법 확인용이 아니다.
티니어 공고에서 반복해서 요구하는 아래 역량을 기준으로 만들었다.

- Kotlin/Java + Spring 기반 서버 개발
- 안정적인 운영과 장애 대응
- 글로벌 멀티 플랫폼 API 설계
- AWS/로그/모니터링/알림에 대한 운영 관점
- RDBMS/NoSQL 데이터 모델링
- 테스트, 코드 리뷰, 협업
- 작게 만들고 빨리 검증하는 실행 방식

또한 현재 이력서의 강점을 그대로 살릴 수 있게 구성했다.

- 외부 API 장애 격리
- 대용량 처리 성능 개선
- DB 모델 일반화/확장성 개선
- IaC/운영 환경 안정화
- 비동기 처리로 핵심 흐름 보호

## 먼저 짚고 가야 할 포인트

현재 이력서로도 티니어 공고와 겹치는 부분이 꽤 많다.
다만 약점은 명확하다.

- `Kotlin/Spring을 실무에서 얼마나 운영해봤는가`는 아직 약하다
- `NoSQL`, `CI/CD`, `모니터링/알림`은 이력서에서 더 구체적으로 말해야 한다
- `멀티 플랫폼 API 설계`는 경험을 재해석해서 말해야 한다

즉, 준비 방향은 이렇다.

1. 이미 있는 Python/Django 실무 강점을 버리지 않는다
2. 그 강점을 Kotlin/Spring 문법과 구조로 번역한다
3. Linkcart를 티니어가 좋아할 만한 방향으로 진화시킨다

---

## 응시 방식

- 권장 시간: 90분
- 총점: 100점
- 답안은 채팅으로 번호별로 보내면 된다
- 내가 채점할 때는
  - 점수
  - 강점
  - 취약점
  - 이력서 수정 포인트
  - Linkcart 다음 구현 과제
  를 같이 정리해준다

## A. 공고 해석력 (각 4점, 총 20점)

### 1.
티니어 공고에서 두 포지션 모두 공통으로 가장 강하게 보는 역량 3가지를 적어라.

### 2.
공고의 `24시간 365일 장애 없는 환경`이라는 표현을, 백엔드 개발 관점에서 3가지 실천 항목으로 바꿔 적어라.

### 3.
`글로벌 멀티 플랫폼 지원`이 단순히 API 하나 만들면 끝나는 일이 아닌 이유를 설명하라.

### 4.
`빠른 실험, 빠른 실패`를 백엔드 개발자가 실제 행동으로 옮기면 어떤 식이어야 하는지 3~4문장으로 적어라.

### 5.
유틸리티 앱 백엔드와 날씨 앱 백엔드 중, 현재 본인 이력서에 더 유리한 포지션이 어느 쪽인지 고르고 이유를 적어라.

---

## B. 이력서 연결형 (각 6점, 총 30점)

### 6.
다음 경험 중 티니어 공고의 `장애 대응 / 안정성`과 가장 직접적으로 연결되는 사례 하나를 고르고, 아래 형식으로 5~7문장으로 답하라.

- 상황
- 문제
- 내가 한 판단
- 구현
- 결과
- 재발 방지 관점

후보:

- 외부 결제 API 지연 fail-fast 개선
- 슬랙 알림 비동기 처리 전환
- 테스트 환경 백업 DB 로직 개선

### 7.
`N+1 해결 + 5시간 → 15분 단축` 경험을 티니어 공고의 `대규모 트래픽 / 성능 최적화`와 연결해서 설명하라.
중요한 것은 “배치 작업 개선”을 “서비스 운영 관점의 성능 개선”으로 번역하는 것이다.

### 8.
버즈빌에서 한 `강결합된 DB 모델을 범용 구조로 재설계`한 경험을, 티니어 공고의 `확장성 있는 웹 아키텍처`와 연결해 5~6문장으로 설명하라.

### 9.
현재 이력서에서 약하게 보이는 항목 3개를 적고, 각각 어떻게 보완할지 적어라.
힌트:

- Kotlin/Spring 운영 경험
- NoSQL
- CI/CD
- 모니터링/알림
- 글로벌 서비스 API 설계

### 10.
면접에서 `왜 Python 기반 경력인데 Kotlin/Spring 회사로 오고 싶냐`고 물으면 어떻게 답할지 4~6문장으로 적어라.

---

## C. Kotlin/Spring 실전형 (각 5점, 총 20점)

### 11.
Spring Boot에서 `@RestController`, `@Service`, `@Configuration`의 역할 차이를 설명하라.

### 12.
Kotlin의 `data class`, `enum class`, `sealed class/interface`를 Linkcart 기준 예시와 함께 설명하라.

### 13.
`interface ProductRepository`를 두고 구현체를 나중에 붙이는 방식이 왜 좋은지 설명하라.
가능하면 Django ORM에 익숙한 사람의 시각에서 비교하라.

### 14.
티니어처럼 모바일 앱 백엔드를 운영할 때, 단순 CRUD API보다 `클라이언트를 고려한 API 설계`가 중요한 이유를 적어라.

### 15.
Spring Boot에서 캐시를 붙일 때 고려해야 할 것 4가지를 적어라.
예: TTL, key, stale data, invalidation 같은 것.

---

## D. 시스템 설계형 (각 10점, 총 20점)

### 16.
Linkcart가 성장해서 `상품 링크 파싱 API`에 트래픽이 몰린다고 가정하자.
아래 항목을 포함해서 간단히 설계하라.

- 어디에 캐시를 둘지
- 외부 쇼핑몰/API 장애를 어떻게 격리할지
- 응답 속도와 정확도 사이에서 어떤 타협을 할지
- 로그/모니터링은 무엇을 볼지

### 17.
티니어의 날씨 앱 백엔드라고 가정하자.
전 세계 사용자가 10분마다 날씨 데이터를 조회할 때, 아래 항목을 포함해 설계 방향을 설명하라.

- 지역별 데이터 특성
- 캐시 전략
- 장애 시 fallback
- 모바일 클라이언트를 위한 응답 최적화

## E. 면접 답변형 (각 5점, 총 10점)

### 18.
`코드 리뷰를 어떻게 받아들이고, 어떻게 남기는 편인가요?`에 대한 답변을 4~6문장으로 적어라.

### 19.
`빠르게 만들다 보면 품질이 떨어질 수 있는데, 어떻게 균형을 잡나요?`에 대한 답변을 4~6문장으로 적어라.

## F. Linkcart 액션 과제 (선택, 20점)

아래 셋 중 하나를 골라, 실제 구현 계획을 6~10문장으로 적어라.
이건 시험이면서 동시에 포트폴리오 설계다.

### 20-A. 캐시 + 장애 격리

Linkcart의 상품 파싱 API에

- Caffeine TTL 캐시
- 외부 요청 timeout
- fallback result
- 실패 사유 로깅

을 넣는 설계를 적어라.

### 20-B. 운영 관측성

Linkcart에 아래를 추가한다고 가정하고 설계를 적어라.

- 요청 ID
- 구조화 로그
- 에러 알림 기준
- 핵심 메트릭

### 20-C. 멀티 플랫폼 API

웹/모바일이 같은 API를 쓰되, 클라이언트별 요구가 조금 다르다고 가정하자.

- API를 하나로 유지할지
- 버전 관리를 어떻게 할지
- 응답 필드 설계를 어떻게 할지
- shared package와 OpenAPI를 어떻게 활용할지

## 채점 기준

### 90점 이상

지원 준비를 시작해도 된다.
이 단계에서는 Kotlin/Spring 실무 문법만 더 보강하면 된다.

### 75~89점

서류는 가능성이 있다.
다만 기술 과제나 면접에서 Kotlin/Spring 운영 경험 질문이 들어오면 흔들릴 수 있다.

### 60~74점

실무 강점은 좋지만, 티니어의 언어와 운영 맥락으로 번역하는 힘이 약하다.
Linkcart를 공고 맞춤형으로 더 다듬어야 한다.

### 59점 이하

아직은 공고 해석과 본인 경험 연결이 분리되어 있다.
시험보다 먼저 이력서 문장과 프로젝트 방향을 다시 맞추는 게 낫다.

## 이 시험 뒤에 바로 해야 할 것

1. 답안을 제출한다
2. 채점 결과를 바탕으로 이력서 문장을 티니어용으로 고친다
3. Linkcart에 티니어 공고와 직접 연결되는 기능 2~3개를 실제로 넣는다

추천 기능:

- 외부 API timeout + fallback + 구조화 로그
- 캐시 + OpenAPI + API 문서화
- 간단한 대시보드용 백오피스 API
- AWS 배포 구성 문서
- 테스트 코드와 장애 대응 시나리오 문서

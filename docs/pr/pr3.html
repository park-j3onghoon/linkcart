PR 3

전용 API 파서와 OG 폴백 체인

이번 PR의 핵심은 "쇼핑몰마다 더 정확한 정보원을 먼저 시도하고, 실패하면 범용 OG 파서로 안전하게 내려온다"는 흐름을 백엔드에 고정하는 것이다. 그래서 쿠팡과 11번가는 전용 API 클라이언트를 두고, 그 외 URL이나 전용 API 실패는 OgParser가 받는다.

URL 입력 -> ParserFactory가 도메인 보고 전용 파서 선택 -> 전용 API 시도 -> 실패하면 OgParser로 fallback -> Success / Partial / Failure 반환

왜 이렇게 나누나

전용 API

가격, 재고 상태처럼 쇼핑몰이 공식으로 주는 값은 HTML보다 신뢰도가 높다. 따라서 지원몰은 API를 먼저 본다.

OG 파서

지원하지 않는 몰도 받아야 하므로 범용 폴백이 필요하다. OG 태그는 완전하지 않아도 최소한의 제목/이미지를 얻을 수 있다.

UseCase의 역할

파서 구현체 안에 분기 로직을 흩뿌리지 않고, ParseProductUseCase가 "시도 -> 실패 시 재시도" 정책을 소유한다.

쿠팡 클라이언트에서 중요한 점

쿠팡은 단순 API 키가 아니라 HMAC 서명 기반 인증을 쓴다. 그래서 access key, secret key, 요청 경로, 시각을 합쳐 Authorization 헤더를 만들어야 한다. 

linkcart:
  coupang:
    access-key: ${LINKCART_COUPANG_ACCESS_KEY:}
    secret-key: ${LINKCART_COUPANG_SECRET_KEY:}

이 구조의 장점은 시크릿이 코드에 박히지 않는다는 점이다. 로컬, 스테이징, 운영이 같은 코드로 가고, 환경변수만 다르게 주입하면 된다.

Fallback Chain 패턴

전용 파서가 실패했다고 해서 요청 전체를 즉시 실패시키면, 외부 API 장애가 곧 사용자 장애가 된다. 그래서 ParseProductUseCase는 전용 파서 실패를 감지하면 OG 파서를 한 번 더 시도한다. 

@Cacheable(
    cacheNames = ["products"],
    key = "#url",
    unless = "#result instanceof T(com.linkcart.domain.model.ParseResult$Failure)",
)
fun execute(url: String): ParseResult

실패 결과는 캐시하지 않는 것도 중요하다. 외부 API가 잠깐 흔들렸을 때 실패를 오래 보관하면, 실제 복구 뒤에도 계속 실패를 재사용하게 되기 때문이다.

ParserFactory를 application 레이어로 옮긴 이유

파서를 실제로 고르는 판단은 "이 유스케이스에서 어떤 전략을 먼저 쓸 것인가"에 가깝다. 그래서 ParseProductUseCase가 infrastructure 구현체에 직접 의존하지 않도록, ParserFactory를 application 레이어로 올려 의존성 방향을 바로잡았다.

테스트가 검증하는 것

  • CoupangApiClientTest: HMAC 헤더 생성, 정상 응답, HTTP 오류, 타임아웃, 삭제/품절 상품 처리
  • ElevenStApiClientTest: XML 응답 파싱, 오류 응답, 상품 없음 처리
  • ParseProductUseCaseTest: 전용 성공, OG 폴백 성공, Partial, 전체 실패, 타임아웃
  • ParseProductUseCaseCachingTest: 성공 결과 캐시, 실패 결과 비캐시

여기서 핵심은 프레임워크 자체를 테스트하지 않고, 우리가 추가한 정책과 분기만 검증한다는 점이다.

PR 4

상품 파싱 API와 이미지 프록시

이번 PR의 목적은 PR 3에서 만든 파싱 로직을 실제 HTTP API로 꺼내는 것이다. 백엔드 안쪽에서는 ParseProductUseCase가 이미 동작하고 있었고, PR 4에서는 그 결과를 프론트엔드가 바로 호출할 수 있는 JSON 응답으로 바꾸는 presentation 레이어를 추가했다.

POST /api/v1/products/parse -> ParseRequest 검증 -> ParseProductUseCase 실행 -> Success / Partial 은 ParseResponse -> Failure 는 502 ErrorResponse GET /api/v1/images/proxy -> URL 검증 + SSRF 차단 -> 외부 이미지 fetch -> image/* 만 전달

왜 DTO를 따로 두나

도메인과 API 계약 분리

도메인의 Product, ParseResult는 내부 계산 모델이다. 반면 API는 snake_case, 에러 코드, nullable 필드 같은 외부 계약이 필요하다. 그래서 presentation DTO를 따로 둔다.

Partial 응답 처리

OG 폴백은 일부 필드만 얻을 수 있으므로, 응답 DTO는 top-level 필드를 nullable로 열고 partial 맵으로 어떤 값이 채워졌는지도 함께 보낸다.

@Valid와 전역 예외 처리

요청이 잘못됐을 때 각 컨트롤러마다 try/catch를 반복하면, 에러 포맷이 조금씩 달라진다. 그래서 검증 실패, 잘못된 요청 본문, upstream 오류를 GlobalExceptionHandler에서 한 번에 모아 ErrorResponse(code, message) 형태로 통일했다. 

data class ParseRequest(
    @field:NotBlank
    @field:Pattern(regexp = "^https?://.+")
    val url: String,
)

이미지 프록시가 왜 필요한가

OG 이미지 주소를 프론트가 직접 열면 CORS, 핫링크, 차단 정책 문제를 만날 수 있다. 그래서 백엔드가 한 번 받아서 전달하는 프록시 엔드포인트를 만든다.

다만 이 패턴은 SSRF(Server-Side Request Forgery) 위험이 바로 따라온다. 사용자가 임의 URL을 넣을 수 있기 때문이다. 그래서 SafeUrlChecker로 loopback, 사설망, link-local 주소를 막고, 응답도 image/* 타입일 때만 전달한다.

MockMvc 테스트가 검증하는 것

  • ProductControllerTest: 정상 파싱, 빈 URL, 잘못된 URL, 파싱 실패, partial 응답의 snake_case 필드
  • ImageProxyControllerTest: 정상 이미지 프록시, 빈 URL, unsafe URL, upstream fetch 실패, non-image 응답

여기서는 실제 네트워크를 열지 않고 controller contract만 본다. 그래서 프론트엔드가 붙을 때 어떤 JSON과 status code를 받는지가 명확해진다.

무엇을 했는가

왜 했는가

프로젝트를 시작하려면 뼈대(scaffold)가 필요합니다. Django에서 django-admin startproject를 실행하듯이, 각 기술 스택의 초기 구조를 잡아야 합니다. 이 PR은 말 그대로 "빈 집을 짓고, 방을 나누고, 기둥을 세운 것"입니다. 아직 실제 기능은 없지만, 이 뼈대 위에 모든 기능이 올라갑니다.

1. 모노레포 구조

Turborepo란

보통 프로젝트는 하나의 저장소 = 하나의 앱입니다. 하지만 LinkCart는 웹, 모바일, 백엔드, 공유 코드까지 4개의 프로젝트가 있습니다. 이것들을 각각 별도 Git 저장소로 관리하면:

  • 타입을 고치면 3개 저장소를 다 고쳐야 합니다
  • 공유 코드 버전 맞추기가 지옥입니다
  • PR 하나로 프론트+백엔드를 동시에 바꿀 수 없습니다

모노레포(monorepo)는 이 모든 프로젝트를 하나의 Git 저장소에 넣는 방식입니다. Turborepo는 모노레포를 효율적으로 관리해주는 도구입니다.

Django와 비교 Django 프로젝트 안에 여러 앱(users, products, orders)이 있듯이, 모노레포 안에 여러 프로젝트(web, mobile, backend)가 있습니다. 차이점은 Django 앱들은 같은 Python 프로젝트지만, 모노레포의 프로젝트들은 완전히 다른 언어/프레임워크일 수 있습니다.

왜 모노레포인가

모노레포의 핵심 장점 3가지
↓
타입/인터페이스를
한 곳에서 정의
프론트/백엔드 동기화
하나의 PR로
프론트+백엔드
동시 변경 가능
공유 패키지를
npm publish 없이
바로 참조

package.json 해부

루트 package.json은 모노레포의 "총괄 설정"입니다. 개별 앱의 package.json이 아닙니다.

{
  "name": "linkcart",              // 프로젝트 이름
  "private": true,                // npm에 공개하지 않는다는 뜻. 회사 프로젝트니까 true
  "workspaces": [
    "apps/*",                     // apps/ 아래의 모든 폴더를 "워크스페이스"로 등록
    "packages/*"                  // packages/ 아래도 마찬가지
  ],
  "scripts": {
    "build": "turbo run build",    // 모든 워크스페이스의 build를 실행 (turbo가 병렬+캐시 관리)
    "dev": "turbo run dev",        // 모든 워크스페이스의 dev 서버를 동시에 실행
    "lint": "turbo run lint",      // 전체 린트 (코드 스타일 검사)
    "test": "turbo run test",      // 전체 테스트
    "codegen": "turbo run codegen" // OpenAPI에서 타입 자동 생성
  },
  "devDependencies": {
    "turbo": "^2"                  // Turborepo 자체를 개발 의존성으로 설치
  },
  "packageManager": "npm@11.11.1"  // 팀원 모두 같은 npm 버전 사용을 강제
}
workspaces가 하는 일 "workspaces": ["apps/*", "packages/*"]라고 쓰면, npm은 apps/web, apps/mobile, packages/shared를 각각 독립된 패키지로 인식합니다. 그러면서도 npm install 한 번이면 전부 설치됩니다. Python으로 비유하면 pip install -e ./apps/web ./apps/mobile ./packages/shared를 한꺼번에 하는 것과 비슷합니다.

turbo.json 해부

turbo.json은 Turborepo에게 "각 태스크를 어떻게 실행할지" 알려주는 설정 파일입니다.

{
  "$schema": "https://turbo.build/schema.json",  // IDE 자동완성용 스키마
  "tasks": {

    "build": {
      "dependsOn": ["^build"],     // ^는 "의존하는 패키지의 build를 먼저 실행"
                                    // 예: web이 shared에 의존하면, shared build → web build 순서
      "outputs": [".next/**", "!.next/cache/**", "dist/**"]
                                    // 빌드 결과물 경로. turbo가 이걸 캐시해서 다음에 안 바뀌면 스킵
    },

    "dev": {
      "cache": false,              // 개발 서버는 캐시하면 안 됨 (항상 새로 실행)
      "persistent": true           // dev 서버는 종료하지 않고 계속 실행 (watch 모드)
    },

    "lint": {
      "dependsOn": ["^build"]      // 린트 전에 의존 패키지를 먼저 빌드
                                    // (타입 체크를 위해 .d.ts가 필요하므로)
    },

    "test": {
      "dependsOn": ["^build"]      // 테스트도 마찬가지
    },

    "codegen": {
      "cache": false               // 코드 자동 생성은 항상 새로 실행 (서버 스펙이 바뀌었을 수 있으니)
    }
  }
}
Django와 비교: dependsOn Django에서는 앱 간 의존성을 INSTALLED_APPS 순서로 관리합니다. Turborepo는 dependsOn: ["^build"]로 "이 패키지가 의존하는 패키지를 먼저 빌드해라"를 명시합니다. ^는 "상위 의존성(upstream)"을 의미합니다. 예를 들어 web이 shared를 사용하면, shared의 build가 먼저 끝난 후 web의 build가 시작됩니다.

2. Spring Boot 프로젝트 구조

build.gradle.kts 해부

Django에서 requirements.txt로 라이브러리를 관리하듯, Spring Boot는 build.gradle.kts로 관리합니다. 다만 Gradle은 "빌드 도구"이기 때문에 의존성 관리 외에 컴파일, 테스트, 패키징까지 전부 담당합니다.

Django와 비교: build.gradle.kts의 정체 build.gradle.kts는 Python 세계의 requirements.txt + setup.py + Makefile을 하나로 합친 것입니다. .kts는 "Kotlin Script"라는 뜻으로, 이 파일 자체가 Kotlin 코드입니다 (단순 텍스트 파일이 아님).

플러그인 블록 (상단)

plugins {
    kotlin("jvm") version "1.9.25"
    kotlin("plugin.spring") version "1.9.25"
    id("org.springframework.boot") version "3.5.3"
    id("io.spring.dependency-management") version "1.1.7"
}
플러그인하는 일Python 비유
kotlin("jvm") Kotlin 코드를 JVM 바이트코드로 컴파일 Python은 인터프리터가 알아서 하지만, Kotlin은 컴파일이 필요
kotlin("plugin.spring") Kotlin 클래스에 자동으로 open 키워드를 추가. Spring이 프록시를 만들 수 있게 해줌 Python은 모든 클래스가 기본적으로 상속 가능하지만, Kotlin은 기본이 final(상속 불가)이라 이 플러그인이 열어줌
org.springframework.boot Spring Boot의 빌드 기능: 실행 가능한 JAR 생성, 버전 관리 등 gunicorn + setuptools의 역할
io.spring.dependency-management Spring Boot가 권장하는 라이브러리 버전을 자동으로 맞춰줌 (BOM) pip-compile이 의존성 버전을 맞춰주는 것과 비슷

프로젝트 메타데이터

group = "com.linkcart"         // Java 세계의 패키지 네이밍 규칙: 도메인 역순
                                // Python의 패키지 이름과 같은 역할
version = "0.0.1-SNAPSHOT"    // SNAPSHOT = 아직 개발 중인 버전이라는 뜻

Java 툴체인

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)   // JDK 21 사용
    }
}
JDK 21을 쓰는 이유 JDK 21은 LTS(Long Term Support) 버전입니다. Python 3.12 같은 안정 버전이라고 보면 됩니다. Kotlin은 JVM 위에서 돌아가기 때문에 JDK가 필요합니다. Django 프로젝트에서 Python 3.12를 지정하는 것과 같은 맥락입니다.

저장소 (repositories)

repositories {
    mavenCentral()   // Java/Kotlin 패키지의 PyPI 같은 곳
                     // Python: pip install X → PyPI에서 가져옴
                     // Kotlin: mavenCentral()에서 가져옴
}

의존성 블록 (핵심!)

dependencies {
    // --- 런타임 의존성 (implementation = pip install X) ---

    implementation("org.springframework.boot:spring-boot-starter-cache")
    // 캐싱 기능. Django의 django.core.cache에 해당

    implementation("org.springframework.boot:spring-boot-starter-validation")
    // 입력값 검증. Django의 Form/Serializer validation에 해당

    implementation("org.springframework.boot:spring-boot-starter-web")
    // 웹 서버 + REST API. Django 자체에 해당 (내장 서버 + URL 라우팅 + 요청/응답 처리)

    implementation("com.fasterxml.jackson.module:jackson-module-kotlin")
    // JSON 직렬화. Django의 json.dumps() 또는 DRF Serializer에 해당
    // Jackson은 Java/Kotlin 세계의 표준 JSON 라이브러리

    implementation("org.jetbrains.kotlin:kotlin-reflect")
    // Kotlin 리플렉션. Spring이 런타임에 클래스 정보를 읽을 때 필요
    // Python은 기본 내장이지만, Kotlin은 별도 라이브러리

    implementation("org.jsoup:jsoup:1.18.3")
    // HTML 파싱. Python의 BeautifulSoup에 해당
    // 상품 페이지의 OG 태그를 파싱할 때 사용 (폴백용)

    implementation("com.github.ben-manes.caffeine:caffeine:3.1.8")
    // 고성능 인메모리 캐시. Django의 LocMemCache보다 훨씬 좋은 것
    // TTL(만료 시간), 최대 크기 제한 등 지원

    implementation("org.springdoc:springdoc-openapi-starter-webmvc-ui:2.8.6")
    // API 문서 자동 생성 (Swagger UI). DRF의 drf-spectacular에 해당
    // /docs로 접속하면 Swagger UI가 뜸

    // --- 테스트 전용 의존성 ---

    testImplementation("org.springframework.boot:spring-boot-starter-test")
    // 테스트 프레임워크. Django의 django.test + pytest에 해당

    testImplementation("org.jetbrains.kotlin:kotlin-test-junit5")
    // Kotlin 테스트 유틸 + JUnit 5. pytest와 비슷한 역할

    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
    // 테스트 실행기. pytest 자체가 실행기인 것처럼, JUnit에도 실행기가 필요
}
implementation vs testImplementation
  • implementation: 실제 서비스 코드에서 사용. Python의 pip install X
  • testImplementation: 테스트 코드에서만 사용. Python의 pip install pytest (dev dependencies)
  • testRuntimeOnly: 테스트 실행할 때만 필요하고, 코드에서 직접 import하지 않음

Kotlin 컴파일러 옵션

kotlin {
    compilerOptions {
        freeCompilerArgs.addAll("-Xjsr305=strict")
        // null 안전성을 엄격하게 체크하라는 옵션
        // Java 라이브러리의 @Nullable/@NonNull 어노테이션을 Kotlin이 존중하게 함
        // Python의 mypy --strict와 비슷한 느낌
    }
}

테스트 프레임워크 설정

tasks.withType<Test> {
    useJUnitPlatform()   // JUnit 5를 테스트 프레임워크로 사용
                         // Django의 pytest.ini에서 pytest를 지정하는 것과 같음
}

application.yml 해부

Spring Boot의 설정 파일입니다. Django의 settings.py에 해당합니다. 단, Python 코드가 아니라 YAML 형식입니다.

spring:
  application:
    name: linkcart-backend      # 앱 이름. 로그에 표시됨

  jackson:
    property-naming-strategy: SNAKE_CASE
    # JSON 응답의 필드명을 snake_case로 변환
    # Kotlin: imageUrl → JSON: image_url
    # Django DRF는 기본이 snake_case지만, Spring은 기본이 camelCase라서 이 설정이 필요

  cache:
    type: caffeine              # 캐시 백엔드로 Caffeine 사용
    caffeine:
      spec: maximumSize=100,expireAfterWrite=300s
      # 최대 100개 항목, 쓴 후 5분(300초) 뒤에 만료
      # Django의 CACHES 설정에 해당:
      # CACHES = {'default': {'BACKEND': 'django.core.cache.backends.locmem.LocMemCache',
      #                       'TIMEOUT': 300, 'OPTIONS': {'MAX_ENTRIES': 100}}}

server:
  port: 8080                   # 서버 포트. Django의 manage.py runserver 8080과 같음

springdoc:
  api-docs:
    path: /openapi.json        # OpenAPI 스펙 JSON이 생성되는 경로
                               # shared 패키지의 codegen이 이 URL에서 스펙을 가져감
  swagger-ui:
    path: /docs                # Swagger UI 경로. 브라우저에서 http://localhost:8080/docs
                               # DRF의 /api/docs/ (drf-spectacular)와 같은 역할
Django settings.py vs application.yml Django의 settings.py는 Python 코드라서 로직을 넣을 수 있지만, Spring의 application.yml은 순수 데이터입니다. 조건부 로직이 필요하면 별도 @Configuration 클래스를 만듭니다 (이 PR의 WebConfig.kt처럼).

진입점 (main)

Spring Boot 앱의 시작 지점입니다. Django의 manage.py + wsgi.py에 해당합니다.

package com.linkcart               // Python의 from com.linkcart import ...와 비슷한 패키지 선언

import org.springframework.boot.autoconfigure.SpringBootApplication
import org.springframework.boot.runApplication

@SpringBootApplication             // "이 클래스가 Spring Boot 앱의 시작점이다"
                                    // 이 하나의 어노테이션이 아래 3가지를 한꺼번에 활성화:
                                    // 1. @Configuration: 설정 클래스로 등록
                                    // 2. @EnableAutoConfiguration: 의존성에 맞게 자동 설정
                                    // 3. @ComponentScan: 같은 패키지 하위의 모든 컴포넌트를 자동 등록
class LinkcartBackendApplication    // 클래스 본문이 비어있어도 됨. 어노테이션이 일을 함

fun main(args: Array<String>) {      // Kotlin의 main 함수 (프로그램 진입점)
    runApplication<LinkcartBackendApplication>(*args)
                                    // Spring Boot 서버를 시작
                                    // Django: python manage.py runserver
}
Django와 비교: 자동 설정(Auto Configuration) Django는 settings.py에 INSTALLED_APPS를 직접 나열해야 합니다. Spring Boot의 @SpringBootApplication은 classpath에 있는 라이브러리를 보고 자동으로 설정합니다. 예: spring-boot-starter-web이 의존성에 있으면 자동으로 웹 서버가 켜지고, caffeine이 있으면 자동으로 캐시가 설정됩니다. "Convention over Configuration"의 극치입니다.

3. 클린 아키텍처

왜 이렇게 나누는가

Django 프로젝트의 전형적인 구조를 떠올려보세요:

# Django의 전형적 구조
products/
  models.py      # DB 모델 + 비즈니스 로직이 섞여있음
  views.py       # HTTP 처리 + 비즈니스 로직이 섞여있음
  serializers.py # 직렬화 + 검증이 섞여있음
  urls.py

이 구조의 문제: 모든 것이 Django에 묶여있습니다. DB를 바꾸면 models.py와 views.py를 다 고쳐야 하고, 테스트할 때도 DB가 필요합니다.

클린 아키텍처는 이렇게 바꿉니다: "비즈니스 로직은 프레임워크를 모르게 하자."

4개 레이어

Presentation (표현 계층)
HTTP 요청/응답 처리. Django의 views.py + urls.py
presentation/api/ — HealthController
↓ 호출
Application (응용 계층)
"무엇을 할 것인가" 정의. 유스케이스 + 인터페이스(포트)
application/port/ — ProductParser, ProductRepository
application/dto/ — ParseResult
↓ 구현
Infrastructure (인프라 계층)
"어떻게 할 것인가" 구현. 외부 연동의 실체
infrastructure/config/ — WebConfig (CORS)
infrastructure/parser/, client/, cache/ — 아직 비어있음 (Phase 2~)
↓ 사용
Domain (도메인 계층)
핵심 비즈니스 개념. 프레임워크에 의존하지 않는 순수 Kotlin
domain/entity/ — Product
domain/vo/ — Money, Mall
레이어역할Django 비유이 PR의 파일
Presentation HTTP 요청을 받고 응답을 돌려줌 views.py + urls.py HealthController.kt
Application 유스케이스 정의 + 외부 시스템 인터페이스 services.py (비즈니스 로직 분리한 경우) ProductParser.kt, ProductRepository.kt, ParseResult.kt
Infrastructure DB, 외부 API 등 구체적 기술 구현 models.py (ORM), 외부 API 클라이언트 WebConfig.kt
Domain 비즈니스 핵심 개념. 프레임워크 무관 Django에는 해당 레이어가 없음 (models.py에 다 넣음) Product.kt, Money.kt, Mall.kt

의존성 규칙

핵심 규칙: 안쪽은 바깥쪽을 몰라야 한다
  • Domain은 아무것도 import하지 않음 (순수 Kotlin)
  • Application은 Domain만 import (Spring을 모름)
  • Infrastructure는 Application의 인터페이스를 구현 (Spring 사용 가능)
  • Presentation은 Application을 호출 (Spring 어노테이션 사용)
Django와 비교: 왜 Django에는 이런 구조가 없는가 Django의 ORM(models.py)은 비즈니스 모델과 DB 스키마가 하나로 결합되어 있습니다. Product를 정의하면 그게 곧 DB 테이블입니다. 이건 편리하지만, "DB를 바꾸면 비즈니스 로직도 고쳐야 하는" 커플링이 생깁니다. 클린 아키텍처에서는 Product(Domain)와 "Product를 DB에 저장하는 방법"(Infrastructure)을 분리합니다.

4. Domain 코드

Domain 레이어는 프로젝트의 핵심 비즈니스 개념을 정의합니다. Spring, DB, HTTP 같은 외부 기술에 일절 의존하지 않는 순수 Kotlin 코드입니다.

Product (엔티티)

파일: domain/entity/Product.kt

package com.linkcart.domain.entity   // 이 파일이 속한 패키지 (Python의 모듈 경로)

import com.linkcart.domain.vo.Mall   // 같은 domain 레이어의 Mall을 가져옴
import com.linkcart.domain.vo.Money   // 같은 domain 레이어의 Money를 가져옴

data class Product(                   // data class = Python의 @dataclass
    val name: String,                  // val = 읽기 전용 (Python의 Final 힌트)
    val price: Money,                  // 가격은 단순 숫자가 아니라 Money 타입 (값 객체)
    val imageUrl: String,              // 상품 이미지 URL
    val sourceUrl: String,             // 원본 상품 페이지 URL
    val mall: Mall,                    // 어느 쇼핑몰인지 (enum)
)
Python @dataclass와 비교 
# Python 등가 코드
from dataclasses import dataclass

@dataclass(frozen=True)  # frozen=True가 Kotlin val과 같은 효과 (불변)
class Product:
    name: str
    price: Money
    image_url: str
    source_url: str
    mall: Mall
data class가 자동으로 만들어주는 것 Kotlin의 data class는 선언만 하면 아래를 전부 자동 생성합니다:
  • equals(): 값이 같으면 같은 객체로 취급 (Python의 __eq__)
  • hashCode(): 해시값 자동 계산 (Python의 __hash__)
  • toString(): 예쁜 출력 (Python의 __repr__)
  • copy(): 일부 필드만 바꿔서 복사 (Python의 dataclasses.replace())
Python의 @dataclass와 거의 동일합니다.

Money (Value Object)

파일: domain/vo/Money.kt

package com.linkcart.domain.vo

data class Money(
    val amount: Long,               // 금액. Long = 64비트 정수 (Python의 int와 비슷하지만 범위 한정)
    val currency: String = "KRW",  // 통화. 기본값 "KRW" (한국 원)
)
Value Object(VO)란? 값으로 비교하는 객체입니다. 1000원짜리 Money 두 개는 같은 객체입니다 (누가 만들었든 상관없음). 반대로 Entity는 ID로 비교합니다 (같은 이름의 상품이라도 ID가 다르면 다른 상품).

"왜 그냥 Int 대신 Money 클래스를 만들었나?" — 나중에 amount가 의미하는 게 "원"인지 "달러"인지 헷갈리지 않도록, currency를 항상 함께 묶어서 다니게 하려는 것입니다. price = 1000보다 price = Money(1000, "KRW")가 의미가 명확합니다.
Python 등가 코드 
@dataclass(frozen=True)
class Money:
    amount: int                 # Python의 int는 크기 제한 없음
    currency: str = "KRW"

val vs var

Kotlin의미Python 비유
val한 번 정해지면 변경 불가 (immutable)Final[str] 타입 힌트. 또는 frozen=True dataclass
var나중에 바꿀 수 있음 (mutable)일반 변수

Domain의 모든 필드가 val인 이유: 불변 객체가 더 안전합니다. 값을 바꾸고 싶으면 기존 객체를 수정하는 게 아니라 copy()로 새 객체를 만듭니다.

Mall (enum)

파일: domain/vo/Mall.kt

package com.linkcart.domain.vo

enum class Mall(val displayName: String) {  // enum 생성자에 프로퍼티를 줄 수 있음
    COUPANG("쿠팡"),                         // 각 상수가 displayName을 가짐
    ELEVENST("11번가"),
    GENERIC("기타"),
}
Python 등가 코드 
from enum import Enum

class Mall(Enum):
    COUPANG = "쿠팡"
    ELEVENST = "11번가"
    GENERIC = "기타"

# 사용: Mall.COUPANG.value → "쿠팡"
# Kotlin: Mall.COUPANG.displayName → "쿠팡"
Kotlin의 enum은 Python과 거의 같지만, 프로퍼티와 메서드를 가질 수 있어서 더 강력합니다. Python에서는 .value로 접근하지만, Kotlin에서는 원하는 이름(.displayName)을 줄 수 있습니다.

5. Application 코드

Application 레이어는 "무엇을 해야 하는지"를 정의합니다. 하지만 "어떻게 하는지"는 정의하지 않습니다. "상품을 파싱해라"라는 인터페이스는 있지만, "Jsoup으로 HTML을 긁어서 파싱한다"는 구현은 Infrastructure에 맡깁니다.

ProductParser (Port / Interface)

파일: application/port/ProductParser.kt

package com.linkcart.application.port  // port = "외부와 연결되는 접점"이라는 뜻

import com.linkcart.application.dto.ParseResult

interface ProductParser {              // interface = Python의 ABC (추상 클래스)
    fun canParse(url: String): Boolean  // "이 URL을 파싱할 수 있는가?" - 쿠팡 파서는 쿠팡 URL만 가능
    fun parse(url: String): ParseResult // "이 URL을 파싱해서 결과를 돌려줘"
}
Python ABC와 비교 
from abc import ABC, abstractmethod

class ProductParser(ABC):
    @abstractmethod
    def can_parse(self, url: str) -> bool: ...

    @abstractmethod
    def parse(self, url: str) -> ParseResult: ...
Kotlin의 interface는 Python의 ABC와 같은 역할입니다. "이 메서드들을 반드시 구현해라"라고 계약(contract)을 정의합니다. 이후 infrastructure/parser/에 CoupangParser, ElevenStParser 등이 이 인터페이스를 구현할 것입니다.
"Port"라는 이름의 의미 헥사고날 아키텍처에서 "Port"는 "외부 세계와 연결되는 접점"입니다. USB 포트를 생각하세요 — 포트 규격(interface)만 맞으면 어떤 기기든 꽂을 수 있습니다. ProductParser라는 포트에 CoupangParser를 꽂든, MockParser를 꽂든 상관없습니다. 이것이 테스트할 때 큰 장점이 됩니다: 실제 HTTP 요청 대신 가짜 파서를 꽂으면 됩니다.

ProductRepository (Port, Phase 2)

파일: application/port/ProductRepository.kt

package com.linkcart.application.port

import com.linkcart.domain.entity.Product

/** Phase 2용 — 현재는 인터페이스만 정의 */
interface ProductRepository {
    fun save(product: Product)            // 상품 저장 (Phase 2에서 DB 연동 시 구현)
    fun findByUrl(url: String): Product?  // URL로 상품 조회. ?는 null 가능(없을 수도 있음)
}
Django ORM과의 결정적 차이 Django에서는 Product.objects.filter(url=url).first()처럼 모델 클래스가 곧 DB 접근 방법입니다. 클린 아키텍처에서는 ProductRepository라는 인터페이스만 정의하고, 실제 DB 접근 코드는 Infrastructure에서 구현합니다. 이렇게 하면:
  • DB를 PostgreSQL에서 MongoDB로 바꿔도 Domain/Application 코드는 안 건드림
  • 테스트할 때 인메모리 구현체를 넣으면 DB 없이 테스트 가능
Kotlin의 ? (null safety) Product?는 "Product이거나 null일 수 있다"는 뜻입니다. Python의 Optional[Product]과 같습니다. 하지만 Python은 힌트일 뿐이고 런타임에 체크하지 않는 반면, Kotlin은 컴파일 시점에 강제합니다. Product? 타입을 Product처럼 쓰면 컴파일 에러가 납니다.

ParseResult (sealed interface)

파일: application/dto/ParseResult.kt

package com.linkcart.application.dto

import com.linkcart.domain.entity.Product

sealed interface ParseResult {        // sealed = "이 파일에서만 구현 가능" (경우의 수 한정)

    data class Success(               // 파싱 성공: 완전한 Product를 담고 있음
        val product: Product,
        val parserUsed: String,        // 어떤 파서가 파싱했는지 ("coupang", "og-tag" 등)
        val fallbackUsed: Boolean = false,  // OG 태그 폴백을 사용했는지
    ) : ParseResult                  // ParseResult를 구현한다는 선언

    data class Partial(              // 파싱 부분 성공: 일부 필드만 추출됨
        val fields: Map<String, Any>, // 추출된 필드들 (Python의 dict[str, Any])
        val parserUsed: String,
        val fallbackUsed: Boolean = false,
    ) : ParseResult

    data class Failure(              // 파싱 완전 실패
        val reason: String,            // 실패 이유
        val parserUsed: String,
    ) : ParseResult
}
sealed interface가 뭔가 sealed는 "밀봉된"이라는 뜻입니다. 이 파일 안에서만 구현체를 만들 수 있습니다. 다른 파일에서 class MyResult : ParseResult를 하면 컴파일 에러!

왜 이렇게 하냐면, 컴파일러가 "모든 경우를 빠짐없이 처리했는지" 확인할 수 있기 때문입니다. when(result)에서 Success, Partial, Failure 중 하나라도 빠지면 컴파일 에러가 납니다.
Python 등가 코드 (여러 방법) 
# 방법 1: Union 타입 (Python 3.10+)
@dataclass(frozen=True)
class Success:
    product: Product
    parser_used: str
    fallback_used: bool = False

@dataclass(frozen=True)
class Partial:
    fields: dict[str, Any]
    parser_used: str
    fallback_used: bool = False

@dataclass(frozen=True)
class Failure:
    reason: str
    parser_used: str

ParseResult = Success | Partial | Failure

# 사용:
match result:
    case Success(product=p):
        print(p.name)
    case Partial(fields=f):
        print(f)
    case Failure(reason=r):
        print(f"실패: {r}")
Kotlin의 sealed interface + when은 Python의 Union + match와 같은 패턴입니다. 차이점은 Kotlin은 컴파일러가 모든 케이스를 빠짐없이 처리했는지 검증한다는 것입니다. Python의 match는 빠진 케이스가 있어도 런타임에야 알 수 있습니다.
왜 예외(Exception) 대신 sealed interface를 쓰는가 파싱이 실패하는 것은 "예외적 상황"이 아니라 "충분히 예상되는 정상 흐름"입니다. 잘못된 URL을 넣으면 당연히 실패합니다. 이런 경우에 Exception을 던지면:
  • 호출하는 쪽에서 try-catch를 깜빡하면 프로그램이 죽음
  • 어떤 Exception이 올지 코드만 봐서는 알 수 없음
sealed interface를 쓰면 반환 타입에 모든 경우가 명시되어 있고, 처리를 강제할 수 있습니다. 이것은 Rust의 Result<T, E>이나 Go의 (value, error) 패턴과 같은 철학입니다.

6. Presentation 코드

Presentation 레이어는 HTTP 요청을 받아서 응답을 돌려주는 역할만 합니다. Django의 views.py + urls.py에 해당합니다.

HealthController

파일: presentation/api/HealthController.kt

package com.linkcart.presentation.api

import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.RestController

@RestController                      // "이 클래스는 REST API 컨트롤러다"
                                      // = Django의 @api_view 또는 APIView 클래스
                                      // 반환값을 자동으로 JSON으로 변환해줌
class HealthController {

    @GetMapping("/health")              // GET /health 요청을 이 메서드로 라우팅
                                      // Django: @api_view(['GET'])
                                      // Django urls.py: path('health', health_view)
    fun health(): Map<String, String> = mapOf("status" to "ok")
                                      // Map<String, String>을 반환하면 Jackson이 자동으로
                                      // {"status": "ok"} JSON으로 변환
}
Django 등가 코드 
# Django REST Framework
from rest_framework.decorators import api_view
from rest_framework.response import Response

@api_view(['GET'])
def health(request):
    return Response({"status": "ok"})

# urls.py
urlpatterns = [
    path('health', health),
]
Django에서는 view 함수와 URL 라우팅이 별도 파일(urls.py)에 있지만, Spring에서는 @GetMapping("/health")로 메서드 위에 직접 URL을 선언합니다. 별도 urls.py가 필요 없습니다.

어노테이션 정리

Spring 어노테이션하는 일Django 비유
@RestController 이 클래스가 REST API 컨트롤러임을 선언. 반환값을 자동으로 JSON 변환 APIView 클래스 또는 @api_view 데코레이터
@GetMapping("/path") GET 요청을 이 메서드에 매핑 urls.py의 path() + @api_view(['GET'])
@PostMapping("/path") POST 요청을 이 메서드에 매핑 @api_view(['POST'])
@RequestBody HTTP body를 객체로 자동 파싱 (역직렬화) DRF의 request.data (자동 파싱)

WebConfig (CORS 설정)

파일: infrastructure/config/WebConfig.kt

package com.linkcart.infrastructure.config

import org.springframework.context.annotation.Configuration
import org.springframework.web.servlet.config.annotation.CorsRegistry
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer

@Configuration                       // "이 클래스는 Spring 설정 클래스다"
                                      // Spring이 시작할 때 이 클래스를 찾아서 실행
class WebConfig : WebMvcConfigurer {   // WebMvcConfigurer를 구현(implements)하면
                                      // Spring MVC의 동작을 커스텀할 수 있음

    override fun addCorsMappings(registry: CorsRegistry) {
        registry.addMapping("/**")     // 모든 경로에 CORS 적용
            .allowedOrigins("http://localhost:3000")  // Next.js 개발 서버만 허용
            .allowedMethods("GET", "POST", "OPTIONS")  // 허용 HTTP 메서드
            .allowedHeaders("*")                      // 모든 헤더 허용
            .allowCredentials(true)                   // 쿠키 포함 요청 허용
    }
}
Django의 CORS 설정과 비교 
# Django: settings.py (django-cors-headers 패키지)
CORS_ALLOWED_ORIGINS = [
    "http://localhost:3000",
]
CORS_ALLOW_METHODS = ["GET", "POST", "OPTIONS"]
CORS_ALLOW_CREDENTIALS = True
Django는 settings.py에 변수로 선언하지만, Spring은 코드(Configuration 클래스)로 설정합니다. 이 방식의 장점은 조건부 로직을 넣기 쉽다는 것입니다 (예: 프로덕션에서는 다른 origin을 허용하는 등).
CORS란? 브라우저의 보안 정책입니다. Next.js 앱(localhost:3000)에서 백엔드(localhost:8080)로 API를 호출하면, 포트가 다르기 때문에 브라우저가 차단합니다. CORS 설정은 "이 origin에서 오는 요청은 허용해"라고 서버가 브라우저에 알려주는 것입니다. 프론트엔드와 백엔드가 다른 서버(포트)에서 돌아가는 경우 반드시 필요합니다.
왜 presentation/이 아니라 infrastructure/config/에 있는가? 처음에는 presentation/에 있었지만, 리뷰에서 위치를 옮겼습니다. CORS는 "HTTP 요청/응답의 비즈니스 로직"이 아니라 "웹 서버의 인프라 설정"이기 때문입니다. Django에서도 CORS 설정이 views.py가 아니라 settings.py에 있는 것과 같은 논리입니다. 이 부분은 리뷰에서 배운 것 섹션에서 더 자세히 다룹니다.

7. shared 패키지

packages/shared는 웹 앱과 모바일 앱이 공통으로 쓰는 TypeScript 코드입니다. 백엔드 API의 타입 정의, API 클라이언트, URL 검증 로직을 공유합니다.

왜 shared 패키지가 필요한가 웹(Next.js)과 모바일(Expo)이 같은 백엔드 API를 호출합니다. 각자 타입을 따로 정의하면 불일치가 생깁니다. shared 패키지에 한 번만 정의하면 양쪽 다 import { Product } from '@linkcart/shared'로 가져다 씁니다. Django에는 대응 개념이 없습니다 (서버가 하나니까 공유할 필요 없음).

TypeScript 타입 정의

파일: packages/shared/src/types/product.ts

/**
 * 상품 정보 타입 -- OpenAPI codegen으로 자동 생성될 예정.
 * PR 4(API 엔드포인트) 완성 후 codegen으로 대체됨.
 * 현재는 개발 편의를 위한 수동 정의.
 */

export interface Money {
  amount: number;       // Kotlin의 Money.amount에 대응
  currency: string;     // Kotlin의 Money.currency에 대응
}

export interface Product {
  name: string;
  price: Money;
  image_url: string;    // snake_case! (Jackson의 SNAKE_CASE 설정 덕분에 이 이름으로 옴)
  source_url: string;
  mall: string;
}

export interface ParseResponse extends Product {  // Product를 상속(확장)
  partial: Record<string, unknown> | null;       // 부분 파싱 결과 (또는 null)
  parser_used: string;                            // 사용된 파서 이름
  fallback_used: boolean;                          // OG 태그 폴백 사용 여부
}
백엔드 Kotlin과 프론트엔드 TypeScript 타입 매핑

API 클라이언트 (createApiClient)

파일: packages/shared/src/api/client.ts

ApiResult 타입

export type ApiResult<T> =
  | { ok: true; data: T }        // 성공: data에 실제 데이터
  | { ok: false; error: ApiError }; // 실패: error에 에러 정보
ApiResult<T>의 의미 <T>는 제네릭(generic)입니다. "어떤 타입이든 들어올 수 있다"는 뜻입니다. ApiResult<Product>이면 성공 시 data가 Product 타입이고, ApiResult<User>이면 data가 User 타입입니다. Python의 Generic[T]과 같은 개념입니다.

이 패턴은 앞서 본 Kotlin의 sealed interface ParseResult와 같은 철학입니다: 예외를 던지는 대신, 성공/실패를 타입으로 표현합니다.

ApiError 타입

export type ApiError =
  | { code: "NETWORK"; message: string }      // 네트워크 연결 실패
  | { code: "PARSE_FAILED"; message: string } // 서버가 파싱 실패 응답
  | { code: "TIMEOUT"; message: string }      // 15초 초과
  | { code: "UNKNOWN"; message: string };     // 그 외

TypeScript의 유니온 타입(Union Type)으로 에러 종류를 한정합니다. error.code를 보고 분기 처리할 수 있습니다.

createApiClient 함수

const DEFAULT_BASE_URL = "http://localhost:8080";
const TIMEOUT_MS = 15_000;            // 15초 타임아웃

export function createApiClient(baseUrl: string = DEFAULT_BASE_URL) {

  async function parseProduct(url: string): Promise<ApiResult<ParseResponse>> {
    const controller = new AbortController();    // 타임아웃 제어용
    const timeoutId = setTimeout(() => controller.abort(), TIMEOUT_MS);

    try {
      const response = await fetch(`${baseUrl}/api/v1/products/parse`, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ url }),   // { "url": "https://..." }
        signal: controller.signal,       // abort 시그널 연결
      });

      if (!response.ok) {                // HTTP 4xx, 5xx 응답
        const body = await response.json().catch(() => ({}));
        // 에러 응답의 body에서 detail 필드를 추출 시도
        const detail = typeof body === "object" && body !== null && "detail" in body
          ? String(body.detail)
          : `HTTP ${response.status} ${response.statusText}`;
        return { ok: false, error: { code: "PARSE_FAILED", message: detail } };
      }

      const data = (await response.json()) as ParseResponse;
      return { ok: true, data };            // 성공!

    } catch (err) {
      if (err instanceof DOMException && err.name === "AbortError") {
        return { ok: false, error: { code: "TIMEOUT", message: "요청 시간이 초과되었습니다" } };
      }
      return { ok: false, error: {
        code: "NETWORK",
        message: err instanceof Error ? err.message : "네트워크 오류가 발생했습니다",
      }};
    } finally {
      clearTimeout(timeoutId);            // 타이머 정리 (메모리 누수 방지)
    }
  }

  function imageProxyUrl(originalUrl: string): string {
    return `${baseUrl}/api/v1/images/proxy?url=${encodeURIComponent(originalUrl)}`;
  }                                      // 이미지 프록시 URL 생성 헬퍼

  return { parseProduct, imageProxyUrl };  // 팩토리 패턴: 함수들을 객체로 반환
}
팩토리 패턴 (createApiClient) createApiClient는 클래스가 아니라 함수인데, 내부에 함수들을 만들어서 객체로 반환합니다. 이것을 "팩토리 패턴"이라고 합니다. 사용하는 쪽에서는: 
const api = createApiClient("http://localhost:8080");
const result = await api.parseProduct("https://www.coupang.com/...");

if (result.ok) {
  console.log(result.data.name);   // 성공: Product 사용
} else {
  console.error(result.error.code); // 실패: 에러 코드 확인
}
baseUrl을 다르게 주면 테스트 서버나 프로덕션 서버용 클라이언트를 쉽게 만들 수 있습니다.

URL 검증 유틸

파일: packages/shared/src/validation/url.ts

const URL_PATTERN = /^https?:\/\/.+/;   // http:// 또는 https://로 시작하는지 정규식 체크

export function validateUrl(input: string): { valid: boolean; error?: string } {
  const trimmed = input.trim();          // 앞뒤 공백 제거

  if (!trimmed) {
    return { valid: false, error: "URL을 입력해주세요" };  // 빈 입력
  }

  if (!URL_PATTERN.test(trimmed)) {
    return { valid: false, error: "올바른 URL 형식이 아닙니다 (http:// 또는 https://)" };
  }

  try {
    new URL(trimmed);                    // 브라우저의 URL 파서로 최종 검증
    return { valid: true };
  } catch {
    return { valid: false, error: "올바른 URL 형식이 아닙니다" };
  }
}
Django의 URLValidator와 비교 
# Django에서는 이렇게 합니다
from django.core.validators import URLValidator
from django.core.exceptions import ValidationError

validator = URLValidator()
try:
    validator("https://...")
except ValidationError:
    print("잘못된 URL")
Django는 예외를 던지지만, shared의 validateUrl은 { valid, error } 객체를 반환합니다. 프론트엔드에서는 예외보다 이 방식이 더 다루기 쉽습니다 (UI에 에러 메시지를 바로 보여줄 수 있음).

8. 리뷰에서 배운 것

PR 1은 초기 세팅이지만, 코드 리뷰를 통해 몇 가지 중요한 수정이 있었습니다. 각 수정의 이유를 상세히 설명합니다.

Money: Int에서 Long으로 변경

Before

data class Money(
    val amount: Int,    // 32비트 정수: 최대 약 21억 (2,147,483,647)
)

After

data class Money(
    val amount: Long,   // 64비트 정수: 최대 약 922경 (9,223,372,036,854,775,807)
)
왜 Long으로 바꿨나 Int의 최대값은 약 21억입니다. 한국 원(KRW) 기준으로 21억 원이 넘는 상품은 드물지만, 만약 외화 처리나 총액 계산을 하게 되면 쉽게 넘어갈 수 있습니다.

Python은 int가 크기 제한이 없어서(arbitrary precision) 이 문제를 겪지 않지만, JVM 언어에서는 Int(32비트)와 Long(64비트)이 다릅니다. 금액에는 항상 Long을 쓰는 것이 안전합니다.
타입크기최대값Python 비유
Int32비트2,147,483,647 (약 21억)해당 없음 (Python int는 무제한)
Long64비트9,223,372,036,854,775,807 (약 922경)해당 없음 (Python int는 무제한)
BigDecimal가변사실상 무제한 + 소수점 정밀Python의 decimal.Decimal
실무에서는 BigDecimal? 달러/유로 등 소수점이 필요한 통화를 다루면 BigDecimal을 쓰기도 합니다. 하지만 KRW만 다루고, 정수 연산이면 Long으로 충분합니다. 성능도 훨씬 좋습니다.

sealed class에서 sealed interface로 변경

Before

sealed class ParseResult      // class: 상태(필드)를 가질 수 있음

After

sealed interface ParseResult  // interface: 계약(contract)만 정의
class vs interface, 왜 중요한가 Kotlin(그리고 Java)에서 클래스는 단일 상속만 됩니다. class A : B()이면, A는 다른 클래스를 상속받을 수 없습니다. 하지만 인터페이스는 다중 구현이 가능합니다. class A : InterfaceB, InterfaceC처럼 여러 개를 구현할 수 있습니다.

ParseResult는 공통 필드나 상태가 없습니다 (Success, Partial, Failure가 각자 다른 필드를 가짐). 그러므로 class일 이유가 없고, interface가 더 유연합니다.
Python에서의 비유 
# sealed class = ABC (상속을 통한 구현)
class ParseResult(ABC): ...        # 상태를 가질 수 있지만, 단일 상속만 가능

# sealed interface = Protocol (구조적 타이핑)
class ParseResult(Protocol): ...    # 상태 없이 계약만 정의, 더 유연
규칙: 공통 상태(필드)가 필요하면 sealed class, 없으면 sealed interface. ParseResult는 공통 필드가 없으므로 interface가 맞습니다.

WebConfig 위치 이동

Before

// presentation/config/WebConfig.kt  -- 잘못된 위치

After

// infrastructure/config/WebConfig.kt  -- 올바른 위치
왜 옮겼나 Presentation 레이어는 "HTTP 요청을 받아서 비즈니스 로직을 호출하고 응답을 돌려주는" 역할입니다. 컨트롤러(HealthController)가 여기에 있는 게 맞습니다.

반면 CORS 설정은 "웹 서버의 인프라 수준 설정"입니다. 비즈니스 로직과 무관하고, 어떤 origin을 허용할지는 배포 환경에 따라 달라지는 인프라 설정입니다. 그래서 Infrastructure 레이어의 config/에 있는 것이 맞습니다.

Django로 비유하면: views.py에 CORS 설정을 넣지 않고, settings.py에 넣는 것과 같은 논리입니다.

Jackson snake_case 설정

무엇이 바뀌었나

application.yml에 아래 설정이 추가되었습니다:

spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
이 설정이 하는 일 Kotlin 코드에서는 camelCase를 씁니다: imageUrl, sourceUrl, parserUsed. 하지만 REST API의 JSON 응답에서는 snake_case가 표준입니다: image_url, source_url, parser_used.

이 설정이 없으면 Jackson(JSON 라이브러리)이 Kotlin 필드명을 그대로 JSON 키로 씁니다: 
// 설정 없을 때 (camelCase)
{ "imageUrl": "...", "sourceUrl": "..." }

// SNAKE_CASE 설정 후
{ "image_url": "...", "source_url": "..." }
Django DRF와 비교 Django는 Python 자체가 snake_case 관습이라 이런 변환이 필요 없습니다. 모델 필드 image_url이 그대로 JSON에 "image_url"로 나갑니다.

하지만 Spring/Kotlin은 camelCase 관습이므로, API를 통해 프론트엔드(TypeScript, snake_case 선호)와 통신하려면 이 변환이 필수입니다. 한 줄의 설정으로 프로젝트 전체에 적용되므로, 각 필드마다 @JsonProperty("image_url")를 붙일 필요가 없습니다.
리뷰에서 배운 핵심 원칙들 정리
  1. 금액은 항상 Long: JVM에서 돈을 다룰 때 Int는 위험. 오버플로우는 디버깅 지옥
  2. 공통 상태 없으면 interface: sealed class 대신 sealed interface가 더 유연
  3. 인프라 설정은 infrastructure/config에: Presentation은 비즈니스 관련 HTTP만 담당
  4. 네이밍 전략은 글로벌 설정으로: 개별 어노테이션보다 application.yml 한 줄이 유지보수에 유리

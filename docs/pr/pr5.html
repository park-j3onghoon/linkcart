PR 5

OpenAPI 타입 동기화와 Next.js 웹 UI

이번 PR의 핵심은 "백엔드 JSON 계약을 프론트 타입으로 직접 끌어온다"는 점이다. PR 4에서 만든 POST /api/v1/products/parse 응답을 이제 수동 TypeScript 인터페이스가 아니라 OpenAPI codegen 결과로 읽고, 그 타입 위에서 웹 훅과 컴포넌트를 조합한다.

Spring Boot DTO -> /openapi.json 생성 -> openapi-typescript로 api.gen.ts 생성 -> shared 타입 래퍼(product.ts) -> web 훅/useProducts -> page.tsx에서 UrlInput + ParseProgress + ProductList 조합

왜 OpenAPI codegen을 먼저 붙이나

계약 중복 제거

백엔드 DTO와 프론트 타입을 사람이 각각 관리하면 snake_case/camelCase, nullable 여부 같은 계약이 쉽게 어긋난다. 그래서 스펙을 한 번만 만들고, 프론트는 그 산출물을 재사용한다.

런타임 계약과 문서 계약 일치

이번 PR에서는 ParseResponse OpenAPI 필드명이 실제 응답처럼 snake_case로 나오도록 백엔드 DTO에도 조정을 넣었다. 그래야 codegen 타입이 실제 JSON과 어긋나지 않는다. 

npm run codegen --workspace @linkcart/shared

packages/shared/src/types/api.gen.ts
  -> generated schema
packages/shared/src/types/product.ts
  -> 프론트에서 쓰기 쉬운 래퍼 타입

Next.js App Router에서 page.tsx와 layout.tsx는 무슨 역할인가

Next.js App Router는 Django의 URLconf + template 입구를 파일 구조로 옮긴 느낌이다. layout.tsx는 공통 html/body, 메타데이터, 폰트 같은 바깥 껍질이고, page.tsx는 실제 라우트 화면의 본문이다.

이번 PR에서는 페이지 전체가 입력과 상태 변화에 반응해야 하므로 page.tsx를 client component로 두고, 그 안에서 커스텀 훅과 프레젠테이션 컴포넌트를 조합했다.

커스텀 훅 분리: useLocalStorage vs useProducts

useLocalStorage

저장소 접근과 hydration 상태만 맡는다. 손상된 JSON이면 초기값으로 복구하고, 저장 실패는 메모리 상태만 유지한다. 즉 "영속성 기술 세부사항"을 격리한다.

useProducts

URL 중복 검사, API 호출, 진행 상태, 사용자 피드백을 맡는다. 즉 "상품 추가 유스케이스"를 프론트엔드용 상태 머신으로 표현한 훅이다. 

useProducts
  -> validateUrl
  -> 중복 URL 확인
  -> parseProduct API 호출
  -> 성공 시 localStorage-backed state 갱신
  -> phase / feedback 반환

localStorage를 안전하게 쓰는 이유

localStorage는 단순해 보이지만, 실제로는 JSON 손상, 저장소 비활성화, quota 초과 같은 실패가 생길 수 있다. 그래서 훅 안에서 try/catch로 읽기/쓰기를 감싸고, 파싱 실패 시 초기값으로 되돌린다.

중요한 점은 "저장 실패 = 앱 실패"로 만들지 않는 것이다. 이 PR에서는 저장이 막혀도 현재 세션의 메모리 상태는 계속 유지된다.

Vitest + Testing Library로 무엇을 검증했나

  • useLocalStorage.test.tsx: 초기값, 저장 후 재마운트 복원, 손상 JSON fallback
  • UrlInput.test.tsx: 빈 입력, 잘못된 URL, 정상 제출
  • ProductCard.test.tsx: 상품 정보 렌더링, 이미지 로드 실패 시 플레이스홀더
  • LinkcartBackendApplicationTests: OpenAPI 스펙이 실제 응답처럼 snake_case 필드를 노출하는지

즉 이번 PR은 화면만 만든 것이 아니라, 프론트와 백엔드 계약이 함께 깨지지 않도록 회귀 테스트를 붙인 것이다.

Q1
Kotlin에서 val과 var의 차이점으로 올바른 것은?
val name = "LinkCart"    // ???
var count = 0            // ???

name = "NewName"          // ???
count = count + 1         // ???
  • A. val은 nullable, var는 non-null을 의미한다
  • B. val은 읽기 전용(재할당 불가) 참조, var는 재할당 가능한 참조다
  • C. val은 함수 안에서만, var는 클래스 안에서만 사용 가능하다
  • D. val과 var는 같으며 스타일 차이일 뿐이다
Show Answer
B
val은 Java의 final 변수와 유사하다. 한 번 할당하면 재할당할 수 없다. var는 재할당이 가능하다. 위 코드에서 name = "NewName"은 컴파일 에러가 발생하고, count = count + 1은 정상 동작한다. 주의: val은 "불변 객체"가 아니라 "재할당 불가 참조"다. val list = mutableListOf(1,2,3)의 경우, list 자체는 바꿀 수 없지만 list.add(4)는 가능하다. Python의 관점에서 보면, 상수(convention 수준)와 비슷하지만 Kotlin은 이를 컴파일러가 강제한다. TNEAR: Kotlin 기초 문법 중 가장 빈출. Java의 final과 비교 설명 필수.
Q2
data class를 선언하면 Kotlin 컴파일러가 자동으로 생성하는 것을 모두 고르시오.
data class Money(
    val amount: Long,
    val currency: String = "KRW",
)
  • A. equals(), hashCode()
  • B. toString()
  • C. copy()
  • D. componentN() (구조 분해)
Show Answer
A, B, C, D — 전부
data class는 primary constructor의 프로퍼티를 기반으로 위 4가지를 모두 자동 생성한다.

equals/hashCode — 값이 같으면 같은 객체로 취급 (Value Object 패턴에 핵심)
toString — Money(amount=15000, currency=KRW) 형태로 디버깅 편의
copy — 일부 필드만 바꾼 새 인스턴스 생성: money.copy(amount = 20000)
componentN — val (amount, currency) = money 구조 분해 가능

Python의 @dataclass와 유사하지만, Kotlin은 copy()와 componentN()까지 포함한다. Java에서는 이 모든 것을 직접 작성하거나 Lombok @Data를 써야 하지만, Kotlin은 언어 레벨에서 지원한다. TNEAR: "Java 대비 Kotlin의 생산성 장점"을 물을 때 data class는 대표적 예시.
Q3
sealed interface와 enum class의 차이점으로 올바른 것은?
// enum: 각 항목이 고정된 싱글턴
enum class Mall(val displayName: String) {
    COUPANG("쿠팡"), ELEVENST("11번가"), GENERIC("기타"),
}

// sealed: 각 항목이 다른 데이터를 가질 수 있음
sealed interface ParseResult {
    data class Success(val product: Product, ...) : ParseResult
    data class Failure(val reason: String, ...) : ParseResult
}
  • A. enum은 각 항목이 같은 구조의 싱글턴이고, sealed는 각 하위 타입이 서로 다른 데이터를 가질 수 있다
  • B. sealed가 더 빠르기 때문에 항상 sealed를 쓰는 것이 좋다
  • C. enum은 Kotlin 전용이고 sealed는 Java에서도 사용 가능하다
  • D. 둘 다 동일하며, 이름만 다르다
Show Answer
A
enum class는 정해진 상수의 집합이다. 모든 항목이 같은 프로퍼티 구조를 갖는다. Mall.COUPANG과 Mall.ELEVENST는 모두 displayName이라는 같은 필드를 가진다.

sealed interface는 가능한 하위 타입의 집합을 제한하되, 각 타입이 서로 다른 데이터 구조를 가질 수 있다. ParseResult.Success는 Product를 갖고, ParseResult.Failure는 reason: String만 갖는다.

둘 다 when 식에서 exhaustive check를 제공한다 (모든 케이스를 처리했는지 컴파일러가 확인).
선택 기준: "값이 고정된 종류" → enum, "종류마다 다른 데이터가 필요" → sealed. TNEAR: 타입 안전한 결과 처리 패턴. API 응답 설계에서 핵심.
Q4
아래 Kotlin 코드 중 컴파일 에러가 발생하는 줄을 모두 고르시오.
val a: String = "hello"       // (1)
val b: String = null          // (2)
val c: String? = null         // (3)
val d: Int = c.length         // (4)
val e: Int? = c?.length       // (5)
  • A. (2)만
  • B. (2)와 (4)
  • C. (4)만
  • D. (2), (4), (5)
Show Answer
B — (2)와 (4)
(2) String 타입(non-null)에 null을 대입할 수 없다. String?이어야 한다.
(4) c는 String?이므로 c.length로 직접 접근할 수 없다. nullable 타입에 대한 멤버 접근은 ?.(safe call)이나 !!(not-null assertion)을 사용해야 한다.
(5) c?.length는 c가 null이면 전체 표현식이 null을 반환하므로 Int? 타입으로 합법적이다.

이것이 Kotlin의 null safety 핵심이다. 타입 시스템에서 nullable 여부를 구분하므로, NullPointerException이 컴파일 시점에 방지된다. Java에서는 모든 참조 타입이 null이 될 수 있어서 런타임에야 NPE가 발생한다. TNEAR: "Kotlin의 null safety가 Java와 어떻게 다른가?" 면접 단골 질문.
Q5
?.(safe call)과 ?:(Elvis operator)의 차이를 설명한 것 중 올바른 것은?
val url: String? = getUrl()

// safe call
val length1 = url?.length           // url이 null이면 ???

// Elvis
val length2 = url?.length ?: 0      // url이 null이면 ???
  • A. ?.은 null이면 null 반환, ?:은 null이면 우항의 기본값을 반환한다
  • B. ?.은 null이면 예외를 던지고, ?:은 null이면 0을 반환한다
  • C. 둘 다 null이면 0을 반환한다
  • D. ?.은 Java의 try-catch와 같고, ?:은 if-else와 같다
Show Answer
A
?. (Safe Call): 왼쪽이 null이면 전체 표현식이 null이 된다. url?.length에서 url이 null이면 결과는 null (Int? 타입).

?: (Elvis Operator): 왼쪽이 null이면 오른쪽 값을 사용한다. url?.length ?: 0에서 url이 null이면 length도 null이 되고, Elvis에 의해 0이 된다. 결과 타입은 Int(non-null).

Python으로 비유하면 ?.는 url.length if url is not None else None, ?:는 url?.length or 0과 유사하다 (정확히 같지는 않음).

실제 PR 1 코드에서 ProductRepository.findByUrl()의 반환 타입이 Product?인 이유도 이것이다. 조회 결과가 없을 수 있으므로 nullable을 명시한다. TNEAR: null 처리 전략은 장애 방지의 기본. 운영 서비스에서 NPE는 치명적.
Q6 Code
PR 1의 Product.kt를 읽고 질문에 답하시오.
package com.linkcart.domain.entity

import com.linkcart.domain.vo.Mall
import com.linkcart.domain.vo.Money

data class Product(
    val name: String,
    val price: Money,
    val imageUrl: String,
    val sourceUrl: String,
    val mall: Mall,
)

아래 코드의 출력 결과는 무엇인가?

val p1 = Product("Phone", Money(10000), "img.jpg", "http://a.com", Mall.COUPANG)
val p2 = Product("Phone", Money(10000), "img.jpg", "http://a.com", Mall.COUPANG)
println(p1 == p2)
  • A. true — data class의 equals가 값 비교를 하므로
  • B. false — 서로 다른 객체(인스턴스)이므로
  • C. 컴파일 에러 — ==를 직접 쓸 수 없으므로
  • D. true — 같은 메모리 주소를 가리키므로
Show Answer
A
data class의 equals()는 primary constructor의 모든 프로퍼티를 값으로 비교한다. p1과 p2는 모든 필드 값이 같으므로 true가 출력된다.

주의: Money도 data class이므로 Money(10000) == Money(10000)도 true다. 만약 Money가 일반 class였다면, 참조 비교가 되어 false가 나왔을 것이다.

Kotlin의 ==는 Java의 .equals()를 호출한다 (구조적 동등성). Java의 == (참조 비교)는 Kotlin에서 ===로 사용한다. TNEAR: Value Object 패턴의 동등성. DDD와 직결되는 개념.
Q7 Code
PR 1의 Money.kt를 보고, amount를 Double 대신 Long으로 선언한 이유로 가장 적절한 것은?
data class Money(
    val amount: Long,
    val currency: String = "KRW",
)
  • A. Kotlin에서 Double 타입이 지원되지 않아서
  • B. 부동소수점(floating point)의 정밀도 문제로 금액 계산에 오차가 생길 수 있어서
  • C. Long이 Double보다 메모리를 적게 차지해서
  • D. JSON 직렬화 시 Long만 지원되므로
Show Answer
B
Double은 IEEE 754 부동소수점으로, 0.1 + 0.2가 정확히 0.3이 되지 않는 문제가 있다. 금액 처리에서 이 오차는 결제 금액 불일치, 정산 오류로 직결된다.

Long으로 원(Won) 단위 정수를 저장하면 오차가 없다. 소수점이 필요한 통화(USD 등)는 센트 단위로 저장하거나 BigDecimal을 사용한다.

Python에서도 같은 이유로 금액 계산에 Decimal 모듈을 쓰는 것과 동일한 원칙이다. PR 1에서 currency에 기본값 "KRW"를 둔 것은, 한국 원화가 소수점이 없으므로 Long만으로 충분하다는 전제이기도 하다. TNEAR: 글로벌 서비스에서 다통화 처리는 필수. 금액 정밀도는 핵심 면접 주제.
Q8 Code
PR 1의 ParseResult.kt에서, Partial 케이스가 존재하는 이유로 가장 적절한 것은?
sealed interface ParseResult {
    data class Success(val product: Product, ...) : ParseResult
    data class Partial(val fields: Map<String, Any>, ...) : ParseResult
    data class Failure(val reason: String, ...) : ParseResult
}
  • A. 외부 쇼핑몰에서 일부 필드만 파싱 가능한 경우를 명시적으로 표현하기 위해
  • B. Kotlin 문법상 sealed interface에는 최소 3개의 하위 타입이 필요해서
  • C. 캐싱을 위한 중간 저장 단계를 표현하기 위해
  • D. Success와 Failure의 공통 필드를 추출하기 위해
Show Answer
A
실제 외부 쇼핑몰 파싱에서는 "상품명은 가져왔지만 가격은 못 가져온" 같은 부분 성공이 빈번하다. 이를 Success나 Failure로 이분법적으로 처리하면, 사용자에게 유용한 정보까지 버리게 된다.

Partial은 Map<String, Any>로 파싱된 필드들을 유연하게 담는다. 프론트엔드는 이를 받아서 "가격 정보를 가져올 수 없습니다" 같은 세분화된 UI를 보여줄 수 있다.

Success는 완전한 Product 객체를, Failure는 reason 문자열만 갖는다. 세 타입이 서로 다른 데이터를 가지므로 sealed interface가 적합한 것이다. TNEAR: 외부 API 의존성이 높은 서비스에서 부분 실패 처리 설계는 운영 안정성의 핵심.
Q9
아래 when 식에서 else 분기가 필요 없는 이유는?
fun toMessage(result: ParseResult): String = when (result) {
    is ParseResult.Success -> "success"
    is ParseResult.Partial -> "partial"
    is ParseResult.Failure -> "failure"
}
  • A. Kotlin의 when에는 else가 없기 때문에
  • B. ParseResult가 sealed이므로 모든 하위 타입이 컴파일 시점에 알려져 있고, 세 가지를 전부 처리했으므로
  • C. String 반환 타입이기 때문에
  • D. is 키워드가 자동으로 나머지 케이스를 처리하기 때문에
Show Answer
B
sealed interface의 하위 타입은 같은 파일에서만 정의할 수 있으므로, 컴파일러가 모든 가능한 타입을 알고 있다. 세 가지를 전부 처리하면 else가 불필요하다.

이것을 exhaustive when이라 한다. 만약 나중에 ParseResult.Timeout 같은 새 타입을 추가하면, 이 when을 사용한 모든 곳에서 컴파일 에러가 발생한다. 즉, 새로운 케이스를 처리하지 않는 실수를 컴파일러가 잡아준다.

Python의 match-case에는 이런 컴파일 시점 보장이 없다. mypy 등 타입 체커가 있지만 강제성이 다르다. TNEAR: 타입 안전성은 대규모 서비스에서 새 기능 추가 시 회귀 버그를 방지하는 핵심.
Q10
PR 1의 Mall enum에서 val displayName: String 프로퍼티의 용도로 가장 적절한 것은?
enum class Mall(val displayName: String) {
    COUPANG("쿠팡"),
    ELEVENST("11번가"),
    GENERIC("기타"),
}
  • A. 데이터베이스 컬럼명으로 사용하기 위해
  • B. 코드에서는 COUPANG으로 타입 안전하게 다루고, 사용자에게 보여줄 때는 한글 이름을 쓰기 위해
  • C. Spring이 자동으로 displayName을 API 엔드포인트로 등록하므로
  • D. enum 항목의 정렬 순서를 결정하기 위해
Show Answer
B
enum 상수(COUPANG)는 코드 내부에서 타입 안전하게 비교/분기하는 데 쓰인다. displayName은 사용자 인터페이스나 로그에서 읽기 쉬운 이름을 제공한다.

"coupang" 같은 raw string을 쓰면 오타가 컴파일 시점에 안 잡히고, 여러 곳에서 하드코딩된 문자열이 흩어져서 일괄 변경이 어렵다.

글로벌 서비스에서는 displayName 대신 i18n key를 넣어서 다국어 처리를 할 수도 있다. 예: COUPANG("mall.coupang") → 한국어면 "쿠팡", 영어면 "Coupang". TNEAR: 글로벌 앱에서 다국어 지원 설계를 물을 때, enum + i18n 조합을 설명할 수 있어야 한다.

Q11
./gradlew build를 실행하면 내부적으로 일어나는 일의 순서로 올바른 것은?
  • A. Kotlin 컴파일 → 의존성 다운로드 → 테스트 실행 → JAR 패키징
  • B. 의존성 해석/다운로드 → Kotlin 컴파일 → 테스트 실행 → JAR 패키징
  • C. JAR 패키징 → 테스트 실행 → Kotlin 컴파일 → 의존성 다운로드
  • D. 테스트 실행 → Kotlin 컴파일 → 의존성 해석 → JAR 패키징
Show Answer
B
Gradle build의 주요 단계:
1. 의존성 해석/다운로드 — repositories { mavenCentral() }에서 라이브러리를 받아온다
2. compileKotlin — src/main/kotlin의 소스를 JVM 바이트코드로 컴파일
3. processResources — application.yml 등 리소스를 복사
4. compileTestKotlin — 테스트 코드 컴파일
5. test — JUnit 테스트 실행
6. jar/bootJar — 실행 가능한 JAR 파일 생성

./gradlew는 Gradle Wrapper로, 프로젝트에 지정된 Gradle 버전을 자동으로 사용한다. 팀원 모두가 같은 빌드 환경을 보장받는다.

Python의 pip install + pytest + packaging을 하나의 명령어로 묶은 것과 비슷하다. TNEAR: CI/CD 파이프라인의 빌드 단계. "빌드가 뭘 하는지" 설명 못하면 운영이 어렵다.

Q22
CQS(Command-Query Separation) 패턴에서 Command와 Query의 차이는?
// 이 메서드는 Command일까, Query일까?
fun save(product: Product)              // (1)
fun findByUrl(url: String): Product?   // (2)
  • A. Command는 상태를 변경하고 값을 반환하지 않는다. Query는 상태를 변경하지 않고 값을 반환한다. (1)은 Command, (2)는 Query.
  • B. Command는 읽기 전용, Query는 쓰기 전용이다
  • C. Command와 Query는 같은 메서드에서 동시에 수행해야 한다
  • D. CQS는 데이터베이스 전용 개념이고 API에는 적용되지 않는다
Show Answer
A
Command: 시스템의 상태를 변경한다. 반환값이 없거나 성공/실패만 반환한다. save(product)는 DB에 저장하므로 Command이다.

Query: 시스템의 상태를 변경하지 않고, 데이터를 조회만 한다. findByUrl(url)은 DB를 읽기만 하고 변경하지 않으므로 Query이다.

CQS 원칙: "질문을 한다고 답이 바뀌면 안 된다." 즉, Query가 상태를 변경하면 안 된다. 이 원칙을 따르면 코드의 예측 가능성이 높아진다.

CQRS는 CQS를 아키텍처 레벨로 확장한 것으로, Command와 Query를 아예 다른 모델/DB로 분리한다. 대규모 서비스에서는 읽기 부하와 쓰기 부하가 다르므로 CQRS가 유용하다. TNEAR: 대규모 트래픽에서 읽기/쓰기 분리는 확장성의 핵심. CQRS까지 설명하면 가산점.

Q25 Essay
의존성 역전(Dependency Inversion)이 왜 필요한지, PR 1의 ProductRepository 인터페이스를 예시로 설명하시오.
Show Answer
Model Answer
의존성 역전 원칙(DIP): "고수준 모듈(비즈니스 로직)이 저수준 모듈(DB, 외부 API)에 직접 의존하지 말고, 추상(인터페이스)에 의존해야 한다."

PR 1 예시:
ProductRepository 인터페이스는 Application 레이어에 있다. Application의 Use Case는 이 인터페이스에만 의존한다: 
// Application 레이어 (고수준)
class ProductParseUseCase(
    private val repository: ProductRepository  // 인터페이스에 의존
)
구현체는 Infrastructure에 위치한다: 
// Infrastructure 레이어 (저수준)
class JpaProductRepository : ProductRepository {
    override fun save(product: Product) { /* JPA 사용 */ }
    override fun findByUrl(url: String): Product? { /* ... */ }
}
왜 필요한가?
1. 테스트: 테스트에서는 InMemoryProductRepository를 주입하면 DB 없이도 테스트 가능
2. 교체: JPA에서 MongoDB로 바꿔도 Use Case 코드는 수정 없음
3. 병렬 개발: 인터페이스만 합의하면 Use Case 개발과 Repository 구현을 동시에 진행 가능

Django에서 Product.objects.filter(...)를 직접 호출하는 것은 의존성 역전이 없는 상태다. DB를 바꾸려면 그 코드를 전부 찾아서 수정해야 한다. TNEAR: DI + DIP 조합은 "테스트하기 쉬운 코드"의 기반. 면접에서 반드시 나온다.

Q27 Interview
"Kotlin의 null safety가 Java와 어떻게 다른가요? 실제로 어떤 이점이 있나요?"

4-6 sentence answer. PR 1의 코드를 예시로 사용하세요.

Show Answer
Key Points
1. 타입 시스템 레벨 구분: Java에서는 모든 참조 타입이 null이 될 수 있다. String name = null;이 합법이다. Kotlin은 String(non-null)과 String?(nullable)을 타입 시스템에서 구분한다. val name: String = null은 컴파일 에러다.

2. 컴파일 시점 방지: Java에서는 NPE가 런타임에 터진다. 프로덕션에서 발견되면 장애다. Kotlin은 nullable 타입에 안전하지 않은 접근을 컴파일 시점에 잡는다.

3. PR 1 예시: ProductRepository.findByUrl(url: String): Product?에서 반환 타입이 Product?다. 호출하는 쪽은 반드시 null 체크를 해야 한다. ?., ?:, let 등의 안전한 연산자를 강제한다.

4. 운영 이점: 24/7 운영되는 글로벌 서비스에서 NPE로 인한 장애는 치명적이다. Kotlin의 null safety는 이런 유형의 장애를 구조적으로 줄여준다. Java에서는 @Nullable, Optional 등으로 부분적으로 대응하지만 강제성이 없다. TNEAR: "24시간 365일 장애 없는 환경"을 언어 레벨에서 지원하는 사례로 연결.

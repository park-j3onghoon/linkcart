PR 6

Expo React Native 모바일 UI 구현

이번 PR은 PR 5에서 만든 웹 흐름을 모바일 앱으로 옮기는 단계다. 핵심은 UI를 새로 짜는 것이 아니라, @linkcart/shared의 API 클라이언트와 URL 검증을 그대로 재사용하고, 저장소만 AsyncStorage로 바꿔 모바일 문법에 맞게 감싼다는 점이다.

shared createApiClient / validateUrl -> mobile useProducts -> useAsyncStorage -> UrlInput / ParseProgress / ProductList / ProductCard -> App.tsx에서 SafeArea + StatusBar + FlatList 조합

React Native는 왜 div 대신 View/Text/Image를 쓰나

React DOM은 브라우저 노드를 그리지만, React Native는 iOS/Android의 네이티브 위젯 트리를 그린다. 그래서 웹의 div, p, img 대신 View, Text, Image를 사용한다.

즉 JSX 문법은 비슷하지만 렌더링 타겟이 다르다. 이번 PR의 카드 컴포넌트도 구조는 웹과 유사하지만, 실제 구현은 StyleSheet와 RN 컴포넌트 조합으로 다시 작성했다.

AsyncStorage는 localStorage와 무엇이 다른가

비동기 API

브라우저의 localStorage는 동기 API지만, AsyncStorage는 Promise 기반 비동기 저장소다. 그래서 hydration 단계 자체가 비동기 흐름이 된다.

손상 데이터 복구

이번 PR의 useAsyncStorage는 JSON 파싱 실패 시 값을 지우고 초기값으로 복구한다. 저장 실패도 앱 전체 실패로 번지지 않게 메모리 상태만 유지한다. 

useAsyncStorage
  -> AsyncStorage.getItem(key)
  -> JSON.parse
  -> 실패 시 removeItem + initialValue fallback
  -> 성공 시 state hydrate
  -> 이후 state 변경분을 setItem으로 저장

FlatList를 왜 중심에 두나

모바일에서 목록이 길어지면 모든 카드를 한 번에 그리는 방식은 메모리와 스크롤 성능에 불리하다. FlatList는 화면에 필요한 아이템만 가상화해서 렌더링한다.

그래서 App 전체를 ScrollView로 감싸지 않고, 헤더를 FlatList.ListHeaderComponent로 붙여서 리스트가 스크롤의 중심이 되도록 구성했다. 이게 모바일 성능 관점에서 더 boring하고 안전한 구조다.

shared 패키지 재사용이 실제로 주는 이점

  • URL 형식 검증 규칙을 웹과 모바일이 따로 유지하지 않는다.
  • 파싱 API 호출/에러 매핑 로직을 한 곳에서 공유한다.
  • 백엔드 OpenAPI가 바뀌면 generated 타입 한 번 갱신해서 양쪽 UI가 함께 따라간다.

즉 "웹 따로, 모바일 따로"가 아니라, 플랫폼별로 달라야 하는 저장소와 렌더링만 각자 구현하고 나머지는 공유하는 구조다.

Jest + React Native Testing Library로 무엇을 검증했나

  • useAsyncStorage.test.tsx: 초기값, 저장 후 재마운트 복원, 손상 데이터 fallback
  • UrlInput.test.tsx: 빈 입력 에러, 정상 URL 제출
  • ProductCard.test.tsx: 상품 정보 정상 렌더링

모바일 테스트는 브라우저 DOM이 아니라 네이티브 컴포넌트 트리를 검사한다는 점만 다르고, "입력 → 상태 변화 → 화면 결과"를 계약으로 고정한다는 원리는 웹과 같다.
